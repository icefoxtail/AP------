# Archive 2.0 "한 길 완성 체계" 업그레이드 계획서 (2026-11-16)

같은 폴더의 `DRAFT.md`(외부 초안)와 `REVIEW.md`(검토)를 합쳐 정리한 판이다. 초안의 구조는 유지하고, 저장소 실제 사정과 어긋난 전제를 고쳤다. 이 문서의 새 경로·명령·필드는 구현 제안이고, 현행 사실에는 근거 경로나 "오늘 실측"(2026-11-16 작업에서 실제로 겪은 일)을 붙였다. 실행하지 않은 검사는 맨 끝에 NOT_RUN으로 적었다.

## 1. 한 쪽 요약

**결론: 시험지 하나를 한 꾸러미로 받아 내용·메타·등록을 함께 마치고, 완성도 검사 도구가 "끝났다"를 판정한다. 첫 구현물은 그 검사 도구다.**

| 항목 | 지금 | 이후 |
| --- | --- | --- |
| 지시 | 발문·그림·난이도·유형·4칸을 따로 의뢰 | "이 기출 완성해", "유사문항 만들어", "빈 곳 채워" 세 마디가 같은 길로 들어감 |
| 작업 단위 | 같은 시험지의 요청·등록 상태가 여러 곳에 흩어짐 | 시험지 1개 = 꾸러미 1개. 병합은 꾸러미 여러 개를 묶어 한 번에(6장) |
| 끝 판단 | 값이 있거나 개별 PASS면 끝난 것으로 추정 | 문항별 상태표로 내용·메타·등록을 각각 확인 |
| 원문 수정 | 그림 하나만 바꿔도 지문 불일치로 메타가 막힘 | 번호표(UID)로 찾아 무엇이 바뀌었는지 판정, 값은 유지하고 꼬리표만 |
| 유형 | 판정기와 대응표에 묶여 대부분 빈칸 | 조회·직접 판정·새 키 신설 모두 정식. 같은 뜻은 상위 묶음으로 |
| 비용 | 판정과 형식 수리가 섞여 상위 모델이 다 함 | 저렴한 모델 독립 2회 → 기계 대조 → 갈린 것만 3차 |
| 생성 | 유사문항과 부족 유형 보충이 별도 작업 | 단원×유형×풀이 방법×난이도 지도로 빈 곳을 찾아 같은 꾸러미로 |

**완성과 이용 가능은 다르다.** 새로 만드는 꾸러미는 필수 메타가 남으면 미완성이다. 이미 있는 문항은 유형·4칸이 비었다고 검색·출제·출력에서 빼지 않는다(4칸 계약 §11, 메타 OS §0).

**순서.** ① 완성도 검사 → ② 재결속 연결과 지금 채우기 마감 → ③ 유형 길 열기 → ④ 새 기출 꾸러미 → ⑤ 유사문항 → ⑥ 빈 곳 지도. 검사를 맨 앞에 둔다. 남은 일을 같은 기준으로 봐야 중복 판정과 거짓 완료가 줄기 때문이다. 진행 중인 채우기는 멈추지 않고 검사 결과에 합류시킨다.

## 3. 완성도 검사 도구 (첫 구현)

**결론: 읽기 전용 도구 하나가 문항별로 "무엇이 있고 무엇이 남았는지"를 보여 준다. 작업자의 종료 조건이자 밀린 일 목록이다.**

- 명령(제안): `node archive/tools/completion/check.mjs --exam <시험지 경로>` / `--grade m2` / `--all`, 출력 `--format json|tsv`. 저장소 안에 파일을 쓰지 않는다.
- 입력: 현재 시험지 JS와 그림, 정본 메타(`archive/data/question_metadata.json`), 4칸 파일과 등록 인덱스, 등록 대기·거절 목록, 유형·단원 레지스트리, source-delta 결과.

**문항별로 보여 주는 칸**

| 칸 | 값 | 판정 방법 |
| --- | --- | --- |
| 발문·보기·정답·해설 | 있음 / 없음 / 틀 문장(내용 없는 상투 해설) | 도구 |
| 그림 | 필요 없음 / 있음 / 참조는 있는데 파일 없음 / 깨진 SVG | 도구 (그림이 필요한지는 발문의 그림 참조로 판단) |
| 단원·소단원 | 승인 / 값만 있음 / 없음 / 키와 이름 불일치 | 도구 |
| 난이도 | 승인 / 숫자만(보조 3칸 없음) / 없음 / 허용 밖 값 | 도구 |
| 유형 | 승인 / 값만 있음 / 보류 / 없음 / 키가 죽었거나 상위 불일치 | 도구 |
| 4칸 | 등록 / 작성됨·미등록 / 없음 / 원문 변경으로 대기 | 도구 |
| 원문 변경 | source-delta 등급과 세부 표시 | 도구 |
| 종합 | 완성 / 등록 대기 / 작업 중 / 막힘(사유) | 위 칸에서 계산 |

- 저장된 "완료" 선언을 믿지 않고 실제 파일과 값에서 매번 계산한다.
- 집계는 시험지·학년·전체 단위로 내고, 칸별 부족 수(서로 겹침)와 종합 상태 수(합이 전체와 같음)를 구분해 보여 준다.
- CI에서는 `--require complete`를 꾸러미 PR에만 건다. 기존 문항의 부족은 CI를 막지 않는다.
- 수학적으로 맞는지, 그림이 문제와 맞는지는 이 도구가 판정하지 못한다. 그 확인은 5장의 길에서 한다.

**완료 기준:** 오늘 GPT가 34분 들여 낸 중등 검수표(384개 시험지·9,139문항)의 주요 수치를 명령 한 번으로 재현하고, 사람이 고른 정상·결함 표본 30문항에서 판정이 일치한다.

## 4. 재결속 (이미 등록된 문항을 고칠 때)

**결론: main 병합 때 등록기가 번호표로 문항을 찾아 옛 판본과 비교하고, 문제가 같으면 메타를 그대로 따라가게 한다.**

| 바뀐 것 | 메타 처리 | 꼬리표 |
| --- | --- | --- |
| 그림만, 표기만 | 전부 유지, 승인 상태 유지 | 변경 종류만 기록 |
| 해설만 | 단원·유형·난이도 유지. 4칸의 풀이 방법 칸만 검토 대기 | 검토 대기(방법) |
| 발문·보기 수정 | 값은 계속 쓰되 검토 대기 | 검토 대기 |
| 정답: 빈 칸이 채워짐 | 유지 | 변경 종류만 기록 |
| 정답: 값이 바뀜 | 값은 계속 쓰되 검토 대기 | 검토 대기 |
| 다른 문항으로 교체 | 옛 값을 화면에 내지 않고 재분류 대기 | 교체 |
| 번호 불일치 | 재결속하지 않음 | 확인 필요 |

- 등급만 보지 않고 세부 표시(그림도 같이 바뀌었는지, 지문에 안 잡히는 다른 키가 바뀌었는지)를 함께 조건으로 쓴다. 수식 밖 숫자 사이 공백을 같은 값으로 보는 구멍은 막는다(PR #2262 검수 지적).
- 승인 상태를 올리지는 않는다. 검증은 유지한다: 번호표·순번·문항 수, 옛 판본이 실제 git 이력에 있는지, 값이 재결속 전후로 같은지.
- 구현은 세 걸음: 판정 도구(끝) → 등록기 재결속 경로(기능을 꺼 둔 채 넣고 보고서 확인 뒤 켬) → 화면·4칸 꼬리표와 교체 문항 차단.
- 예상 효과(추정): 지문 때문에 막힌 약 6,300건 중 4,600건 이상, 4칸 "원본이 바뀜" 대기 1,363건의 대부분.
- 그림 라인 운영 규칙: 그림만 바꾸는 PR과 본문 오류를 고치는 PR을 나누고, PR 설명에 문항별 변경 종류를 적고, 순번과 문항 수를 바꾸지 않는다.

## 5. 세 가지 길

**결론: 세 길 모두 "내용 → 독립 풀이 확인 → 메타 판정 2회 → 그림·화면 → 꾸러미 검사 → 병합·등록 확인"으로 닫힌다. 실패하면 그 단계로만 돌아간다.**

### 5-1. "이 기출 완성해"

| 단계 | 담당 | 산출물 | 합격 기준 |
| --- | --- | --- | --- |
| 1. 범위 | 도구 | 문항 목록과 지금 완성도 표 | 문항 누락·중복 0 |
| 2. 내용 | 저렴한 모델, 어려운 것만 상위 모델 | 발문·보기·정답·학생용 해설 | 교육과정 안의 풀이, 답이 하나로 정해짐 |
| 3. 독립 풀이 | 내용을 쓰지 않은 다른 모델 | 정답·해설을 가린 채 푼 답 | 저장된 정답과 일치. 다르면 2로 |
| 4. 메타 | 서로 다른 저렴한 모델 2회 + 도구 대조, 갈리면 3차 | 단원·난이도·유형·연결 개념·조건·4칸 | 근거 구절이 원문에 있음, 키가 살아 있음, 둘 일치 또는 셋 중 둘 |
| 5. 그림·화면 | 그림 작성 모델 + 도구 | SVG 또는 기존 그림, 렌더 결과 | 도구가 전 문항 렌더·잘림·넘침 검사. 눈 확인은 그림 문항과 도구가 표시한 문항(PC·휴대폰) |
| 6. 꾸러미 검사 | 도구 | 목록 파일과 등록 요청 | 완성도 검사 `--require complete` 통과 |
| 7. 병합·등록 | 병합 담당(6장) | 등록 결과 | 정본에서 대상 문항의 값을 다시 읽어 일치 |

- 3단계와 4단계는 다른 일이다. 3은 답이 맞는지(해설을 보지 않고 품), 4는 분류(해설을 읽고 판정하되 서로의 판정은 보지 않음).
- 같은 모델로 4단계의 두 판정을 다 받으면 독립성이 약하다. 한쪽은 다른 모델로 받는다.
- 학생 화면 기준: "학생이 풀고 해설을 이해할 수 있는가". 수치상 완벽을 요구하지 않는다.

### 5-2. "이 기출의 유사문항 만들어"

5-1과 같되 앞에 두 단계가 붙는다.

1. **원본 이해:** 원본의 핵심 풀이, 유지할 구조, 바꿀 조건·수치를 뽑는다. 원본 자체에 결함이 있으면 먼저 원본을 고친다.
2. **제작:** 수치만 바꿔 조건이 무너지지 않는지, 답이 하나로 정해지는지 확인한다.

- 유사문항의 메타는 원본에서 복사하지 않는다. 완성된 유사문항을 5-1의 4단계로 다시 판정한다. 원본과의 관계(어느 문항에서 만들었는지)만 따로 적는다.
- 닮은 도형은 실제 닮음비대로, 분수는 세로분수로, 같은 배율 그래프 등 기존 그림 규칙(`docs/agents/visual-svg.md`)을 따른다.

### 5-3. "빈 곳 채워"

7장의 지도에서 고른 칸을 생성 명세로 바꿔 5-2의 제작 단계부터 들어간다. 생성 뒤 판정된 실제 칸이 목표 칸과 다르면 메타를 목표에 맞춰 덮어쓰지 않는다. 문항은 실제 칸에 보존하고 원래 빈 칸은 미해결로 남긴다.

### 5-4. 기존 4단계 라인과의 관계

지금 새 기출은 예약 라인(제작 → 1차 → 2차 → 3차 검수)이 만들고 Git에는 쓰지 않는다. 꾸러미 길과의 관계는 사용자 결정이다(9장 결정 1). 추천: **새 시험지는 꾸러미 길로 받고, 예약 라인의 검수 규칙 가운데 "정답·해설을 가린 독립 풀이"와 "그림 직접 확인"만 5-1의 3·5단계로 가져온다.** 4번 반복하던 전 문항 검수를 독립 풀이 1회 + 메타 판정 2회로 줄이는 것이 "한 줄 지시로 끝까지"에 맞다.

## 6. 꾸러미와 병합 길

**결론: 파일은 옮기지 않고 목록 파일로 묶는다. 병합은 꾸러미 단위가 아니라 묶음 단위로 하고, 등록기는 한 번에 하나만 돈다.**

### 6-1. 꾸러미 구성

| 위치 | 내용 | 구분 |
| --- | --- | --- |
| `archive/exams/**/<시험지>.js` | 발문·보기·정답·해설, 인라인 메타 | 기존 위치 |
| `archive/assets/images/<시험지>/` | 그림 | 기존 위치 |
| `archive/data/item-4slot/**/<시험지>.4slot.json` | 4칸 | 기존 위치 |
| `archive/data/exam-bundles/<시험지>.bundle.json` | 목록 파일: 문항 수, 문항별 번호표·순번, 파일과 그림의 해시, 문항별 메타 값과 판정 근거(판정 2~3회의 모델·일치 방식), 부분 완성 표시 | 신설 |

- 등록 요청의 "이전 값"·해시·문항 수는 도구가 만든다. 모델은 값과 근거만 낸다.
- 판정 원장 원본, 캡처, 로그는 Git에 넣지 않는다(`docs/agents/git-evidence.md`).
- 부분 완성 표시: 유형 보류(사유), 그림 없음(파일이 저장소에 없음), 4칸 일부 미작성. 표시가 있으면 "완성"이 아니라 "부분 등록"으로 들어간다.

### 6-2. 지금 막힌 곳 (오늘 실측, 꾸러미 길을 열려면 고쳐야 함)

| 막힌 곳 | 사실 | 할 일 |
| --- | --- | --- |
| 등록 요청 형식이 여러 개 | 난이도 요청, 단원 요청, 4칸 파일이 따로이고 서로 지문으로 묶임 | 목록 파일 하나를 받는 입력을 등록기에 추가. 기존 형식은 어댑터로 유지 |
| 유형 보류 문항이 CI에서 막힘 | `tools/ci/archive-pr-native-preview.mjs`가 유형 미배정 행을 난이도 요청일 때만 허용 → `CONSUMER_NOT_PASS` | 부분 등록 표시가 있는 행을 허용하도록 조건 정리 |
| 4칸 부분 제출 | 서로 다른 작성자·검토자 영수증 필요, 변환물을 받는 어댑터 없음, 기존 4칸이 일부 있는 시험지에 나머지를 더하는 길 없음(금당중 2개 시험지 보류) | 꾸러미 판정 근거(독립 2회 일치)를 영수증 종류로 인정하는 추가 경로 |
| 그림 안의 `#` 참조 오인 | `verify-archive-content-scope`가 SVG 안의 `url(#arrow_r)`을 파일 참조로 봄 | `#`으로 시작하는 참조는 건너뜀(검사 완화가 아니라 오인 수정) |

### 6-3. 병합 처리량 (초안에 없던 가장 큰 위험)

오늘 실측: main 병합마다 등록기가 20~60분 돌고 그 사이 다른 병합이 오면 취소된다. PR CI의 `test`는 45분 제한이라 요청 306개짜리 PR이 취소됐고, Chrome 확인 단계는 8분 제한이라 시험지 74개 PR을 5개로 쪼갰다.

- **묶음 병합:** 꾸러미는 시험지 단위로 만들되 병합 PR은 시험지 5~10개 묶음으로 한다.
- **직렬화:** 등록기가 도는 동안 메타에 영향을 주는 병합은 대기한다. 병합 담당을 한 곳으로 정하고(9장 결정 2), 대기 중인 PR 목록을 한 화면에서 본다.
- **등록기 시간 단축:** 바뀐 시험지만 다시 계산하도록 하는 것이 근본 해결이다. 지금은 전체를 다시 만든다(확인 필요: `archive-main-auto-meta` 워크플로의 단계별 소요 시간 측정).
- 이 세 가지가 없으면 꾸러미 길은 CI 대기에서 멈춘다. 3단계(8장)의 완료 조건에 넣는다.

## 7. 유형 열기와 빈 곳 지도

### 7-1. 유형(PT/TPL)

**결론: 근거가 있으면 어느 길로 낸 값이든 받는다. 같은 뜻의 키가 늘어나는 것은 상위 묶음으로 정리한다.**

- 2026-11-16 결정으로 "공식 판정기 결과만" 제한을 없앴다(문서 PR #2288).
- 등록기는 이미 요청의 유형 값을 직접 받는다. 검사는 키가 살아 있는지, 틀(TPL)의 상위 유형(PT)이 맞는지, 교육과정 연결 행이 있는지다(`reviewed-exam-registration-v2.mjs`의 `resolve()`, 코드 읽기로 확인).
- 코드에 남은 잠금 셋: ① 교육과정 연결 행이 없으면 거부 → 요청 생성기가 행을 추가만 하는 방식으로 자동 생성 ② 유형 보류로 등록된 문항에 나중에 유형을 채우는 경로 ③ 새 기출 생산 단계의 판정기 일치 강제(`completion-evidence.mjs`) → 불일치를 오류가 아니라 "대응표 행 추가 후보"로.
- **새 키를 만드는 기준:** 같은 상위 유형 아래 기존 정의를 읽어도 결정 단계의 풀이 구조를 담을 키가 없을 때. 숫자·학교·표기만 다르면 기존 키를 쓴다. 이름은 기존 형태(`TPL_<범위>_<풀이 구조>`)를 따르고, 정의는 특정 시험의 수치 없이 풀이 순서로 쓴다.
- **상위 묶음:** 키 → 대표 유형 묶음 표를 따로 둔다. 원래 키와 판정은 보존하고, 화면과 지도는 묶음을 읽는다. 묶이지 않은 키는 "미분류 묶음"으로 보인다.
- **판정 방식:** 유형은 선택지가 많아 저렴한 모델에 전체 목록을 주면 일치율이 떨어진다. 단원이 정해진 뒤 그 단원의 유형 목록만 주고 고르게 하고, 맞는 것이 없으면 "새 키 후보"를 이름·정의와 함께 내게 한다(확인 필요: 단원별 유형 목록 크기와 시범 일치율).

### 7-2. 빈 곳 지도

**결론: "0개"를 바로 생성 지시로 바꾸지 않는다. 메타가 비어서 안 보이는 것과 진짜 없는 것을 먼저 가른다.**

- 칸: 과목·단원 × 유형 묶음 × 4칸 풀이 방법 묶음 × 난이도 1~5. 출처(기출·교과서·문제집·생성)는 필터다.
- 칸마다 세는 것: 확정 문항 수, 그 단원에서 유형·4칸·난이도가 아직 없는 문항 수(불확실 분모).
- 진짜 공백으로 보는 조건: 그 단원의 불확실 분모가 0에 가깝고(기준은 9장 결정 5), 교과서·문제집에는 그 칸이 있다.
- 생성 우선순위: ① 교과서·문제집에는 있는데 기출에 없는 유형 ② 같은 유형의 특정 난이도 공백 ③ 같은 유형인데 풀이 방법이 다른 변형. 처음에는 칸마다 1문항만 만들어 본다.
- 지도는 유형과 4칸이 채워진 범위부터 의미가 있다. 중3 1학기처럼 채우기가 끝난 범위에서 먼저 시범한다.

## 8. 단계와 완료 기준

| 단계 | 하는 일 | 완료 기준 |
| --- | --- | --- |
| 0. 지금 마감 | 중등 판정 최종값 표와 등록, 4칸 PR, 중3 1학기 등록, 유형 문서 PR | 해당 PR 병합과 등록기 성공 확인 |
| 1. 완성도 검사 | 3장의 도구와 전 학년 기준선 | 3장의 완료 기준 |
| 2. 재결속 | 등록기 재결속 경로, 화면·4칸 꼬리표 | 중3 1학기 소급 적용에서 값 손실·잘못된 결속 0, 4칸 대기 감소 확인 |
| 3. 꾸러미 길 | 목록 파일 입력, 6-2의 막힌 곳 넷, 6-3의 병합 길, 판정 라인 도구를 저장소로 | 새 시험지 1개가 지시 한 줄로 등록까지. 같은 입력 재실행에 중복 없음 |
| 4. 유형 | 7-1의 잠금 셋, 상위 묶음 표, 단원별 유형 판정 시범 | 중등 한 학기의 유형 빈칸이 판정 2회 일치로 채워짐 |
| 5. 유사문항 | 5-2의 길 | 기출 1개에서 유사 시험지 1개를 등록까지 |
| 6. 빈 곳 | 7-2의 지도와 생성 | 한 단원에서 진짜 공백 1~3칸을 채우고 지도에서 늘어난 것 확인 |

- 0~2는 서로 이어져 있어 바로 간다. 3과 4는 병행할 수 있다.
- 일정은 약속하지 않는다. 단계마다 실제 시험지로 끝까지 통과한 것을 보고 다음으로 간다.

**스킬과 실행기.** 규칙 본체는 저장소 문서 한 장(`docs/agents/one-route.md`, 3단계에서 작성)과 도구다. Claude 스킬 세 개(`기출 완성`, `유사문항 생성`, `빈 곳 채우기`)는 그 문서를 읽고 도구를 부르는 껍데기로 둔다. 다른 실행기는 같은 문서를 읽는다.

## 10. 비용과 모델 배분

| 일 | 모델 | 근거 |
| --- | --- | --- |
| 대량 판정 1차·2차 | `opencode-go/deepseek-v4.1-flash`와 다른 모델 하나 | 실측: 형식 통과 6/6, 난이도 일치 70%(전부 1단계 이내), 소단원 87%, 그림(PNG) 읽음 |
| 갈린 문항 3차 | 저렴한 다른 모델 → 남으면 Sonnet | 갈리는 비율: 난이도 28%, 단원 15% |
| 형식 구제 | 도구, 안 되면 Sonnet | 탈락의 대부분은 인용 글자 불일치와 필수 칸 누락 |

- 가장 큰 절감은 이미 있는 값을 다시 판정하지 않는 것이다. 재결속이 그 역할을 한다.
- 판정에는 전체 목록 대신 그 단원의 선택지만 준다.
- opencode는 동시 6줄 안팎, 내부 DB 용량을 지켜본다(오늘 15.9GB).

## 12. 확인하지 않은 것

- NOT_RUN: 이 계획서를 위한 새 측정, 등록기에 유형 값을 직접 넣는 실제 실행, 등록기 단계별 소요 시간 측정, 단원별 유형 목록 크기 조사.
- 이 문서의 중등 수치는 GPT 검수 보고와 오늘 판정 라인의 보고 값이다. 완성도 검사 도구의 기준선이 나오면 그 값으로 바꾼다.
- 봉인 문서(`docs/rules/MANIFEST.md` 등재), 대응표 봉인, 4칸 사전, 기존 등록 영수증은 이 계획의 어느 단계에서도 고치지 않는다. 새 규칙은 다른 문서에 적고 우선 적용을 명시한다.
