# 작업 13 — 그림 장부를 시험지별 파일로 쪼개고, 그림 작업 도구를 빠르게 (초벌)

## 왜
사용자 말: "엔진은 완성됐는데 SVG 작업 속도가 너무 느려 한 번에 많은 양을 처리 못 한다. 엔진을 만든 이유가 대량 작업이었다." "그림 장부를 쪼개 버리면 되지." "장부·병합기 등 사용하는 도구들의 최적화가 제일 중요할 듯."

지금 그림 장부는 `archive/tools/geometry-equation/production/exam-figure-ledger.json` 한 파일(4.1MB)이다. 내용은 시험지·문항별로 나뉘어 있지만 모든 그림 작업이 이 파일 하나를 고친다(하루 15회 이상). 그래서 서로 다른 시험지를 다루는 그림 PR끼리도 충돌해 한 번에 하나씩만 병합된다. 일부 문항만 다시 게시하면 같은 시험지의 기존 PUBLISHED가 OPEN으로 덮인 사고도 있었다. 목표는 **여러 시험지의 그림을 동시에 만들고 동시에 병합할 수 있게** 하는 것이다.

## 어디에 쓰나
코드 브랜치 `feat/figure-ledger-split-20261117`(최신 `main`에서), 보고 `TASK-13-REPORT.md`(계획 브랜치). 유형 판정(작업 10~12)과 파일이 겹치지 않으니 병행한다.

## 먼저 조사 (보고서 1절)
1. 장부를 읽거나 쓰는 곳 전부와 각자 하는 일: `archive/tools/geometry-equation/ops/svg-m1/`의 `ledger-upsert.py`, `publish-exam.py`, `exam-status.py`, `cmp-triage.py`, `academy-pipeline/ledger-repair.cjs`, `academy-pipeline/planmatch.py`, `portable-publish.test.mjs`, `ops/claude-batch/ledger2md.cjs`, `make-dec-open.cjs`, 그리고 `exam-figure-queue.md`를 만드는 곳. 테스트·CI·화면 코드가 장부를 읽는지도 `git grep exam-figure-ledger`로 확인.
2. 도구마다 한 번 실행에 걸리는 시간과 그 이유(전체 장부 파싱, 전체 시험지 JS 로드, 그림 파일 전수 확인, 파이썬 프로세스 반복 기동 등). 실제로 재서 표로.
3. 그림 하나를 게시하는 길(사양 → 렌더 → 검사 → 장부 → 시험지 JS 반영)에서 도구가 부르는 순서와, 시험지 하나 게시에 도구가 총 몇 번·몇 초 도는지.
4. 장부 항목의 필드와 상태값, 시험지 CLOSED 규칙이 어디서 강제되는지.

## 만들 것
1. **저장 형식:** `archive/tools/geometry-equation/production/exam-figure-ledger/<시험지 src 경로를 따른 하위 폴더>/<시험지 이름>.json` — 시험지 하나에 파일 하나. 내용은 지금 `exams[]`의 한 원소 그대로(필드·순서·줄바꿈 LF 유지). 맨 위 규칙 문구 같은 공통 머리는 `exam-figure-ledger/_meta.json`.
2. **공용 읽기·쓰기 모듈**(파이썬과 Node 각각 얇게, 같은 규칙): `load_all()`(지금 한 파일과 **바이트 의미가 같은** 객체를 돌려준다), `load_exam(src)`, `save_exam(src, obj)`(그 시험지 파일만 쓴다, 정렬·들여쓰기 고정), `upsert_item(src, ord, patch)`. 쓰기는 항상 **문항 단위 병합**이어야 한다: 넘겨받지 않은 문항의 상태를 바꾸지 않는다(부분 게시가 기존 PUBLISHED를 덮던 사고의 재발 방지). 이것을 테스트로 고정한다.
3. **이전 도구:** 지금 한 파일을 쪼개는 `split-ledger`(되돌려 합치는 `join-ledger` 포함). 쪼갰다가 합치면 원본과 내용이 같아야 한다(테스트).
4. **기존 도구를 공용 모듈로 옮긴다**(위 1절 목록 전부). 동작은 그대로, 시험지 하나를 다룰 때는 그 시험지 파일만 읽고 쓰게. `exam-figure-queue.md` 같은 전체 요약은 필요할 때만 만드는 별도 명령으로 뺀다(게시할 때마다 전체를 다시 쓰지 않게).
5. **속도:** 1절 2번에서 느린 것으로 나온 원인을 고친다. 방향: 시험지 하나 작업은 그 시험지 파일·JS·그림만 읽는다 / 여러 그림 검사는 한 프로세스에 묶는다 / 바뀐 것만 다시 본다. 고치기 전후 시간을 같은 입력으로 재서 표로.
6. **옛 형식으로 열려 있는 PR을 옮기는 명령:** 한 파일 장부를 고친 브랜치에서, 그 브랜치가 바꾼 시험지만 골라 새 형식 파일로 내보내는 `port-ledger-change --base <main 커밋> --head <브랜치>`. 지금 열린 그림 PR이 10개 넘게 있어서 관제가 이것으로 하나씩 옮긴다.
7. 문서: `docs/agents/visual-svg.md`와 `ops/workers/common-publish.md`·`merge-main.md`·`HANDOFF_SVG_*.md`에서 장부 경로와 "한 번에 하나씩 병합" 안내를 새 방식으로 고친다. 옛 한 파일은 이 PR에서 지운다(두 형식을 함께 두지 않는다).

## 지킬 것
- 장부의 **내용**(상태, 그림 경로, 묶음 이름)은 한 글자도 바꾸지 않는다. 바뀌는 것은 저장 위치와 도구뿐이다.
- 그림 파일, 시험지 JS, 엔진(`archive/tools/geometry-equation`의 렌더 코드)은 고치지 않는다. 그림 검수 기준을 약하게 만들지 않는다.
- 검사를 지우거나 건너뛰게 하지 않는다. 실행하지 않은 검사는 NOT_RUN.
- 위험하거나 지시가 실제 코드와 맞지 않으면 구현하지 말고 조사 결과와 선택지를 보고한다.

## 완료 기준과 보고
새 테스트 통과(쪼개기·합치기 왕복, 문항 단위 병합이 다른 문항을 건드리지 않음, 도구별 기존 동작 유지). 보고서: 장부 사용처 표, 도구별 전후 시간, 시험지 하나 게시에 걸리는 총 도구 시간의 전후, 옮기기 명령을 열린 PR 1개에 시험해 본 결과, 임의로 정한 것, NOT_RUN. 그리고 **도구 말고 남는 병목**(사양 작성, 눈으로 보는 검수, CI 시간 등)을 본 대로 적는다.
