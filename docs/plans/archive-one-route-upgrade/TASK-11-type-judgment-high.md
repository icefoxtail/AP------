# 작업 11 — 고등 유형(PT/TPL) 독립 판정 (PT 담당 인계문)

이 문서는 PT(ChatGPT 안의 작업자)에게 주는 인계문이다. 인수 전에 이 폴더의 `QUEUE.md`와 실제 브랜치 상태를 다시 확인하고, 이미 누가 처리 중이거나 끝낸 범위는 건너뛴다.

## 1. 저장소와 문서

- 저장소 `icefoxtail/AP------`, 계획 브랜치 `plan/archive-one-route-upgrade-20261116`, 폴더 `docs/plans/archive-one-route-upgrade/`.
- 먼저 읽을 것: `PLAN.md`(전체 계획), `QUEUE.md`(공통 규칙·대기열), `FEEDBACK-02.md`와 `TASK-02-REPORT.md`의 "수정 반영" 절(후보 도구 사용법), `TASK-10-type-judgment.md`(같은 일을 중등에서 하는 다른 작업자의 지시. 형식이 같다).
- 2026-11-16 사용자 결정: 유형은 공식 판정기 결과만 쓴다는 잠금을 풀었다. 근거(결정적 풀이 단계)가 있으면 직접 판정한 값도 정식 값이다. 근거 없이 채우지 않는 것, 키가 ACTIVE인지, TPL의 상위 PT가 맞는지는 그대로 지킨다. 원칙은 "항상 넓은 방식, 모든 문항을 활용 가능하게"다(연결 행이 없으면 버리지 말고 꼬리표만).

## 2. 범위와 지금 상태

- **PT의 범위: `archive/exams/original/high/h2` 전체(유형이 비어 있는 약 5,184문항 중 후보가 나오는 약 4,175문항) → 끝나면 `original/high/h3`.** 시험지 파일 단위로 소유한다.
- 다른 작업자의 범위(건드리지 않는다):
  - 중등(`original/middle`) 전체: 작업 10 담당자. 결과 브랜치 `data/type-judgment-c-20261116`.
  - 고1(`original/high/h1`)부터 내려오는 저렴한 모델 두 줄: 관제 PC의 로컬 작업 폴더에서 진행. 결과는 저장소에 없다. 이 두 줄이 고2에 도달하면 PT의 판정과 **서로 독립인 두 번째 판정**이 된다. 겹치는 것이 목적이므로 중복이 아니다.
- 도구: 브랜치 `feat/type-judgment-tools-20261116`(커밋 `1bea581a13`)의 `archive/tools/type-judgment/` (`options.mjs`, `check-ledger.mjs`). 아직 `main`에 없다. 고치지 않는다.
- 후보 범위 근거: `TASK-02-REPORT.md` 수정 반영 절의 표(고2 1학기 중간 1,697 중 1,374, 1학기 기말 1,167 중 561, 2학기 중간 1,476 중 1,396, 2학기 기말 844 중 844).

## 3. 바꿀 수 있는 것

- **쓸 수 있는 곳은 한 곳뿐:** 새 브랜치 `data/type-judgment-d-20261116`(최신 `main`에서 만든다)의 `docs/plans/archive-one-route-upgrade/type-results-d/<학년>-<학기구분>.jsonl` 과, 계획 브랜치의 `TASK-11-REPORT.md`. 이 두 브랜치에 커밋·푸시할 수 있다.
- 하지 않는 것: PR 생성, `main` 병합, 강제 push, 이력 재작성, 다른 브랜치 수정. 정본 메타·레지스트리·크로스워크·시험지 JS·4칸 데이터·등록 요청(inbox) 변경. 공식 등록은 관제가 두 판정을 대조한 뒤에 한다.
- 후보 목록, 검사용 원장 같은 중간 산출물은 커밋하지 않는다.

## 4. 하는 법, 검증, 완료 조건

1. 시험지마다 `options.mjs --exam <경로>`로 문항별 후보를 뽑는다(PT가 25개를 넘으면 `--stage pt` 후 `--stage tpl --pt <키>`).
2. 시험지 JS의 발문·보기·정답·해설을 읽고, 발문이 그림을 가리키면 그림 파일(`archive/assets/images/...`, 인라인 `<svg>`)도 본다.
3. 문항마다 해설의 **결정적 풀이 단계**를 한 문장으로 적고 그에 맞는 PT와 그 아래 TPL을 고른다. 맞는 후보가 없으면 억지로 고르지 않고 `HOLD`(이유) 또는 `NEW_KEY`(이름·정의·구별 단서). PT만 맞으면 PT만 고른다.
4. 결과표 한 줄 형식(문항 하나):
   `{"uid": "...", "exam": "<시험지 경로>", "no": <문항 순번>, "decision": "PICK|HOLD|NEW_KEY", "pt": "<키 또는 null>", "tpl": "<키 또는 null>", "binding": "EXACT|ALIAS|CROSS_CURRICULUM|USED_IN_UNIT|null", "step": "<결정적 풀이 단계 한 문장>", "note": "<HOLD 이유 / 새 키 이름·정의 / 없으면 빈 문자열>", "figure": true|false}`
5. **필수 검증:** 적기 전에 임시 폴더에서 `type-judgment-ledger-v1` 원장으로 만들어 `check-ledger.mjs`를 돌린다. 통과한 문항만 `PICK`으로 적는다. 돌리지 못했으면 보고서에 NOT_RUN으로 적는다.
6. 내부 서브 에이전트로 나눌 때는 시험지 단위로 소유를 나누고, 같은 결과표 파일을 동시에 고치지 않게 PT가 모아서 커밋한다. 독립 검토 에이전트를 쓴다면 표본(시험지 10개 중 1개)만 다시 판정해 일치율을 보고서에 적는다. 검토 결과로 원래 판정을 덮어쓰지 말고 둘 다 남긴다(`note`에).
7. 시험지 30개마다 결과표와 보고서를 커밋한다(끊겨도 남게).
- **완료 조건:** 범위의 모든 시험지에 대해 후보가 있는 문항이 결과표에 한 줄씩 있고, `PICK` 줄은 검사를 통과했으며, 후보 0개로 건너뛴 문항이 보고서 목록에 있다.

## 5. 재사용과 독립성

- **보지 말 것(독립 판정을 깨는 자료):** 정본 메타에 이미 적힌 PT/TPL 값과 유형 관련 상태, 다른 판정 줄의 결과(`type-results-c/`, 관제의 로컬 판정), 예전 분류 산출물(`META_PIPELINE`, 기존 등록 요청·영수증의 유형 값), 같은 시험지의 유사 시험지에 적힌 유형.
- **써도 되는 것:** 후보 도구가 주는 후보 목록과 정의, 시험지 JS의 문항 내용과 그림, 단원·소단원(정본 또는 `--units inline`), 레지스트리의 유형 정의 문서.
- 이미 유형이 승인된 문항은 판정하지 않는다(후보 도구의 대상에서 빠진다). 다시 판정해 값을 바꾸지 않는다.
