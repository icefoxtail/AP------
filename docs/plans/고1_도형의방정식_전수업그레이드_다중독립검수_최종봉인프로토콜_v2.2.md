## 0.1 FALSE PASS 차단 상위 원칙

geometry 검수에서 선언값을 실제 도형의 정답 증거로 취급하지 않는다. 다음 값은 모두
검수 보조 데이터 또는 제작자 주장일 뿐이며, 그 자체로 최종 PASS 근거가 아니다.

```text
data-fact-hash
data-geometry-fact-hash
data-scale-policy
data-axis-scale-mode
data-point-x
data-point-y
data-radius
data-equation
data-slope
data-model-x1
data-model-y1
data-model-x2
data-model-y2
builder Python facts
builder self-check 결과
```

최종 PASS는 반드시 문제에서 독립적으로 다시 계산한 `EXPECTED FACT`와 최종 SVG의 실제
geometry element를 읽고 역산한 `OBSERVED FACT`의 일치로 판정한다.

```text
DECLARED_METADATA_PARITY != OBSERVED_GEOMETRY_PARITY
```

SVG metadata가 자기 내부적으로 일관되고 fact hash가 일치하더라도 실제 원의 pixel 반지름,
직선 endpoint, 점 위치, 객체 identity 또는 관계가 독립 계산값과 다르면 HARD FAIL이다.
이 원칙은 Builder의 Python facts와 SELF_CHECK에도 동일하게 적용한다.

## 0.2 이번 계약의 적용 경계

이번 보강은 기존 전체 inventory/manifest, staging/candidate, PILOT SYSTEM GATE, 5문항
BUILD LOOP, 독립 A/B/C, Mother Pre-Seal, Atomic Production Promotion, Production Parity,

대체하지 않는다.

## 0.3 실제 검수 evidence에서 확인된 false-PASS 유형

기존 평면좌표·직선·원의 방정식·도형의 이동 검수에서 확인된 다음 유형은 단순 metadata
lint만으로 차단되지 않는다. 따라서 아래 계약은 사례를 별도 예외로 처리하는 것이 아니라
모든 해당 문항에 일반 hard gate로 적용한다.

- metadata상 평면좌표였지만 실제 핵심 내용은 직선의 방정식인 문항
- `data-equation`의 직선식은 맞지만 실제 line endpoint의 기울기·절편이 다른 SVG
- `data-radius`, `EQUAL_UNIT`, fact hash는 맞지만 실제 circle pixel radius가 다른 SVG
- 벡터·변위를 점으로 잘못 시각화하거나 문제의 객체 identity와 다른 이름을 붙인 SVG
- 수선의 발·교점·접점·공통현 등 핵심 semantic object가 실제 조건을 만족하지 않는 SVG
- 설명 텍스트는 맞지만 SVG에 핵심 관계가 없거나, 일부 대표 시험지만 렌더하여 전수를 PASS한 보고서
- PASS 보고서 발급 후 SVG가 바뀌었는데 이전 PASS와 seal이 계속 유효하다고 처리한 상태

이 목록은 기존 A/B/C/Mother 구조를 대체하지 않으며, 독립 expected fact·observed SVG
fact·invariant·denominator·reseal 계약이 왜 필요한지를 설명하는 설계 근거다.

# 0. 문서 목적

본 문서는 고1 도형의 방정식 영역에 속하는 기존 JS아카이브 원본 문항 전체를 대상으로 학생용 해설과 해설용 SVG를 체계적으로 업그레이드하고, 제작자 자기검수와 독립 검수자를 명확히 분리한 뒤 동일한 최종 산출물 SHA에 대해 다중 독립 검수를 통과한 경우에만 전체 단원을 최종 봉인하기 위한 프로젝트 전용 실행 프로토콜이다.

본 작업은 시험지 하나씩 최종 완료하고 다음 시험지로 넘어가는 기존 방식과 달리, 먼저 도형의 방정식 전체 범위를 inventory와 manifest로 확정한 뒤 전체 문항을 생산·정리하고, 독립 A·B·C 검수와 수정 루프를 반복한 후 최종 Mother Verifier가 전체 단원 릴리스를 봉인하는 방식으로 수행한다.

핵심 목표는 다음과 같다.

1. 학생이 해설만 보고 풀이를 재현할 수 있도록 논리 점프가 없는 solution을 제공한다.
2. 점·직선·원·접점·교점·평행이동·대칭이동 등 핵심 관계를 검증된 SVG로 시각화한다.
3. 문제·정답·해설·SVG 사이의 수학적 불일치를 제거한다.
4. 제작자 SELF_CHECK와 독립 검수 PASS를 분리한다.
5. 산출물 변경 시 이전 PASS를 자동 무효화한다.
6. 모든 독립 검수자는 동일한 최종 `RELEASE_ARTIFACT_SHA`를 기준으로 최종 PASS 보고서를 발급해야 한다.
7. 대량 생산 전에 H15/H22 × 4개 단원 대표문항으로 `PILOT_SYSTEM_GATE`를 통과하여 반복 오류를 조기에 차단한다.
8. 실제 production engine의 `exam`, `solution`, `answer` 렌더를 시험지별로 전수 확인한다.
9. 검수 보고서와 렌더 증거는 release payload와 분리하여 `REVIEW_EVIDENCE_SHA`로 관리한다.
10. 최종 Mother Verifier는 수정하지 않고 release·evidence·환경 fingerprint를 묶은 `SEAL_BUNDLE_SHA`를 확인한다.
11. production baseline은 전 과정 동안 READ ONLY로 유지하고, 모든 제작·수정·A/B/C 검수는 별도 staging/candidate에서 수행한다.
12. Mother pre-seal 후 staging artifact를 production으로 원자적 승격하고 production parity·실렌더를 다시 통과한 경우에만 최종 `SEALED`를 선언한다.

# 1. 프로젝트 전용 규정 우선순위 및 OVERRIDE

## 1.1 기본 원칙

본 프로젝트는 기존 JS아카이브 공식 규정의 원문 보호, 최소 수정, 독립 검산, Python 기반 SVG 생성, 실제 렌더 게이트, 확인하지 않은 항목 PASS 금지 원칙을 그대로 유지한다.

다만 기존 `도형의방정식_해설_SVG_독립검수_운영규정_v1.1`의 **시험지 단위 최종 폐쇄 루프**는 이번 프로젝트에 한하여 아래 프로젝트 전용 구조로 대체한다.

```text
기존:
시험지 1개 제작
→ 시험지 독립검수
→ 시험지 SHA 봉인
→ 다음 시험지

본 프로젝트:
전체 단원 inventory/manifest 동결
→ PRODUCTION BASELINE READ-ONLY LOCK
→ PROJECT STAGING / CANDIDATE 생성
→ PILOT SYSTEM GATE
→ 5문항 배치 생산
→ 전체 단원 생산 완료
→ 독립 A
→ 수정
→ A 재검
→ 독립 B
→ 수정
→ A+B 재검
→ 독립 C
→ 수정 시 이전 SHA의 PASS 보고서는 무효화
→ hash-preserved evidence carry-forward 가능 여부 판정
→ 최종 RELEASE_ARTIFACT_SHA 기준 A/B/C 보고서 재발급
→ Mother Pre-Seal
→ Atomic Production Promotion
→ Production Parity + exam/solution/answer 재검
→ Mother Final Seal
```

## 1.2 유지되는 상위 규칙

본 프로젝트에서도 다음 원칙은 변경하지 않는다.

- 원본 사실의 최상위 기준은 원본 시험지 소스다.
- 기존 `answer`, 기존 `solution`, 이전 PASS 보고서는 독립 검산의 정답 근거가 아니다.
- 수정은 허용 필드에 한정한다.
- 확인하지 않은 항목은 PASS로 기록하지 않는다.
- production `exam`, `solution`, `answer` 실제 렌더가 최종 봉인의 필수 조건이다.
- 좌표 기반 SVG는 Python 수치 검증 없이 생성하지 않는다.
- 2015 개정과 2022 개정 체계를 임의로 섞거나 자동 변환하지 않는다.
- 마스터 테이블에 없는 세부단원 키를 임의 생성하지 않는다.

## 1.3 프로젝트 전용 봉인 정의

본 프로젝트에서 시험지별 PASS는 중간 상태일 뿐 최종 릴리스 의미를 갖지 않는다.

최종 완료 상태는 오직 다음 하나다.

```text
GEOMETRY_EQUATION_UNIT = SEALED
```

단, 시험지별 렌더 결과·파일 SHA·문항별 검수 결과는 전체 단원 봉인을 위한 증거로 모두 보존한다.

## 1.4 VISUAL 정책 충돌 시 프로젝트 전용 OVERRIDE

기존 `도형의방정식_해설_SVG_독립검수_운영규정_v1.1`의 교육용 시각화 기본 필수 원칙은 유지하되, 이번 전수 프로젝트에서 개별 문항의 시각화 필요 여부는 본 문서 §11의 `VISUAL_REQUIRED / VISUAL_OPTIONAL / VISUAL_EXEMPT` 판정을 최종 실행 기준으로 사용한다.

즉, 기존 규정의 “직선의 방정식은 원칙적으로 시각화”와 본 문서의 “초단순 공식 대입형은 OPTIONAL/EXEMPT 가능”이 충돌할 경우 다음을 따른다.

```text
본 프로젝트 visualRequirement 판정 > 기존 일반 시각화 기본값
```

단, `VISUAL_EXEMPT`는 반드시 사유 코드와 독립 검수 확인을 요구하며, 단순 작업량 절감을 이유로 EXEMPT를 부여할 수 없다.

## 3.3 메타데이터 불일치 처리

역방향 스캔에서 실제 내용은 도형의 방정식인데 표준단원키가 다른 문항을 발견하면 즉시 production metadata를 수정하지 않는다.

상태를 다음 중 하나로 기록한다.

```text
SCOPE_INCLUDED_METADATA_DEFECT
METADATA_REVIEW_REQUIRED
OUT_OF_SCOPE_CONFIRMED
```

실제 수학 내용상 scope가 명확하면 이번 프로젝트 대상에는 포함시키되 메타데이터 수정은 별도 승인 범위로 분리한다.

## 3.4 안정적 questionUid와 중복 제거

같은 문항이 여러 candidate·copy·backup·similar 경로에 존재할 수 있으므로 `questionUid` 기준으로 중복을 제거한다.

`questionUid`는 승인된 source repair나 solution 변경으로 인해 바뀌지 않는 **안정적 identity**여야 한다. 따라서 `contentHash`를 UID 자체의 구성요소로 사용하지 않는다.

권장 stable identity 구성:

```text
sourceJsPath
examId
id
displayNo
```

inventory 시점에 `questionUid`를 한 번 생성한 뒤 manifest 동결 후에는 source repair·solution 수정·asset 수정·경로 정리만으로 UID를 재계산하지 않는다. source 파일 자체가 교체되거나 identity가 재구성되는 경우는 `MANIFEST_REBUILD_REQUIRED`로 처리한다.

원문 상태 검증용 해시는 별도로 둔다.

```text

baselineQuestionHash
ORIGINAL_PROTECTED_HASH
```

`contentHash` 변화는 문항 identity 변경이 아니라 source payload 변경으로 추적한다. 승인된 source repair가 발생해도 동일 `questionUid`를 유지하고 change ledger에서 before/after hash를 기록한다.

최종 inventory는 다음을 만족해야 한다.

```text
duplicate_question_uid = 0
missing_source_path = 0
unresolved_identity = 0
```

## 3.5 COMPOSITE / SHARED MATERIAL dependency closure

공통자료·공통그림·연속 소문항·복합문항 구조에서는 target 문항 하나만 독립적으로 scope에 넣지 않는다.


1. target 문항이 공통자료를 참조하면 해당 shared material anchor를 반드시 식별한다.

- 도형의방정식 해설 SVG 독립검수 운영규정


를 생성한다.

## 4.3 환경 변경 감지

작업 도중 rules/master/engine/runtime이 바뀌면 다음 상태로 전환한다.

```text
ENVIRONMENT_CHANGED
```

변경 영향이 없다고 자동 판단하지 않는다.

변경 후 진행하려면:

1. 변경 파일·runtime fingerprint와 SHA 차이 기록
2. 영향 범위 판정
3. 필요한 검수 단계 무효화
4. 새 fingerprint로 재동결

## 4.4 PROJECT CONFIG FREEZE — scale tolerance 및 전역 상수

작업자가 중간에 허용오차를 임의 변경하지 못하도록 manifest 동결 전에 프로젝트 상수를 고정하고 canonical JSON의 SHA를 `PROJECT_CONFIG_SHA`로 기록한다.

최소 고정값:

```text
EQUAL_SCALE_MODEL_TOLERANCE = 1e-9
EQUAL_SCALE_RENDER_TOLERANCE = 0.005
PILOT_MAX_PER_BUCKET = 2
BUILD_BATCH_SIZE = 5
```

`EQUAL_SCALE_REQUIRED`의 Python 좌표변환 검사는 다음 상대오차를 사용한다.

```text
scale_error = abs(x_px_per_unit - y_px_per_unit) / max(abs(x_px_per_unit), abs(y_px_per_unit))
MODEL_PASS iff scale_error <= EQUAL_SCALE_MODEL_TOLERANCE
```

실제 브라우저 raster/render 측정에서는 소수점 반올림·device pixel ratio 영향을 고려하여:

```text
RENDER_PASS iff rendered_scale_error <= EQUAL_SCALE_RENDER_TOLERANCE
```

를 적용한다. 수학적 transform 자체는 가능한 한 `sx == sy`가 되도록 생성하고, 0.005는 눈대중 SVG 제작을 허용하는 오차가 아니라 **최종 렌더 측정 허용오차**다.

`PROJECT_CONFIG_SHA`가 변경되면 관련 SVG/B/C 증거의 승계 가능성을 다시 판정한다.

## 4.5 PRODUCTION READ-ONLY / PROJECT STAGING LOCK

본 프로젝트는 장기간·다수 문항 작업 중 production archive가 반완성 상태가 되는 것을 금지한다.

```text
PRODUCTION_BASELINE = READ_ONLY

PRODUCTION BASELINE
        ↓ exact copy / referenced dependency snapshot
PROJECT STAGING / CANDIDATE
        ↓
BUILD + PILOT + A/B/C + REPAIR
        ↓
MOTHER_PRESEAL_PASS
        ↓
ATOMIC_PRODUCTION_PROMOTION
        ↓
PRODUCTION_PARITY_GATE
        ↓
SEALED
```

필수 원칙:

1. inventory·baseline lock 이후 production target-bearing JS와 필요한 assets의 기준 SHA를 동결한다.
2. Builder는 production 파일을 직접 수정하지 않는다.
3. solution·solutionImage·승인 source repair를 포함한 모든 변경은 staging/candidate에서만 수행한다.
4. A/B/C는 production baseline이 아니라 **동결된 staging release candidate**를 검수한다.
5. production 승격 전까지 운영 archive에는 부분 수정본을 노출하지 않는다.
6. staging 생성 직후 기준본과의 parity를 기록한다.
7. staging 자체의 baseline digest를 `PROJECT_STAGING_BASELINE_SHA`로 고정한다.
8. production baseline이 외부 작업으로 변경되면 `PRODUCTION_BASELINE_DRIFT`로 전환하고 promotion을 금지한다.

production 승격과 최종 parity 절차는 §24.4~§24.6을 따른다.

## 5.2 INDEPENDENT_GEOMETRY_FACT_LEDGER

각 문항의 geometry fact는 Builder가 SVG 제작에 사용한 Python facts와 분리하여 독립
검수자가 별도로 작성한다. 이 ledger의 원천은 기존 answer, solution, SVG metadata 또는
이전 review가 아니라 문제의 content·choices·직접 주어진 조건이다.

```text
independentGeometryFactStatus
independentGeometryFactHash
independentGeometryFactSource = PROBLEM_REDERIVATION
independentGeometryFactLedger
geometryApplicableInvariantSet
```

`independentGeometryFactSource`에 다음 값을 사용하면 FAIL이다.

```text
BUILDER_FACT_COPY
SVG_METADATA_COPY
SOLUTION_COPY_ONLY
PREVIOUS_REVIEW_COPY
```

ledger에는 해당 문항에서 의미가 있는 fact만 넣는다. 적용 가능한 항목을 계산하지 않은
상태는 PASS가 아니라 `NOT_TESTED`이며, 적용되지 않는 항목은 PASS로 세지 않고
`NOT_APPLICABLE`로 명시한다.

가능한 fact 항목은 다음과 같다.

```text
points, segments, lines, circles, slopes, intercepts, intersections,
perpendicularFeet, distances, midpoints, divisionPoints, circleCenters,
circleRadii, tangentPoints, chords, translationVectors, reflectionAxes,
sourceImagePoints, transformedImagePoints, invariantDistances
```

독립 검수자는 문제에서 출발하여 필요한 좌표·식·관계를 다시 계산한 뒤에만
`independentGeometryFactHash`를 발급한다.

## 5.3 SVG_OBSERVED_FACTS 및 역좌표 검증

최종 SVG는 metadata를 복사하여 검수하지 않는다. 최종 파일의 실제 drawing primitive를
parse하여 다음 값을 관측하고 `svgObservedFacts`로 기록한다.

```text
circle: cx, cy, r
line: x1, y1, x2, y2
polyline/polygon: points
path: d
ellipse: cx, cy, rx, ry
text/label: 실제 위치와 bounding box
SVG root: viewBox, preserveAspectRatio, transform
plot frame / coordinate frame / rendered transform
```

좌표평면 SVG는 생성 시의 `math → pixel` 변환만 확인하지 않는다. 최종 산출물에서
`pixel → math` 역변환을 다시 수행하여 독립 fact와 비교한다.

```text
svgObservedFactStatus
svgObservedFactHash
svgObservedFacts
svgObservedGeometryCount
svgObservedEntityMap
svgObservedFactExtractorVersion
```

`data-*` attribute는 object identity 또는 보조 힌트로 사용할 수 있지만 수치 정답을
대체할 수 없다. 예를 들어 독립 계산상 중심 사이 거리가 4이고 `EQUAL_SCALE_REQUIRED`
이면 실제 pixel 중심거리에서 px/unit을 재계산한 뒤 실제 `circle r`가 `3 × px/unit`인지
검증한다. `data-radius="3"`만으로 PASS하지 않는다.

직선도 `data-equation`만 확인하지 않는다. 실제 endpoint를 역산하여 기울기·절편·점의
incidence·교점·평행·수직 관계를 다시 계산한다.

## 5.4 EXPECTED ↔ OBSERVED GEOMETRY PARITY

독립 geometry 판정은 다음 두 결과의 직접 비교를 중심으로 한다.

```text
PROBLEM
  → INDEPENDENT EXPECTED FACTS

FINAL SVG
  → OBSERVED FACTS

EXPECTED FACTS ↔ OBSERVED FACTS
```

기존 3-way parity와 결합하여 최종 B 수학 parity는 아래를 모두 요구한다.

```text
PROBLEM ↔ INDEPENDENT FACTS
SOLUTION ↔ INDEPENDENT FACTS
SVG OBSERVED FACTS ↔ INDEPENDENT FACTS

PROBLEM ↔ SOLUTION
PROBLEM ↔ SVG OBSERVED
SOLUTION ↔ SVG OBSERVED
```

적용 가능한 항목 중 하나라도 FAIL이면 `B FAIL`이다. metadata와 independent fact hash가
일치하더라도 observed geometry가 다르면 `FAIL_SVG_OBSERVED_GEOMETRY`로 기록한다.

```text
AUXILIARY_OBJECT
```

모든 named object는 가능하면 다음 provenance 중 하나를 가진다.

```text
SOURCE_DEFINED
SOLUTION_DEFINED
INDEPENDENT_AUXILIARY_DEFINED
```

문제의 C를 A로 표시하거나, 벡터·좌표차를 실제 점으로 그리거나, 정의되지 않은 보조
객체를 핵심 객체처럼 표시하거나, 접점이 원과 접선 양쪽에 속하지 않거나, 수선의 발이
실제 수선의 발이 아닌 경우는 `UNDEFINED_SEMANTIC_ENTITY` 또는 해당 parity HARD FAIL이다.

또한 SVG가 존재한다는 이유만으로 시각화 PASS를 선언하지 않는다. 문항 이해에 필요한
핵심 객체·관계가 실제 geometry element로 존재하는지 `svgObservedEntityMap`으로 대조한다.
제목·계산 카드만 있고 원·선·점·수선·접점·교점 등 필요한 실제 객체가 없으면
`SEMANTIC_OBJECT_COVERAGE_FAIL`이다.

# 6. 보호 범위와 수정 허용 범위

## 6.1 기본 보호 필드

다음은 원칙적으로 READ ONLY다.

- `content`
- `choices`
- `answer`
- `image`
- id
- displayNo
- 출처 정보
- 시험지 identity
- 문제용 원본 시각자산
- 기존 배치 정보

## 6.2 기본 수정 허용 필드

이번 프로젝트에서 기본 허용 범위는 다음으로 제한한다.

```text
solution
solutionImage
solutionImage 관련 실제 SVG asset
해설 시각자료 상태를 위한 이미 승인된 필드
```

## 6.3 조건부 수정 필드

아래는 자동 허용하지 않는다.

```text
tags
subUnit*
standardUnit*
questionType
layoutTag
wide
image
```

필요성이 발견되면 `METADATA_DEFECT` 또는 `RENDER_METADATA_DEFECT`로 기록하고 별도 수정 범위를 확정한다.

## 6.4 동일 시험지 비대상 문항 보호 — OUT-OF-SCOPE LOCK

한 시험지의 일부 문항만 target인 경우 나머지 문항을 명시적 보호 대상으로 잠근다.

시험지별로 반드시 다음을 만든다.

```text
TARGET_QUESTION_UIDS
PROTECTED_QUESTION_UIDS
```

`PROTECTED_QUESTION_UIDS`는 해당 시험지의 실제 문항 중 이번 target도 아니고 승인된 dependency 수정 대상도 아닌 모든 문항이다.

비대상 문항의 canonical payload를 정렬하여 시험지별로:

```text
OUT_OF_SCOPE_BASELINE_HASH
OUT_OF_SCOPE_FINAL_HASH
```

를 계산한다.

최종 조건:

```text
OUT_OF_SCOPE_FINAL_HASH == OUT_OF_SCOPE_BASELINE_HASH
OUT_OF_SCOPE_DIFF == 0
```

승인된 범위 확장 없이 하나라도 달라지면:

```text
SCOPE_VIOLATION
HARD_FAIL
```

이다. shared material 또는 비대상 문항 자체를 수정해야 하는 경우 먼저 `SCOPE_EXPANSION_APPROVED`를 기록하고 target/dependency manifest를 갱신한 뒤 새 `MANIFEST_SHA`에서 작업을 재개한다.

## 6.5 원문·정답 오류

문제·보기·정답 오류가 의심되면 다음 상태를 사용한다.

```text
SOURCE_DEFECT
ANSWER_DEFECT
SOURCE_BLOCKED
APPROVED_SOURCE_REPAIR
APPROVED_EXCEPTION
```

승인 없이 `content`, `choices`, `answer`를 수정하지 않는다.

`SOURCE_BLOCKED` 문항이 1개라도 남아 있으면 전체 단원은 `SEALED`가 될 수 없다.

메타데이터 결함은 최종 봉인 전에 반드시 다음 중 하나로 종료 상태를 가져야 한다.

```text
METADATA_CONFIRMED
METADATA_REPAIRED
APPROVED_METADATA_EXCEPTION
```

`METADATA_REVIEW_REQUIRED`가 미해결 상태로 남아 있으면 `SEALED`를 금지한다. 다만 본 프로젝트의 기본 허용 필드가 solution/solutionImage이므로, production metadata 수정을 원하지 않는 경우 사용자의 명시 승인으로 `APPROVED_METADATA_EXCEPTION` 처리할 수 있다.

# 7. 보호 해시 — ORIGINAL / EFFECTIVE 2계층

보호 필드의 역사적 원본과 승인 수리 이후의 유효 기준을 분리한다. `APPROVED_SOURCE_REPAIR`가 정당한데도 baseline hash와 달라졌다는 이유만으로 HARD_FAIL이 발생하는 구조를 금지한다.

권장 protected payload:

```json
{
  "content": "...",
  "choices": [],
  "answer": "...",
  "image": "...",
  "id": 0,
  "displayNo": "...",
  "sourceIdentity": "..."
}
```

## 7.1 ORIGINAL_PROTECTED_HASH

inventory/baseline 시점의 원본 protected payload를 정규화하여 계산한다.

```text
ORIGINAL_PROTECTED_HASH
```

이 값은 historical baseline이며 어떤 승인 수리가 발생해도 덮어쓰거나 재정의하지 않는다.

## 7.2 EFFECTIVE_PROTECTED_HASH

승인 source repair가 없으면:

```text
EFFECTIVE_PROTECTED_HASH = ORIGINAL_PROTECTED_HASH
```

`content`, `choices`, `answer`, 문제용 image 등 protected field의 실제 오류가 확인되고 사용자가 명시적으로 수리를 승인한 경우:

```text
ORIGINAL_PROTECTED_HASH
→ APPROVED_SOURCE_REPAIR ledger
→ repaired protected payload
→ EFFECTIVE_PROTECTED_HASH
```

로 새 유효 기준을 만든다.

승인 수리 ledger에는 최소 다음을 기록한다.

```text
questionUid
field
beforeHash
afterHash
approvalRef
reasonCode
sourceEvidenceRef
approvedBy
approvedAt
```

## 7.3 최종 보호 판정

승인 수리가 없는 문항:

```text
FINAL_PROTECTED_HASH == ORIGINAL_PROTECTED_HASH
```

승인 수리가 있는 문항:

```text
FINAL_PROTECTED_HASH == EFFECTIVE_PROTECTED_HASH
AND APPROVED_SOURCE_REPAIR ledger valid
```

모든 경우:

```text
UNAPPROVED_PROTECTED_DIFF == 0
```

이어야 한다.

`ORIGINAL_PROTECTED_HASH`는 감사용으로 끝까지 보존하며 승인 수리 후에도 원래 값과 최종값의 차이를 숨기지 않는다.

불일치가 승인되지 않았거나 ledger가 불완전하면:

```text
SCOPE_VIOLATION
HARD_FAIL
```

이다.

# 9. PILOT SYSTEM GATE — 대량 생산 전 시스템 검증

전체 manifest 동결 직후, 대량 BUILD를 시작하기 전에 대표 문항으로 제작 체계 자체를 검증한다.

## 9.1 Pilot 표본

기본 표본은 H15/H22 × 4개 표준단원에서 각 2문항씩, **최대 16문항**을 권장한다. 해당 bucket의 실제 target이 2문항보다 적으면 존재하는 문항을 전부 사용하고, target이 0이면 `PILOT_NO_TARGET`으로 기록한다.

```text
PILOT_SAMPLE_COUNT = Σ min(2, bucket_target_count)
```

```text
H15 평면좌표 2
H15 직선의 방정식 2
H15 원의 방정식 2
H15 도형의 이동 2
H22 평면좌표 2
H22 직선의 방정식 2
H22 원의 방정식 2
H22 도형의 이동 2
```

표본은 가능하면 다음을 섞는다.

- 단순 계산형
- 복합 조건형
- 좌표/등축척 민감형
- 접점·교점형
- 이동/대칭형
- 객관식과 서답형

## 9.2 Pilot 실행

Pilot 문항도 실제 production target과 동일한 절차로 처리한다.

본 Pilot 렌더는 기존 운영규정의 “전체 대상 수정 완료 후 전체 렌더”에 대한 **프로젝트 전용 제한적 예외**다. 목적은 학생용 최종 PASS가 아니라 production engine·SVG template·경로·scale의 시스템 오류를 조기 탐지하는 것이다. Pilot 때문에 아직 처리하지 않은 비Pilot 문항이나 보호 필드를 수정할 권한은 생기지 않는다.

```text
독립 풀이
→ solution 작성
→ visualRequirement 판정
→ Python 수치검증
→ SVG 생성
→ BUILDER SELF_CHECK
→ 해당 시험지 solution 실렌더
→ 필요 시 exam/answer 보조 렌더
```

## 9.3 Pilot Independent System Verifier

Pilot의 목적은 잘못된 제작 template·좌표변환·asset path가 수백 문항에 확산되는 것을 막는 것이므로 Builder SELF_CHECK만으로 Pilot을 통과시킬 수 없다.

Builder와 다른 독립 컨텍스트/에이전트가 Pilot 완료본을 검수한다.

독립 Pilot Verifier 최소 검수 범위:

- 독립 수학 fact 확인
- solution 핵심 식과 결론 확인
- Python geometry facts ↔ SVG 좌표 확인
- `scalePolicy`와 등축척/비율 준수 확인
- solution ↔ SVG correspondence
- asset 존재·경로 확인
- 실제 production engine solution render 확인
- 필요 시 exam/answer 보조 render 확인
- 보호 필드 및 out-of-scope diff 확인

필수 상태:

```text
PILOT_BUILDER_PASS
PILOT_INDEPENDENT_SYSTEM_PASS
```

독립 Pilot Verifier는 정식 A/B/C 최종 검수를 대체하지 않는다.

## 9.4 Pilot 판정

다음이 모두 통과해야 대량 BUILD를 개방한다.

```text
PILOT_BUILDER_PASS
PILOT_INDEPENDENT_SYSTEM_PASS
PILOT_SOLUTION_PASS
PILOT_SVG_PASS
PILOT_SCALE_PASS
PILOT_PATH_PASS
PILOT_RENDER_PASS
PILOT_PROTECTION_PASS
```

반복 구조·SVG template·경로·렌더 방식에 시스템 오류가 있으면:

```text
PILOT_SYSTEM_FAIL
```

로 두고 원인을 수정한 뒤 Pilot부터 다시 수행한다.

Pilot PASS는 독립 A/B/C 최종 검수를 대체하지 않는다. Pilot 문항은 최종 manifest의 실제 target 문항이며 이후 전체 검수에 다시 포함된다.

# 10. 제작 운영 — 5문항 배치 루프

전체 단원을 한 번에 한 컨텍스트로 처리하지 않는다.

문항을 `questionUid` 또는 안정적으로 정렬된 `sourceJsPath × id` 순서로 5문항씩 처리한다.

각 배치마다 다음 LOOP를 반드시 완료한다.

## 10.0 SOURCE VALIDITY GATE

문항별 처리 순서는 다음과 같이 고정한다.

```text
PROBLEM READ
→ INDEPENDENT SOLVE
→ SOURCE VALIDITY
→ ANSWER VALIDITY
→ SOLUTION REVIEW
→ VISUAL REQUIREMENT
→ SVG
```

다음 상태 중 하나라도 해당하면 SVG 제작을 그대로 진행하지 않는다.

```text
PROBLEM_NOT_WELL_DEFINED
ANSWER_INCONSISTENT
MULTIPLE_ANSWERS_UNDECLARED
NO_VALID_ANSWER
CONDITION_CONTRADICTION
SOURCE_DEFECT_REVIEW_REQUIRED
```

source defect가 발견되면 기존 source repair 승인·ledger 정책으로 이동한다. 잘못된
answer를 기준으로 SVG를 정교하게 만들거나, solution·SVG가 서로 맞는다는 이유로 문제의
성립성과 answer validity 검수를 생략하지 않는다.

## LOOP 1. 입력 검증

- 현재 5문항의 JS 원문 읽기
- 문제용 이미지 존재 시 실제 확인
- content
- choices
- answer
- 기존 solution
- 기존 solutionImage
- 단원/세부단원
- 원본 시험지 source

## LOOP 2. 독립 수학 풀이

기존 answer와 solution을 정답 근거로 사용하지 않는다.

각 문항을 독립 풀이하여 다음을 확정한다.

- 실제 정답
- 핵심 풀이식
- 조건 적용 순서
- 경우 나누기
- 좌표
- 교점
- 중심·반지름
- 기울기
- 거리
- 이동 관계
- 고1 교육과정 내 풀이법

객관식은 모든 선지를 판정한다.

## LOOP 3. 학생용 solution 작성

해설은 학생이 풀이를 재현할 수 있어야 한다.

필수 원칙:

- 새 기호·점·직선은 먼저 정의한다.
- “정리하면”, “계산하면”, “대입하면”으로 핵심 단계를 생략하지 않는다.
- 왜 해당 식을 세우는지 적는다.
- 계산값과 도형적 의미를 연결한다.
- 경우 나누기 조건을 생략하지 않는다.
- 고1 범위 밖 벡터·미적분·과도한 공식 사용을 피한다.
- 마지막 결론은 answer와 일치한다.
- 내부 운영 메모를 solution에 넣지 않는다.

## LOOP 4. Visual Requirement 판정

문항별로 반드시 다음 셋 중 하나를 기록한다.

```text
VISUAL_REQUIRED
VISUAL_OPTIONAL
VISUAL_EXEMPT
```

`VISUAL_EXEMPT`는 사유 코드가 반드시 있어야 한다.

또한 시각자료가 있는 문항은 다음 중 하나의 `scalePolicy`를 미리 고정한다.

```text
EQUAL_SCALE_REQUIRED
PROPORTIONAL_REQUIRED
SCHEMATIC_ALLOWED
```

- 원·거리·각도·대칭 등 좌표의 metric 의미가 직접 사용되면 `EQUAL_SCALE_REQUIRED`.
- 상대적 길이·위치 비율이 의미 있지만 x/y 단위 등축 자체가 핵심이 아니면 `PROPORTIONAL_REQUIRED`.
- 위치관계만 설명하는 개념도이며 실제 길이/각을 읽으면 안 되는 경우만 `SCHEMATIC_ALLOWED`.

## LOOP 5. Python 수치검증

좌표·도형·그래프 기반 SVG는 Python 수치검증을 선행한다.

검증 대상:

- 핵심 점 좌표
- 교점
- 중심
- 반지름
- 직선 식
- 기울기
- 접점
- 대칭점
- 이동 후 좌표
- 실제 좌표 → SVG 좌표 변환
- x/y scale

SVG 좌표를 눈대중으로 배치하지 않는다.

## LOOP 6. SVG 생성

Python에서 확정한 수학 사실과 좌표를 기준으로 생성한다.

SVG 내부 금지:

- `<br>`
- `$...$`
- `\frac`
- `\sqrt`
- MathJax
- 외부 리소스 의존
- 설명용 운영 메모

## LOOP 7. BUILDER SELF_CHECK

다음을 5문항마다 확인한다.

- answer와 독립 풀이 일치
- solution 마지막 결론 일치
- 논리 점프 없음
- 교육과정 적합
- SVG 좌표가 Python 결과와 일치
- 문제↔solution↔SVG 라벨 일치
- SVG 잘림·빈 패널 없음
- 허용 필드 밖 수정 없음
- 보호 hash 변경 없음

SELF_CHECK FAIL이면 다음 배치로 넘어가지 않는다.

# 11. VISUAL_REQUIRED / OPTIONAL / EXEMPT 기준

## 11.1 평면좌표

### REQUIRED

- 좌표 배치 자체가 풀이 이해에 핵심
- 중점·내분점·외분점의 상대 위치 이해가 필요
- 좌표를 이용한 도형 관계
- 점들의 위치를 통해 넓이·거리·대칭 관계를 해석

### OPTIONAL

- 단순 두 점 거리 공식 대입
- 단순 중점 좌표 계산

### EXEMPT

식만으로 충분하며 그림이 오히려 정보량만 늘리는 단순 계산형

## 11.2 직선의 방정식

원칙적으로 시각화 우선.

### REQUIRED

- 두 직선의 위치관계
- 교점
- 평행·수직
- 절편
- 점과 직선의 거리의 기하적 의미
- 삼각형/사각형과 직선의 결합
- 좌표평면에서 여러 직선 비교

### OPTIONAL/EXEMPT

직선 식 한 개를 단순히 공식에 대입해 구하는 초단순 문항은 예외 가능.

## 11.3 원의 방정식

실수 범위의 실제 원이면 원칙적으로 `VISUAL_REQUIRED`.

- 중심
- 반지름
- 원과 직선의 위치관계
- 원과 원의 위치관계
- 접선
- 접점
- 교점

예외:

```text
r^2 = 0 → 퇴화점
r^2 < 0 → 실수 좌표평면에서 실제 원 없음
```

필요하면 최소 시각자료를 제공하고 예외 사유를 기록한다.

## 11.4 도형의 이동

### REQUIRED

- 이동 전후 위치관계를 비교해야 함
- 평행이동 전후 도형
- 대칭축 기준 관계
- 원·직선·점의 대응
- 두 단계 이상 이동

### OPTIONAL

좌표값만 단순 계산하는 매우 직접적인 문항.

### 11.5 SCHEMATIC_ALLOWED HARD RESTRICTION

기존 `SCHEMATIC_ALLOWED` 정의는 유지하되, 실제 metric 또는 topology를 읽어야 하는
문항에 이를 사용하여 수치 검수를 우회할 수 없다. 다음 중 하나라도 해당하면 원칙적으로
`SCHEMATIC_ALLOWED`를 사용할 수 없다.

```text
좌표축이 존재
수치 좌표가 표시
기울기를 읽어야 함
거리 비교가 풀이 핵심
각 또는 수직 관계가 풀이 핵심
원 반지름이 의미 있음
절편이 의미 있음
교점 위치가 의미 있음
대칭 위치가 의미 있음
이동 전후 좌표가 의미 있음
길이 또는 넓이를 실제 geometry에서 해석
```

이 경우 적절한 `EQUAL_SCALE_REQUIRED` 또는 `PROPORTIONAL_REQUIRED`를 사용하고, 실제
geometry를 독립 계산값으로 검증한다.

```text
SCHEMATIC_ALLOWED != WRONG_GEOMETRY_ALLOWED
```

도식화가 허용되는 경우에도 object identity, incidence, ordering, parallel,
perpendicular, inside/outside, intersection/non-intersection, tangent/non-tangent 등
topology·semantic 관계는 정확해야 한다. 이를 실제 element에서 검사하지 않은
`SCHEMATIC_ALLOWED` 문항은 PASS가 아니라 `NOT_TESTED`다.

# 12. SVG 정적·수치 검수 게이트

SVG마다 최소 다음을 검사한다.

```text
XML parse
viewBox
width/height
forbidden token
external resource
empty panel
clip/overflow
label bounds
coordinate scale
scalePolicy compliance
metric equality
asset existence
asset path
```

좌표평면에서는 가능하면 다음을 기록한다.

```text
x_px_per_unit
y_px_per_unit
scale_ratio = x_px_per_unit / y_px_per_unit
```

원의 방정식·거리·각도 관계처럼 등축척이 수학적 의미에 영향을 주는 그림은 의도하지 않은 비등축을 허용하지 않는다.

`scalePolicy == EQUAL_SCALE_REQUIRED`이면 §4.4에서 동결한 허용오차를 사용하여 `x_px_per_unit`과 `y_px_per_unit`의 차이를 자동 검사한다.

```text
model_scale_error <= 1e-9
rendered_scale_error <= 0.005
```

Python transform 단계에서는 가능한 한 x/y 단위 스케일을 동일하게 생성하고, 실제 브라우저에서의 0.005 허용치는 rasterization·DPR 측정 오차에만 적용한다. 작업자가 문항별로 tolerance를 임의 완화할 수 없다.

`SCHEMATIC_ALLOWED`인 경우에는 학생이 실제 길이·각도·거리로 오독하지 않도록 해설 문맥과 시각 표현을 함께 검수한다.

## 12.1 OBSERVED GEOMETRY HARD GATE

위 정적 검사는 선언 metadata의 존재를 확인하는 단계일 뿐 최종 geometry correctness를
증명하지 않는다. B 검수자는 최종 SVG의 실제 `circle`, `line`, `polyline`, `polygon`,
`path`, `ellipse`, `text` element를 읽어 `SVG_OBSERVED_FACTS`를 작성한다.

좌표평면 SVG는 실제 pixel 값을 수학 좌표로 역변환한다. 원은 실제 `cx`, `cy`, `r`로부터
중심·반지름·중심거리·점의 원주 위 여부를 재계산하고, 직선은 실제 endpoint로부터
기울기·절편·점의 incidence·교점·평행·수직을 재계산한다. `data-equation`,
`data-radius`, `data-point-x`, `data-point-y`, `data-fact-hash`가 맞다는 이유만으로
이 단계를 생략할 수 없다.

`EQUAL_SCALE_REQUIRED`이면 다음을 모두 비교한다.

```text
axis unit scale
center-to-center pixel scale
radius pixel scale
rendered transform scale
```

적용 가능한 geometry invariant, semantic object coverage, expected↔observed parity 중
하나라도 계산되지 않으면 `NOT_TESTED`이고 최종 PASS를 금지한다. observed 결과는 다음
필드를 포함하여 review evidence에 연결한다.

```text
svgObservedFactStatus
svgObservedFactHash
svgObservedFacts
svgObservedGeometryCount
svgObservedEntityMap
svgObservedFactExtractorVersion
```

# 13. Sentinel Audit — 대량 반복 오류 조기 탐지

정식 독립 검수는 전체 BUILD 완료 후 시작한다. 여기서 “전체 BUILD 완료 후”는 독립
검수의 시작 시점을 뜻하며, 독립 검수 실행 단위는 §34의 5문항 review batch들의
연속이다. 모든 문항을 하나의 context에서 한 번에 훑는 방식은 최종 독립 검수로
인정하지 않는다.

다만 수백 문항 규모의 대량 작업에서 동일한 제작 오류가 반복되는 것을 막기 위해 `SENTINEL_AUDIT`를 둔다.

권장 주기:

```text
50문항 누적 또는 source JS 10개 완료 시
```

Sentinel Audit은 다음만 본다.

- solution 구조가 동일하게 잘못 생성되고 있는지
- Python 검증 없이 SVG가 만들어지고 있는지
- scale 왜곡이 반복되는지
- 허용 필드 밖 수정이 반복되는지
- 파일 경로 패턴이 잘못 적용되는지
- 교육과정 밖 풀이가 반복되는지

Sentinel Audit은 최종 PASS 권한이 없다.

결과는:

```text
NO_SYSTEMIC_DEFECT
SYSTEMIC_DEFECT_FOUND
```

만 기록한다.

# 15. 독립 에이전트 A — 수학·해설·교육성

## 15.1 역할

A는 제작자가 아닌 독립 검수자다.

A는 수정하지 않는다.

A는 SVG geometry metadata, fact hash, Builder Python facts를 독립 정답의 근거로 사용하지
않는다. A가 확정하는 것은 문제의 성립성, 독립 정답, solution correctness,
solution completeness, curriculum validity, 조건·경우 나누기와 source defect이며,
geometry fact는 해설 검증에 필요한 경우에만 별도 참고값으로 남긴다.

## 15.2 독립성 조건

첫 판정 전에 A에게 제공하는 것은 원칙적으로 다음뿐이다.

- frozen artifact
- frozen manifest
- frozen ruleset
- 원본 시험지 source
- 필요 시 master

```text
A_START_RELEASE_SHA
A_END_RELEASE_SHA
```

두 값이 다르면 A 검수 과정에서 artifact가 변경된 것이므로 해당 검수 결과는 자동 무효다.

- 문항 성립성

# 16. 수정 프로토콜 A

A에서 FAIL이 있으면 Builder가 허용 범위 안에서 수정한다.

수정 후:

1. 변경 문항 diff 기록
2. 관련 solutionImage 재검증
3. 보호 hash 확인
4. 전체 JS syntax 확인
5. dependency 영향 범위 계산
6. 새 `RELEASE_ARTIFACT_SHA` 생성

```text
S0 → S1
```

**S0에 대해 발급된 A PASS 보고서는 무효다.**

다만 §22의 `HASH-PRESERVED EVIDENCE CARRY-FORWARD` 조건을 만족하면, S0에서 이미 독립 검수한 문항 중 **A에 해당하는 `A_REVIEW_INPUT_HASH`**가 unchanged이고 전역 영향이 없는 문항의 A 검수 증거는 승계할 수 있다.

A는 S1에서 최소한 다음을 수행한다.

- 변경 문항 재검
- dependency 영향 문항 재검
- carry-forward 대상 hash 재확인
- S1 전체 manifest coverage 확인
- `A_FINAL_RELEASE_SHA = S1`로 새 최종 보고서 발급

A의 S1 보고서가 전체 target coverage를 증명해야 B로 넘어갈 수 있다.

수정하지 않는다.

## 17.4 B INDEPENDENT GEOMETRY FACT / OBSERVED SVG CONTRACT

B는 Builder의 Python facts, `data-*` metadata, fact hash 또는 SELF_CHECK 결과를 독립
geometry 정답의 근거로 사용하지 않는다. B의 판정 순서는 다음과 같다.

```text
1. 문제 content·choices·직접 주어진 조건에서 EXPECTED FACTS 재도출
2. 최종 SVG 실제 element parse
3. pixel → math 역변환으로 OBSERVED FACTS 생성
4. EXPECTED ↔ OBSERVED invariant 비교
5. semantic object coverage 확인
6. 문제·해설·SVG parity 확인
```

B는 문항별로 `independentGeometryFactLedger`와 `svgObservedEntityMap`을 연결하고,
`geometryApplicableInvariantSet`의 모든 적용 항목이 `TESTED`인지 확인한다. 적용되지 않는
항목은 `NOT_APPLICABLE`, 계산하지 않은 적용 항목은 `NOT_TESTED`로 기록하며 후자는 PASS로
승격하지 않는다.

다음은 기존 삼각 대응과 함께 B의 필수 parity다.

```text
PROBLEM ↔ INDEPENDENT FACTS
SOLUTION ↔ INDEPENDENT FACTS
SVG OBSERVED FACTS ↔ INDEPENDENT FACTS
PROBLEM ↔ SOLUTION
PROBLEM ↔ SVG OBSERVED
SOLUTION ↔ SVG OBSERVED
```

metadata가 내부적으로 일관되더라도 실제 geometry가 독립 fact와 다르면
`FAIL_SVG_OBSERVED_GEOMETRY`로 판정한다. 필요한 실제 객체가 빠졌거나 정의되지 않은
객체가 추가되면 `SEMANTIC_OBJECT_COVERAGE_FAIL` 또는 `UNDEFINED_SEMANTIC_ENTITY`로
판정한다.

# 20. Render Matrix

전체 단원의 렌더 완료 여부를 시험지별 matrix로 관리한다.

예:

| examId | exam | solution | answer | console | overflow | final |
|---|---|---|---|---|---|---|
| EXAM_A | PASS | PASS | PASS | PASS | PASS | PASS |
| EXAM_B | PASS | PASS | PASS | PASS | PASS | PASS |

완료 조건:

```text
rendered_exam_count == TARGET_RENDER_EXAM_COUNT
exam_mode_pass == TARGET_RENDER_EXAM_COUNT
solution_mode_pass == TARGET_RENDER_EXAM_COUNT
answer_mode_pass == TARGET_RENDER_EXAM_COUNT
NOT_TESTED == 0
```

## 20.1 DENOMINATOR CLOSURE 및 FINAL RENDER DENOMINATOR

최종 보고서의 “전수” 표현은 다음 분모를 실제 count로 채운 경우에만 사용할 수 있다.

```text
TARGET_QUESTION_COUNT
MATH_REVIEW_COUNT
SOLUTION_REVIEW_COUNT
SVG_REQUIRED_COUNT
SVG_REVIEW_COUNT
GEOMETRY_FACT_EXPECTED_COUNT
GEOMETRY_FACT_OBSERVED_COUNT
METADATA_REVIEW_COUNT
TAG_REVIEW_COUNT
JS_REVIEW_COUNT
TARGET_EXAM_COUNT
EXAM_RENDER_COUNT
SOLUTION_RENDER_COUNT
ANSWER_RENDER_COUNT
```

최종 PASS에는 최소한 다음 equality를 결박한다.

```text
MATH_REVIEW_COUNT == TARGET_QUESTION_COUNT
SOLUTION_REVIEW_COUNT == TARGET_QUESTION_COUNT
METADATA_REVIEW_COUNT == TARGET_QUESTION_COUNT
TAG_REVIEW_COUNT == TARGET_QUESTION_COUNT
JS_REVIEW_COUNT == TARGET_QUESTION_COUNT
SVG_REVIEW_COUNT == SVG_REQUIRED_COUNT
GEOMETRY_FACT_EXPECTED_COUNT == GEOMETRY_FACT_OBSERVED_COUNT
EXAM_RENDER_COUNT == TARGET_EXAM_COUNT
SOLUTION_RENDER_COUNT == TARGET_EXAM_COUNT
ANSWER_RENDER_COUNT == TARGET_EXAM_COUNT
```

각 geometry 적용 대상은 `EXPECTED == OBSERVED == TESTED`여야 한다. 적용 가능한 invariant,
semantic object coverage, expected↔observed parity를 세지 않았으면 `NOT_TESTED > 0`으로
기록하고 최종 PASS를 금지한다.

`PILOT` 또는 sentinel의 대표 렌더는 시스템 오류 조기 탐지용으로만 허용한다. FINAL C,
Mother Pre-Seal 및 Mother Final Seal에서 대표 렌더로 전수 PASS를 대체할 수 없다.

```text
FINAL_RENDER_DENOMINATOR = TARGET_RENDER_EXAM_COUNT × 3
```

`TARGET_RENDER_EXAMS`의 모든 시험지에 대해 production engine의 `exam`, `solution`,
`answer`를 실제 렌더해야 한다. 하나라도 누락되면 `NOT_TESTED`이며, 예를 들어
`79/81` 또는 `80/81`은 PASS가 아니다.

# 21. C FAIL 후 재검 규칙

C에서 수정이 필요한 오류가 발견되어 release payload를 수정하면:

```text
S2 → S3
```

S2에 대해 발급된 A/B/C 최종 보고서는 모두 무효다.

단, 모든 문항을 무조건 처음부터 다시 풀도록 강제하지 않고 §22의 영향 범위·hash-preserved evidence 규칙을 적용한다.

최종적으로는 반드시 S3에 대해:

```text
A_FINAL_REPORT(S3) = PASS
B_FINAL_REPORT(S3) = PASS
C_FINAL_REPORT(S3) = PASS
```

를 새로 발급해야 한다.

본 프로젝트에서 **A·B·C가 서로 다른 RELEASE_ARTIFACT_SHA에 대해 발급한 보고서를 조합하는 것은 최종 PASS가 아니다.**

# 22. HASH-PRESERVED EVIDENCE CARRY-FORWARD + SAME-SHA LOCK

## 22.1 기본 원칙

release payload가 변경되면 이전 SHA에 대해 발급된 verifier의 최종 PASS 보고서는 무효다.

그러나 변경되지 않은 검수 입력까지 동일한 독립 검사를 매번 반복하여 재검 비용이 폭발하는 것을 막기 위해, **verifier별 입력 hash에 기반한 검수 증거 단위의 조건부 승계**를 허용한다.

generic `reviewedQuestionHash` 하나로 A/B/C 승계를 공통 판정하는 것을 금지한다.

## 22.2 Verifier별 canonical input hash

### A_REVIEW_INPUT_HASH

A가 수학·해설·교육성을 검수하는 데 필요한 canonical payload의 SHA다.

최소 포함:

```text
questionUid
content
choices
answer
solution
curriculumVersion
standardCourse
standardUnitKey
standardUnit
subUnitKey/subUnit (A의 교육과정 판정에 실제 사용되는 경우)
relevant source dependency hash
```

SVG만 변경되어 위 A 입력이 unchanged라면 A evidence 승계 가능성을 검토할 수 있다.

### B_REVIEW_INPUT_HASH

B가 문제·해설·SVG 대응성을 검수하는 데 필요한 canonical payload의 SHA다.

최소 포함:

```text
questionUid
content
solution
solutionImageRef
solutionImageAssetHash
pythonGeometryFactsHash
independentGeometryFactHash
svgObservedFactExtractorVersion
geometryInvariantMatrixVersion
semanticObjectRequirementHash
scalePolicy
visualRequirement
relevant dependency hash
```

SVG·좌표·Python facts·independent geometry facts·observed extractor·invariant matrix·semantic
object requirement·scalePolicy 중 하나라도 바뀌면 B hash는 변경되어야 한다. 단,
`svgObservedFactHash`는 검수 산출물이므로 review input과 순환참조하지 않고 별도 evidence에
둔다.

### C_RENDER_INPUT_HASH

C의 실제 렌더는 시험지 전체 payload·engine·asset·runtime의 영향을 받으므로 원칙적으로 **exam 단위 hash**로 계산한다.

최소 포함:

```text
examId
full exam JS hash
referenced asset set hash
renderSequence/dependency hash
ENGINE_SHA
DB_SHA / QUESTION_INDEX_SHA 중 실제 렌더에 영향 주는 값
RENDER_RUNTIME_FINGERPRINT_SHA
PROJECT_CONFIG_SHA
```

question manifest row에 `C_RENDER_INPUT_HASH`를 기록할 경우 같은 exam의 문항에는 동일 exam-level 값을 참조시켜도 된다. 정규 원본은 exam/render manifest의 exam-level hash다.

## 22.3 Carry-forward evidence 레코드

승계 대상은 PASS 문자열이 아니라 다음과 같은 검수 증거다.

```text
questionUid or examId
verifierType
reviewInputHash
reviewResult
sourceDependencyHash
rulesetSha
masterSha
projectConfigSha
reviewedAtReleaseSha
```

## 22.4 Carry-forward 허용 조건

A evidence:

```text
A_REVIEW_INPUT_HASH unchanged
relevant rules unchanged
relevant master mapping unchanged
no shared-material impact
no global transform impact
```

B evidence:

```text
B_REVIEW_INPUT_HASH unchanged
relevant rules unchanged
relevant dependency hash unchanged
no shared-material impact
no geometry/template transform impact
```

C evidence:

```text
C_RENDER_INPUT_HASH unchanged
AND render runtime unchanged
AND engine/runtime-affecting dependency unchanged
```

C의 경우 시험지 안의 solution/SVG 한 항목만 바뀌어도 보통 full exam JS 또는 referenced asset set hash가 달라지므로 **해당 시험지 실제 렌더는 재실행**한다.

모든 verifier에서 하나라도 확인하지 못하면 해당 scope는 새로 검수한다.

## 22.5 전수 재검 강제 트리거

다음 변경은 원칙적으로 selective carry-forward를 금지하고 영향받는 verifier의 전체 scope를 재검한다.

- RULESET의 해당 검수 기준 변경
- master 구조/라벨/parent 변경이 대상 범위에 영향
- 대량 생성 template 또는 transform 로직 변경
- shared material 구조 변경으로 영향 범위를 확정할 수 없음
- identity/manifest 재구성
- 보호 필드 대량 변경
- source baseline 교체
- `PROJECT_CONFIG_SHA` 변경이 광범위 영향
- 영향 범위를 신뢰성 있게 계산할 수 없는 변경

## 22.6 Verifier 영향 매트릭스

| 변경 | A | B | C |
|---|---|---|---|
| `solution` | `A_REVIEW_INPUT_HASH` 변경 문항 재검 | `B_REVIEW_INPUT_HASH` 변경 문항 재검 | 해당 시험지 `C_RENDER_INPUT_HASH` 변경 → 재렌더 |
| `solutionImage`/SVG | A hash unchanged면 승계 가능 | B hash 변경 → 재검 | 해당 시험지 재렌더 |
| Python geometry facts / scalePolicy | 필요 시 A 교육성 영향 판정 | B hash 변경 → 재검 | 해당 시험지 재렌더 |
| approved protected source repair | A hash 변경 → 독립 재풀이 | B hash 변경 → 대응성 재검 | exam/solution/answer 재렌더 |
| shared material | dependency closure 전부 | dependency closure 전부 | 관련 `TARGET_RENDER_EXAMS` 전부 |
| engine/runtime only | A hash 조건 아래 승계 가능 | B hash 조건 아래 승계 가능 | C hash 변경 → 영향 시험지 렌더 재검 |
| rules/master 영향 | 영향 판정 후 전수 가능 | 영향 판정 후 전수 가능 | 영향 판정 후 전수 가능 |

## 22.7 SAME-SHA 최종 보고서 잠금

최종 핵심 규칙:

```text
FINAL_PASS =
A_FINAL_REPORT(S_final) == PASS
AND
B_FINAL_REPORT(S_final) == PASS
AND
C_FINAL_REPORT(S_final) == PASS
```

각 최종 보고서는 직접 재검한 scope와 hash-preserved carry-forward scope를 합쳐 **전체 manifest coverage**를 증명해야 한다.

다음은 금지한다.

```text
A_REPORT(S1) PASS
B_REPORT(S2) PASS
C_REPORT(S3) PASS
→ SEALED
```

위 상태는 FAIL이다.

모든 verifier의 최종 보고서는 반드시 같은 `FINAL_RELEASE_ARTIFACT_SHA`를 가리켜야 한다.

## 22.8 FINAL RESEAL 및 OBSERVED-FACT INVALIDATION

최종 보고서 작성 후 release payload가 바뀌면 이전 PASS는 현재 release의 PASS가 아니다.
특히 SVG 하나만 변경되어도 최소 B, C, Mother Seal의 관련 evidence를 새 artifact SHA에서
재판정한다. solution까지 변경되면 A도 영향 범위를 재검하고, source/content/answer가
변경되면 A/B/C 모두 영향 범위를 다시 판정한다.

```text
CURRENT_RELEASE_ARTIFACT_SHA != VERIFIED_RELEASE_ARTIFACT_SHA
→ REVIEW_STATUS = STALE
→ FINAL_SEAL = INVALID
```

모든 최종 보고서와 carry-forward 레코드는 현재 `FINAL_RELEASE_ARTIFACT_SHA`를 직접
가리켜야 한다. Mother는 과거 PASS 보고서 파일의 존재만 확인하지 않고 각 보고서의 대상
release SHA, input hash, rules/master/runtime fingerprint를 다시 대조한다.

```text
SVG change
→ B recheck
→ C target-exam re-render
→ Mother reseal
```

검수 중 또는 봉인 후 observed fact extractor가 실제 SVG와 다른 결과를 내거나 artifact
SHA가 바뀌면 `EVIDENCE_STALE` 또는 `SEAL_BROKEN`으로 전환하고, 새
`REVIEW_EVIDENCE_SHA`·`PRESEAL_BUNDLE_SHA`·필요한 promotion/seal evidence를 생성하기
전에는 PASS/SEALED를 유지하지 않는다.

# 24. Mother Verifier — 최종 단원 봉인

## 24.1 역할

Mother Verifier는 제작자가 아니다.

수정하지 않는다.

다수결을 하지 않는다.

FAIL을 override하지 않는다.

## 24.2 입력

- 최종 artifact
- final manifest
- staging release candidate
- production baseline snapshot
- A final report
- B final report
- C final report
- render matrix
- change ledger
- exception ledger
- SHA ledger
- carry-forward evidence map
- render runtime fingerprint
- seal bundle
- ruleset/master/engine/runtime fingerprint

## 24.3 최종 확인

Mother는 다음을 확인한다.

```text
A final SHA == FINAL_RELEASE_ARTIFACT_SHA
B final SHA == FINAL_RELEASE_ARTIFACT_SHA
C final SHA == FINAL_RELEASE_ARTIFACT_SHA
A coverage count == target_count
B coverage count == target_count
C release/render coverage == required_scope
DENOMINATOR_CLOSURE_PASS
GEOMETRY_FACT_EXPECTED == GEOMETRY_FACT_OBSERVED == GEOMETRY_FACT_TESTED
SVG_OBSERVED_GEOMETRY_PASS
SEMANTIC_OBJECT_COVERAGE_PASS
carry-forward evidence hash valid
A/B/C review input hash map valid
OUT_OF_SCOPE_DIFF == 0
UNAPPROVED_PROTECTED_DIFF == 0

MANIFEST_SHA unchanged
RULESET_SHA valid
MASTER_MD_SHA valid
MASTER_JSON_SHA valid
ENGINE_SHA valid
RENDER_RUNTIME_FINGERPRINT_SHA valid
REVIEW_EVIDENCE_SHA valid
PRESEAL_BUNDLE_SHA valid

SOURCE_BLOCKED == 0
METADATA_REVIEW_REQUIRED == 0
NOT_TESTED == 0
FINAL_RENDER_DENOMINATOR complete
SCOPE_VIOLATION == 0
UNRESOLVED_FAIL == 0
VISUAL_REQUIRED_MISSING == 0
PRODUCTION_BASELINE_DRIFT == 0
```

하나라도 실패하면:

```text
REPAIR_REQUIRED
```

이며 production promotion으로 넘어가지 않는다.

Mother의 이 단계 통과 상태는 최종 SEALED가 아니라:

```text
MOTHER_PRESEAL_PASS
```

다.

## 24.4 ATOMIC PRODUCTION PROMOTION

`MOTHER_PRESEAL_PASS` 이후에만 staging release candidate를 production으로 승격한다.

여러 파일을 한 번에 바꾸는 작업은 파일시스템 차원에서 진정한 단일 atomic write가 어려울 수 있으므로 본 문서의 `ATOMIC_PRODUCTION_PROMOTION`은 다음 **transactional all-or-rollback 계약**을 뜻한다.

필수 절차:

1. promotion 직전 production baseline SHA를 다시 계산한다.
2. baseline drift가 있으면 즉시 `PRODUCTION_BASELINE_DRIFT`로 중단한다.
3. promotion 대상 파일 목록과 before/after SHA를 `promotion_manifest.json`에 고정한다.
4. 모든 replacement 파일을 임시 promotion area에 준비한다.
5. syntax/load/asset existence를 사전 검사한다.
6. promotion transaction을 실행한다.
7. 하나라도 실패하면 baseline snapshot으로 전 파일을 rollback한다.
8. partial promotion 상태를 최종 운영본으로 남기지 않는다.

필수 기록:

```text
PROMOTION_TRANSACTION_ID
PROMOTION_BASELINE_SHA
PROMOTION_EXPECTED_RELEASE_SHA
PROMOTION_STATUS
ROLLBACK_STATUS
```

## 24.5 PRODUCTION PARITY GATE

승격 직후 production에서 다시 확인한다.

```text
PRODUCTION_RELEASE_ARTIFACT_SHA == FINAL_RELEASE_ARTIFACT_SHA
OUT_OF_SCOPE_FINAL_HASH == OUT_OF_SCOPE_BASELINE_HASH
UNAPPROVED_PROTECTED_DIFF == 0
node/load == PASS
asset/path == PASS
```

그리고 `TARGET_RENDER_EXAMS` 전체에 대해 production engine의:

```text
exam
solution
answer
```

를 다시 실제 렌더한다.

이 promotion 후 렌더는 C의 staging 렌더를 대체하는 것이 아니라 **승격 과정에서 production이 staging 검수본과 동일하게 작동함을 확인하는 최종 parity gate**다.

promotion·production parity·post-promotion render 증거를 canonical bundle로 묶어:

```text
PROMOTION_EVIDENCE_SHA
```

를 생성한다. 최소 포함:

```text
PROMOTION_TRANSACTION_ID
promotion_manifest hash
PRODUCTION_RELEASE_ARTIFACT_SHA
production parity report hash
post-promotion render matrix hash
rollback status
```

## 24.6 FINAL SEAL CONFIRMATION

다음이 모두 참일 때만 Mother가 최종 상태를 `SEALED`로 확정한다.

```text
MOTHER_PRESEAL_PASS
AND PROMOTION_STATUS == PASS
AND PRODUCTION_PARITY_GATE == PASS
AND PRODUCTION_RELEASE_ARTIFACT_SHA == FINAL_RELEASE_ARTIFACT_SHA
AND POST_PROMOTION_ALL_RENDER == PASS
AND PROMOTION_EVIDENCE_SHA valid
```

위 조건이 충족되면 §25.3의 최종 `SEAL_BUNDLE_SHA`를 생성·검증하고 `MOTHER_FINAL_REVIEW = PASS`를 기록한 뒤 `SEALED`를 선언한다.

promotion 후 production payload가 staging 최종 SHA와 다르면 `PROMOTION_FAILED` 또는 `SEAL_BROKEN`으로 처리하고 `SEALED`를 금지한다.

# 25. 최종 SHA 3계층 및 Seal Bundle

검수 보고서 생성 때문에 release SHA가 다시 변하는 순환을 막기 위해 SHA를 세 계층으로 분리한다.

## 25.1 RELEASE_ARTIFACT_SHA

학생에게 실제 서비스될 payload의 digest다. A/B/C 단계에서는 staging release candidate에서 계산하고, promotion 후 production에서 같은 digest가 재현되어야 한다.

최소 포함 범위:

- target을 포함하는 최종 production JS 파일 전체
- 해당 JS가 참조하는 문제용 시각자산 중 release 재현에 필요한 파일
- 신규/수정된 `solutionImage` SVG asset
- 학생 화면의 문항/해설 내용에 직접 영향을 주는 release payload

제외:

- A/B/C 보고서
- render screenshot
- ledger
- final review 문서

최종값:

```text
FINAL_RELEASE_ARTIFACT_SHA

PROMOTION 후:
PRODUCTION_RELEASE_ARTIFACT_SHA == FINAL_RELEASE_ARTIFACT_SHA
```

## 25.2 REVIEW_EVIDENCE_SHA

검수·렌더 증거를 묶은 digest다.

최소 포함:

- A final report
- B final report
- C final report
- render matrix
- render failure/console report
- verifier START/END SHA 기록
- carry-forward evidence map
- protected field diff report
- repair/change ledger

```text
REVIEW_EVIDENCE_SHA
```

## 25.3 PRESEAL_BUNDLE_SHA / PROMOTION_EVIDENCE_SHA / SEAL_BUNDLE_SHA

### PRESEAL_BUNDLE_SHA

production promotion 전 Mother가 검수본과 규칙·환경을 연결하여 승인하는 중간 봉인 digest다.

canonical pre-seal bundle에는 최소 다음 값을 넣는다.

```text
FINAL_RELEASE_ARTIFACT_SHA
REVIEW_EVIDENCE_SHA
MANIFEST_SHA
BASELINE_TREE_SHA
PROJECT_STAGING_BASELINE_SHA
PROJECT_CONFIG_SHA
RULESET_SHA
MASTER_MD_SHA
MASTER_JSON_SHA
ENGINE_SHA
DB_SHA
QUESTION_INDEX_SHA
RENDER_RUNTIME_FINGERPRINT_SHA
RENDER_REPORT_SHA
```

이를 canonical JSON으로 정렬·직렬화하여:

```text
PRESEAL_BUNDLE_SHA
```

를 계산한다. `MOTHER_PRESEAL_PASS`는 이 digest를 기준으로 한다.

### PROMOTION_EVIDENCE_SHA

production 승격 이후 실제 운영본과 staging 검수본의 동일성을 증명하는 digest다.

최소 포함:

```text
PROMOTION_TRANSACTION_ID
promotion_manifest hash
PROMOTION_BASELINE_SHA
PRODUCTION_RELEASE_ARTIFACT_SHA
production parity report hash
post-promotion render matrix hash
rollback status
```

```text
PROMOTION_EVIDENCE_SHA
```

### SEAL_BUNDLE_SHA

최종 `SEALED` 상태를 나타내는 최상위 fingerprint다.

```text
SEAL_BUNDLE_SHA = SHA256(canonical {
  PRESEAL_BUNDLE_SHA,
  PROMOTION_EVIDENCE_SHA,
  FINAL_RELEASE_ARTIFACT_SHA,
  PRODUCTION_RELEASE_ARTIFACT_SHA
})
```

최종 조건:

```text
PRODUCTION_RELEASE_ARTIFACT_SHA == FINAL_RELEASE_ARTIFACT_SHA
PRESEAL_BUNDLE_SHA valid
PROMOTION_EVIDENCE_SHA valid
SEAL_BUNDLE_SHA valid
```

검수 보고서 생성과 promotion evidence 생성은 release payload에 포함되지 않으므로 `FINAL_RELEASE_ARTIFACT_SHA`를 순환 변경시키지 않는다.

## 27.2 APPROVED_EXCEPTION

사용자가 명시적으로 원본 결함 또는 시각화 예외를 승인한 경우에만 사용할 수 있다.

승인 근거와 문항 UID를 기록한다.

## 27.3 봉인 후 상태 변경 / Reopen Policy

`SEALED`는 해당 release·evidence·환경 fingerprint 조합에 대한 상태다. 봉인 이후 다음 변화가 생기면 상태를 자동 재평가한다.

```text
RULESET / MASTER 변경 → SEALED_RULESET_STALE
ENGINE / browser / MathJax / font / viewport 등 렌더 환경 변경 → SEALED_RENDER_STALE
RELEASE payload 변경 → SEAL_BROKEN
MANIFEST / source baseline / identity 변경 → SEAL_BROKEN
```

처리 원칙:

- `SEALED_RULESET_STALE`: 변경 규칙의 영향 범위를 판정하고 필요한 A/B/C 증거를 재검한 뒤 새 seal을 발급한다.
- `SEALED_RENDER_STALE`: release payload가 동일하면 A/B 증거는 hash 조건 아래 승계할 수 있으나 C 실제 렌더 증거를 새 runtime에서 재검한다.
- `SEAL_BROKEN`: 기존 seal은 종료된 historical record로만 보존하고 새 `FINAL_RELEASE_ARTIFACT_SHA` 기준으로 필요한 재검 절차를 수행한다.
- 어떤 stale 상태도 기존 `SEALED` 표시를 현재 유효 상태처럼 유지하지 않는다.

검출력을 강제하는 추가 계약이다. 기존 구조를 축약하거나 대체하지 않는다.

문서의 품질은 사람이 읽고 촘촘하다고 느끼는 정도가 아니라, 정답지와 기존 finding을
검수자에게 제공하지 않은 상태에서 known-bad 및 mutation 결함을 실제로 FAIL시키는
성능으로 판정한다.

```text
PROTOCOL_QUALITY = ACTUAL_DEFECT_DETECTION_PERFORMANCE
```

다음 선언만으로는 PASS를 만들 수 없다.

```text
QUESTION_REVIEWED != QUESTION_PROVEN
SVG_LOADED != SVG_CORRECT
SVG_METADATA_VALID != SVG_GEOMETRY_VALID
PYTHON_FACTS_VALID != FINAL_SVG_VALID
94/94 QUESTIONS OPENED != 100% FACT COVERAGE
RENDER_PASS != MATH_PASS
```

## 34.1 REVIEW_BATCH_SIZE와 fresh-context 결박

독립 A/B 검수는 `REVIEW_BATCH_SIZE = 5`를 기본 단위로 수행한다. 마지막 batch만
1~4문항을 허용한다.

각 batch는 다음 식별·해시·상태를 별도 기록한다.

```text
reviewBatchId
reviewBatchOrdinal
REVIEW_BATCH_SIZE = 5
BATCH_QUESTION_UID_SET
BATCH_INPUT_SHA
BATCH_EXPECTED_FACT_SHA
BATCH_OBSERVED_FACT_SHA
BATCH_REVIEW_EVIDENCE_SHA
BATCH_SOURCE_VALIDITY_STATUS
BATCH_B1_NUMERIC_RESULT
BATCH_B2_SEMANTIC_RESULT
BATCH_B3_METADATA_RESULT
BATCH_FINAL_STATUS
```

각 batch는 독립 검수자의 새로운 context에서 시작한다.

- 앞 batch의 PASS, answer, solution, expected fact, observed fact, 라벨 판정, review
  메모를 뒤 batch의 정답 근거로 복사하지 않는다.
- batch 입력에는 해당 batch의 frozen source·artifact·ruleset만 넣는다.
- 이전 batch의 수치·해설·SVG metadata·fact hash는 참고 근거로 제공하지 않는다.
- carry-forward가 승인된 경우에도 §22의 verifier별 input hash와 영향 범위를 먼저
  재확인하고, 새 batch evidence row에서 승계 사유와 재확인 결과를 기록한다.

```text
FULL_UNIT_COVERAGE
!=
SINGLE_CONTEXT_FULL_UNIT_REVIEW
```

전수검수는 모든 문항을 검사했다는 의미이지, 한 context에서 모든 문항을 빠르게
열었다는 의미가 아니다. `REVIEW_BATCH_SIZE`가 없거나 batch별 hash/evidence가 없으면
`REVIEW_EXECUTION_BATCHED = FAIL`이다.

## 34.2 batch fail-stop과 review depth degradation

한 batch에서 HARD FAIL이 하나라도 발견되면 해당 batch는 PASS를 선언하지 않는다.

```text
BATCH_HARD_FAIL > 0
→ BATCH_FINAL_STATUS = FAIL
→ unresolvedBatchFail 기록
→ 허용 범위 내 staging repair
→ 새 RELEASE_ARTIFACT_SHA
→ 영향 batch 재검
```

다음 batch로 진행할 수는 있지만 이전 unresolved FAIL을 숨기거나 전체 PASS로 합산할
수 없다. 최종 seal 직전에는 다음 값이 모두 0이어야 한다.

```text
UNRESOLVED_BATCH_FAIL = 0
UNRESOLVED_FAIL = 0
```

각 batch는 최소 다음 밀도 지표를 남긴다.

```text
QUESTION_COUNT
FACT_OBLIGATION_COUNT
FACT_TESTED_COUNT
OBSERVED_FACT_COUNT
SEMANTIC_ENTITY_COUNT
REVIEW_EVIDENCE_BYTES 또는 동등한 구조화 count
```

뒤 batch에서 문항의 수학적 단순성으로 설명되지 않는 obligation/evidence 급감이
있으면 `REVIEW_DEPTH_DEGRADATION_WARN`, 핵심 fact가 누락되면
`REVIEW_DEPTH_DEGRADATION_FAIL`이다. 이전 batch의 평균값에 맞추기 위해 적용되지
않는 fact를 억지로 추가하지 않으며, 단순 문항의 낮은 실제 obligation은
`N/A_REASON_CODE` 또는 문항별 수치 근거로 설명한다.

## 34.3 BLIND 3-PASS 독립 검수

모든 review batch의 각 문항은 다음 세 pass를 순서대로 수행한다.

### PASS 1 — SOURCE ONLY

검수자가 이 pass에서 볼 수 있는 것은 다음뿐이다.

```text
content
choices
문제 원본 시각자료
```

다음은 PASS 1에서 보지 않는다.

```text
answer
solution
solutionImage
SVG metadata
builder geometry facts
기존 검수 보고서
이전 batch PASS
```

목적은 문제 자체에서 독립 `INDEPENDENT_ANSWER`와 `EXPECTED_FACT_LEDGER`를 만드는
것이다. 산출물은 최소 다음을 포함한다.

```text
INDEPENDENT_ANSWER
SOURCE_VALIDITY_STATUS
EXPECTED_FACT_LEDGER
EXPECTED_FACT_HASH
SOURCE_EVIDENCE_REF
```

`SOURCE_VALIDITY_STATUS`가 다음 중 하나이면 downstream PASS를 생성하지 않는다.

```text
PROBLEM_NOT_WELL_DEFINED
ANSWER_INCONSISTENT
MULTIPLE_VALID_ANSWERS
NO_VALID_ANSWER
CONDITION_CONTRADICTION
SOURCE_DEFECT
```

source defect를 발견했을 때는 answer·solution·SVG를 맞추어 정상처럼 만드는 것이
아니라, 기존 source repair·예외·보류 ledger로 이동한다.

### PASS 2 — ARTIFACT OBSERVATION

PASS 1의 expected 값을 정답으로 삼아 SVG를 판정하지 않는다. 최종 SVG를 독립적으로
parse하고 실제 geometry primitive에서 observed fact를 역산한다.

```text
circle: cx, cy, r
line: x1, y1, x2, y2
polyline/polygon: points
path: d
ellipse: cx, cy, rx, ry
text/label: 실제 위치와 bounding box
SVG root: viewBox, preserveAspectRatio, transform
plot frame / coordinate frame / rendered transform
```

다음 선언 metadata는 observed 정답으로 사용할 수 없다.

```text
data-equation
data-slope
data-point-x
data-point-y
data-radius
data-scale-policy
data-axis-scale-mode
data-model-x1
data-model-y1
data-model-x2
data-model-y2
data-fact-hash
data-geometry-fact-hash
```

metadata는 object identity와 provenance의 보조 힌트로만 보존한다. 실제 `cx/cy/r`,
endpoint, `points`, `path d`, plot frame을 읽어 pixel→math 역변환을 수행한다.

산출물은 최소 다음을 포함한다.

```text
OBSERVED_FACT_LEDGER
OBSERVED_FACT_HASH
OBSERVED_ENTITY_MAP
OBSERVED_SCALE_FACTS
SVG_OBSERVED_GEOMETRY_COUNT
SVG_OBSERVED_FACT_EXTRACTOR_VERSION
```

### PASS 3 — PARITY

마지막에만 다음 값을 함께 비교한다.

```text
EXPECTED FACTS ↔ ANSWER
EXPECTED FACTS ↔ SOLUTION
EXPECTED FACTS ↔ SVG OBSERVED FACTS
SOLUTION ↔ SVG OBSERVED FACTS
METADATA ↔ OBSERVED FACTS (보조 consistency only)
```

다음 parity 중 하나라도 FAIL이면 문항과 batch는 FAIL이다.

```text
PROBLEM ↔ INDEPENDENT FACTS
SOLUTION ↔ INDEPENDENT FACTS
SVG OBSERVED FACTS ↔ INDEPENDENT FACTS
PROBLEM ↔ SOLUTION
PROBLEM ↔ SVG OBSERVED
SOLUTION ↔ SVG OBSERVED
```

### 34.3.1 anchoring 금지

다음 행위는 독립 검수 위반이며 해당 batch의 결과를 무효화한다.

- answer를 보고 독립 정답을 계산함
- solution에 적힌 좌표·식을 expected fact로 복사함
- SVG `data-*` 좌표·식을 expected fact로 사용함
- Builder Python facts를 verifier expected fact로 사용함
- 기존 finding 목록을 보고 해당 오류가 있는지 확인하는 방식으로 PASS를 만듦

판정:

```text
INDEPENDENCE_BROKEN
→ BATCH_REVIEW_INVALID
→ 새 fresh context에서 해당 batch 재실행
```

`N/A`를 허용한다.

```text
해당 entity/relation이
content / choices / 독립 solution graph / solution / SVG
어디에도 존재하지 않음
```

N/A를 기록할 때 반드시 다음을 남긴다.

```text
N/A_REASON_CODE
N/A_EVIDENCE_REF
```

```text
NOT_TESTED_FACT_COUNT == 0
```

## 34.5 직선·수선·교점의 실제 SVG 역검산

`data-equation == expected`만으로 PASS하지 않는다. 실제 line endpoint를 plot frame의
역변환으로 math coordinate로 복원하여 다음을 다시 계산한다.

```text
OBSERVED_POINT_1
OBSERVED_POINT_2
OBSERVED_SLOPE
OBSERVED_LINE_EQUATION
OBSERVED_X_INTERCEPT
OBSERVED_Y_INTERCEPT
```

그 뒤 expected와 비교한다.

```text
actual rendered geometry
→ recovered equation
→ expected equation
```

수선의 발 H가 문제·solution·SVG 어느 한 곳이라도 등장하면 다음을 모두 검사한다.

1. H의 독립 계산 좌표와 observed 좌표
2. H가 대상 직선 위인지
3. PH와 대상 직선이 수직인지
4. solution이 거리를 사용하면 `|PH|`

다음은 모두 HARD FAIL이다.

- H 이름만 맞고 좌표가 다름
- 대상 직선 위지만 PH가 수직이 아님
- 수직이지만 H가 대상 직선 위가 아님
- solution 수치는 맞지만 SVG pixel 위치가 다름
- SVG metadata 좌표는 맞지만 실제 pixel geometry가 다름

교점 P는 두 직선에 실제로 대입한다.

```text
P ∈ line1
P ∈ line2
```

평행은 기울기 또는 일반형 계수의 비례 관계를 계산하고, 수직은 유한 기울기인
경우 `m1 × m2 = -1`을 계산한다. 수직선·수평선은 별도 특수 케이스로 처리한다.

## 34.6 B 검수를 B1/B2/B3로 분리

기존 독립 B의 역할은 유지하되, 다음 세 sub-pass를 한 문항·한 batch에서 별도
판정한다. “전체적으로 정상”은 B 결과가 아니다.

### B1 — NUMERIC GEOMETRY

다음을 실제 수치로 계산한다.

```text
coordinates
line equations
slope
intercepts
intersection
parallel/perpendicular
perpendicular foot
distance
circle center/radius
transform coordinates
pixel scale
```

결과는 `B1_PASS` 또는 `B1_FAIL`이며 적용 obligation별 실제 값과 residual을 evidence row에
남긴다.

### B2 — SEMANTIC GEOMETRY

수치가 맞는 것과 학생용 SVG가 충분한 것은 별도다. 다음을 확인한다.

```text
핵심 객체 존재
핵심 관계의 실제 시각 표현
풀이 핵심 단계의 SVG 표현
불필요하거나 가짜인 객체 부재
객체 identity 일치
```

예를 들어 수선 문항의 required semantic set이 다음이면:

```text
P, line, H, PH segment, PH ⟂ line
```

관측 set에 H만 있고 PH segment 또는 perpendicular relation이 없으면
`SEMANTIC_GEOMETRY_INSUFFICIENT`이며 B2 FAIL이다.

### B3 — METADATA

다음을 B1/B2와 독립적으로 검사한다.

```text
standardUnitKey
standardUnit
subUnitKey
subUnit
subUnitConfidence
subUnitClassificationDepth
tags
questionType
solutionImage linkage
```

B3의 metadata PASS는 B1/B2 PASS를 대신하지 않는다.

```text
B1_PASS AND B2_PASS AND B3_PASS = B_BATCH_PASS 후보
```

## 34.7 실제 scale과 geometry invariant

`EQUAL_SCALE_REQUIRED`, `EQUAL_UNIT`, `data-radius`, fact hash 선언을 확인하는 것만으로
scale PASS를 만들지 않는다. 실제 SVG에서 다음을 계산한다.

```text
PX_PER_X_UNIT
PX_PER_Y_UNIT
SCALE_RATIO = PX_PER_X_UNIT / PX_PER_Y_UNIT
RENDERED_SCALE_ERROR
```

원·거리·각·대칭처럼 metric 의미가 있으면 실제 pixel 중심·반지름·거리도 같은 단위계로
검증한다. 예를 들어 `data-radius="3"`이어도 실제 `r`이 `3 × PX_PER_UNIT`과 다르면
FAIL이다. 선언 metadata와 실제 geometry가 다르면 `FAIL_SVG_OBSERVED_GEOMETRY`다.

기존 §4.4 허용오차를 사용하며 문항별로 임의 완화하지 않는다.

```text
model_scale_error <= 1e-9
rendered_scale_error <= 0.005
```

`SCHEMATIC_ALLOWED`인 경우에도 object identity, incidence, ordering, parallel,
perpendicular, inside/outside, intersection/non-intersection, tangent/non-tangent 같은
topology·semantic 관계를 실제 element에서 확인한다. 검사하지 않은 도식은 PASS가 아니라
`NOT_TESTED`다.

## 34.9 denominator closure와 coverage 분리

최종 보고서에는 다음 coverage를 별도로 기록한다.

```text
METADATA_COVERAGE
RENDER_COVERAGE
```

## 34.11 inventory qualification과 full render closure

metadata key로 모은 목록만으로 scope를 닫지 않는다. 기존 forward + reverse scan을
모두 실행하고 다음을 기록한다.

```text
FORWARD_SCOPE_COUNT
REVERSE_SCOPE_CANDIDATE_COUNT
RECONCILED_SCOPE_COUNT
RECLASSIFIED_COUNT
```

metadata 기준 대상만 검사했거나 forward/reverse 차이를 설명하지 못하면
`SCOPE_DISCOVERY_INCOMPLETE`다.

최종 C에서는 대표 시험지·sentinel만 렌더할 수 없다.

```text
TARGET_RENDER_EXAMS × {exam, solution, answer}
```

모든 target-containing production exam을 실제 렌더한다.

```text
FINAL_RENDER_DENOMINATOR = TARGET_RENDER_EXAM_COUNT × 3
EXAM_RENDER_COUNT == TARGET_RENDER_EXAM_COUNT
SOLUTION_RENDER_COUNT == TARGET_RENDER_EXAM_COUNT
ANSWER_RENDER_COUNT == TARGET_RENDER_EXAM_COUNT
NOT_TESTED == 0
```

83/84, 79/81처럼 하나라도 빠진 결과는 PASS가 아니다. 문항 하나의 변경도 해당
시험지 전체 `exam/solution/answer` 세 모드 재검을 요구한다. C의 실제 렌더는 MathJax
완료, 이미지 decode, SVG 출력, 빈 패널, clipping, label overlap, overflow, answer
table, console error, runtime fingerprint를 함께 기록한다.

## 34.12 PROTOCOL QUALIFICATION GATE — known-bad corpus

v2.2 문서 자체를 운영 채택하기 전에, 기존 외부 검수 전 SHA의 직선의 방정식 corpus를
사용하여 protocol detection 성능을 측정한다.

```text
KNOWN_BAD_REPO_SHA
+
v2.2 execution contract
```

검수 context에는 기존 finding 목록을 넣지 않는다. ground truth evaluator만 나중에
검수 결과와 비교한다.

현재 qualification 기준 corpus:

```text
KNOWN_BAD_SCOPE = 94문항 / 28 JS
KNOWN_NUMERIC_HARD_FAIL = 21
KNOWN_SEMANTIC_SVG_DEFECT = 27
KNOWN_METADATA_DEFECT = 10
```

범주 중복은 문항 UID/category 기준으로 중복 제거하여 계산한다.

```text
KNOWN_NUMERIC_HARD_FAIL_RECALL
  = detected_numeric_known_bad / total_numeric_known_bad

KNOWN_SEMANTIC_SVG_RECALL
  = detected_semantic_known_bad / total_semantic_known_bad

KNOWN_METADATA_DEFECT_RECALL
  = detected_metadata_known_bad / total_metadata_known_bad
```

최종 목표와 fail condition은 다음과 같다.

```text
P0/P1_FALSE_NEGATIVE == 0
KNOWN_BAD_RECALL_GATE_PASS
```

known P0/P1 defect miss가 1개라도 있거나, expected/observed evidence가 없거나,
scope denominator가 닫히지 않거나, `NOT_TESTED > 0`이면:

```text
PROTOCOL_QUALIFICATION_FAIL
NOT_READY_FOR_PRODUCTION_REVIEW
```

기존 결함의 약 1/3만 재현하는 결과를 PASS로 기록하지 않는다.

## 34.13 MUTATION DETECTION GATE

known-bad corpus 과적합을 막기 위해 정상 asset의 임시 candidate/staging copy에
synthetic defect를 주입한다. production과 production baseline은 절대 수정하지 않는다.

최소 mutation family:

```text

X_INTERCEPT_MUTATION
Y_INTERCEPT_MUTATION
INTERSECTION_SHIFT
PERPENDICULAR_FOOT_SHIFT
PARALLEL_ROTATION
PERPENDICULAR_ROTATION
POINT_COORDINATE_SHIFT
CIRCLE_RADIUS_MUTATION
X_Y_SCALE_MISMATCH
LABEL_SWAP
ENTITY_TYPE_SWAP

REMOVE_PERPENDICULAR_RELATION
ADD_UNDEFINED_POINT
SCHEMATIC_POLICY_MISUSE
```

mutation을 만든 로직이 스스로 detection을 판정하지 않도록 역할을 분리한다.


```text

MUTATION_DETECTION_GATE_PASS
```

mutation은 `temp/` 또는 staging에서만 수행하고, 실제 production asset·DB·index·
production JS의 hash는 mutation 전후 동일해야 한다.

## 34.14 Pilot Gate의 검출력 qualification

PILOT SYSTEM GATE는 known-good만 PASS시키는지 확인하는 절차가 아니다. 다음 두 종류를
모두 포함해야 한다.


사실만으로 `PILOT_INDEPENDENT_SYSTEM_PASS`를 선언하지 않는다.

```text

AND PILOT_KNOWN_BAD_DETECTION_PASS
AND PILOT_MUTATION_DETECTION_PASS
```

# 36. 실제 실행기 결박 — source fact와 SVG observed fact의 분리

v2.2 실행 검수기는 production SVG의 `data-*` 메타데이터, 기존 PASS 보고서, 생성기
fact map을 expected value로 사용하지 않는다. expected 쪽은 현재 production
`questionBank`의 `content`와 `solution`에서 별도로 파싱·계산하고, SVG 쪽은 현재
파일의 실제 `<line>`, model endpoint, pixel endpoint, `<segment>`, point,
caption을 관찰해 다시 계산한다. 따라서 `data-a/b/c`가 자기 label과 일치해도 endpoint가
그 식 위에 없으면 PASS할 수 없다.

실행기는 다음 명시적 hard gate 이름을 machine-readable evidence row마다 기록한다.

```text
LINE_LABEL_COEFFICIENT_PARITY
NONZERO_LINE_GEOMETRY
REQUIRED_POINT_ON_LINE
PERPENDICULAR_FOOT_PARITY
PARALLEL_PERPENDICULAR_PARITY
INTERSECTION_PARITY
INTERCEPT_PARITY
REQUIRED_GEOMETRY_PRESENCE
CAPTION_SEMANTIC_PARITY
VISIBLE_GEOMETRY_PARITY
SVG_XML_WELL_FORMED
```

각 gate의 입력은 다음처럼 고정한다.

```text
SOURCE_CANONICAL_FACT
  = current content/solution parse + independent algebraic recomputation

SVG_OBSERVED_FACT
  = visible primitive + model endpoint + pixel endpoint + visible text observation

LINE_LABEL_COEFFICIENT_PARITY
  = normalize(visible equation label)
  = normalize(data-a, data-b, data-c)
  = normalize(line(endpoint-1, endpoint-2))
  = SOURCE_CANONICAL_FACT when a concrete source equation exists
```

`N/A`는 source에 해당 의무가 실제로 없거나 수치 fact를 독립 산출할 수 없는 경우에만
허용하며, 사유를 row에 남긴다. parse 불가·파일 누락·렌더 미실행은 `N/A`가 아니라
`FAIL` 또는 `NOT_TESTED`다.

## 36.1 94문항·28파일 reverse confirmation

실행 시점의 scope contract는 다음을 동시에 만족해야 한다.

```text
TARGET = 94
REVIEWED = 94
COVERAGE = 100%
H15-SA-10 = 63
H22-C2-02 = 31
SOURCE_JS_FILE_COUNT = 28
```

`reviewed`는 문항 row가 생성되었다는 뜻만이 아니라, 각 row에 source digest,
independent canonical fact 결과, SVG actual observation, 모든 applicable gate 결과가
있다는 뜻이다. 23문항 또는 known-bad 목록만 재검한 결과는 94문항 qualification으로
승격하지 않는다.

## 36.2 생성기·source-of-truth 무쓰기 검수

현재 생성기 `archive/tools/geometry-equation/finalize-line-equation-current.mjs`가
dirty라면 이를 실행하거나 덮어쓰지 않는다. 대신 다음 무쓰기 검수기를 실행한다.

```powershell
node archive/tools/geometry-equation/verify-line-equation-v22-qualification.mjs --check
```

이 명령은 생성기를 import/execute하지 않고, 생성기 source hash와 정적 fact-entry
coverage를 기록하며, expected fact를 production SVG에서 읽지 않았음을 함께 기록한다.
`productionWrites = 0`, `generatorExecuted = false`, `staleReportUsedAsOracle = false`가
아니면 검수는 즉시 종료한다. 생성기의 별도 `--check` 지원을 나중에 추가하더라도
그 결과는 이 독립 verifier의 source-side expected fact를 대체하지 않는다.

## 36.3 fail-closed로 남긴 현재 보류

현재 실행 evidence는 검수기를 추가한 것과 release qualification이 통과한 것을
구분한다. 다음은 자동 수정하지 않고 명시적으로 보류한다.

```text
SOURCE_CONFLICT/HOLD
  22_팔마고_1학기_기말_고1_기출.js#5
  current source: m=-2 → 3x+3y+5=0
  external candidate: 3x+3y-5=0

SCHEMATIC_ALLOWED/HOLD
  24_제일고_1학기_중간_고1_기출.js#15
  22_강남여고_2학기_중간_고1_기출.js#22
  25_제일고_2학기_중간_고1_기출.js#12
```

위 source conflict에서 외부 후보를 정답으로 취급하거나, 세 `SCHEMATIC_ALLOWED`를
검수 통과로 변환하는 것은 금지한다. 현재 브라우저 evidence는 28개 시험지 84모드를
새로 실행하고, `exam / sol / ans` 문항 수·마지막 문항·raw LaTeX·load error·overflow를
확인한다. 단 하나의 live SVG decode 실패라도 `BROWSER_RENDER_FAIL`이며, 해당 자산이
다른 작업의 dirty 변경이면 덮어쓰지 않고 HOLD/FAIL 근거로 기록한 뒤 재실행한다.

현재 구현의 qualification 산출물은 다음이다.

```text
archive/tools/geometry-equation/verify-line-equation-v22-qualification.mjs
archive/analysis/line-equation-v22-qualification/qualification.json
archive/analysis/line-equation-v22-qualification/browser-render-evidence.json
```

`qualification.status`가 `PASS`가 아니거나 `releaseReady`가 false이면 production
fact의 atomic promotion, final seal, main release를 선언하지 않는다. 이 상태는 새
검수기 구현의 커밋 가능 여부와 별개로, 현재 production line-equation 사실의 최종
봉인을 차단하는 fail-closed 상태다.
