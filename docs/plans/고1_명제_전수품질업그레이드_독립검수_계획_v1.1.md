- 명제와 조건의 구분
- 참과 거짓의 판정

- 필요조건·충분조건·필요충분조건

모든 대상 문항을 실제로 검토하며, 이미 충분한 해설은 무리하게 늘리지 않는다. 그러나 명제 특유의 핵심 논리가 생략되어 있으면 반드시 보강한다.


# 4. 문항별 상태 분류

모든 대상 문항을 다음 중 하나로 분류한다.

## 4.1 `KEEP_VERIFIED`

현재 해설이 명제 강화 기준을 충분히 만족한다.

조건:

- 학생이 핵심 논리 방향을 재현 가능
- 반례 또는 증명 이유가 충분
- 필요·충분 방향이 명확
- 논리 점프 없음
- 시각자료가 없어도 이해 가능

## 4.2 `TEXT_UPGRADE`

문제와 답은 정상이나 해설이 학생 관점에서 부족하다.

대표 예:

- 결론만 있고 이유가 없음
- `P⊆Q`만 쓰고 필요·충분 의미를 설명하지 않음
- 대우를 결과만 제시
- 반례 값만 적고 왜 반례인지 설명하지 않음
- 귀류법의 모순 대상이 불명확
- 존재·전칭 부정 변환을 한 줄로 처리
- 증명 중간 단계가 생략됨

## 4.3 `VISUAL_ADD`

텍스트 해설은 충분하지만 시각자료가 있으면 학생 이해가 크게 좋아지는 문항.

## 4.4 `TEXT_AND_VISUAL_UPGRADE`

해설과 시각자료가 모두 필요한 문항.

## 4.5 `SOURCE_REVIEW`

해설 업그레이드 전에 원본 또는 문항 성립성 확인이 필요한 경우.

대표 예:

- 발문 LaTeX 깨짐
- 선택지 형식 불명확
- 단일정답/복수정답 충돌
- 원문 수 체계 누락 의심
- 원본에서 빠진 조건 가능성
- answer와 발문 형식 불일치

`SOURCE_REVIEW` 상태에서는 임의로 문제를 고쳐 맞추지 않는다.
먼저 source/provenance를 확인한다.

# 7. 참·거짓과 반례

거짓 명제는 가능한 한 실제 반례를 제시한다.

단순히:

```text
x=3이 반례이다.
```

로 끝내지 않는다.

권장 구조:

```text
x=3을 대입하면
가정은 참이지만
결론은 거짓이다.
따라서 이 값은 반례이고,
명제 전체는 거짓이다.
```

전칭명제의 거짓 판정에서는 **반례 하나면 충분한 이유**를 학생이 이해할 수 있게 한다.

# 8. 역·이·대우

기본 변환 구조:

```text
원명제: p → q
역:     q → p
이:     ~p → ~q
대우:   ~q → ~p
```

단, 기호만 나열하지 않는다.
실제 문제의 문장으로 다시 번역한다.

## 8.1 대우

필요한 문항에서는 다음을 명시한다.

> 원명제와 대우는 항상 같은 참·거짓을 가진다.

대우를 이용한 증명에서는:

```text
원명제보다 대우가 다루기 쉬운 이유
→ 대우 작성
→ 대우 증명
→ 원명제와 대우의 진리값이 같음
→ 원명제 참
```

순서가 보이게 한다.

# 9. 필요조건·충분조건·필요충분조건

명제 단원에서 가장 강하게 보강할 영역이다.

## 9.1 충분조건

```text
p가 q의 충분조건
↓
p이면 q
↓
p → q
↓
P ⊆ Q
```

학생 설명:

> p만 만족하면 q까지 자동으로 따라오므로 p는 q를 보장하기에 충분하다.

## 9.2 필요조건

```text
p가 q의 필요조건
↓
q이면 반드시 p
↓
q → p
↓
Q ⊆ P
```

학생 설명:

> q가 성립하려면 p가 반드시 필요하므로 p는 q의 필요조건이다.

## 9.3 필요충분조건

양방향을 반드시 각각 확인한다.

```text
p → q
q → p
```

둘 다 참이어야 한다.
단순히 “두 조건이 같다”로 끝내지 않는다.

# 10. 진리집합과 명제

명제의 핵심 연결:

```text
p → q  ⇔  P ⊆ Q
```

를 학생이 이해할 수 있게 설명한다.

필요할 경우:

> p를 만족하는 모든 x가 q도 만족해야 하므로 P 전체가 Q 안에 들어가야 한다.

라고 문장으로 풀어준다.

여집합 포함의 방향이 바뀌는 경우도 이유를 생략하지 않는다.

```text
P ⊆ Q
⇔
Q^c ⊆ P^c
```

# 11. 존재명제·전칭명제와 부정

## 11.1 존재명제의 부정

```text
어떤 x에 대하여 P(x)
↓ 부정
모든 x에 대하여 ~P(x)
```

## 11.2 전칭명제의 부정

```text
모든 x에 대하여 P(x)
↓ 부정
어떤 x에 대하여 ~P(x)
```

## 11.3 부등식 부정

필요한 문항에서 동시에 확인한다.

```text

≤  ↔ >
>  ↔ ≤
≥  ↔ <
=  ↔ ≠
```

학생이 `어떤→모든`만 바꾸고 부등호 부정을 놓치지 않도록 한다.

# 12. 귀류법

귀류법은 다음 5단계를 명확하게 보여준다.

```text
1. 결론의 부정을 가정
2. 그 가정에서 논리를 전개
3. 모순 발생
4. 무엇과 무엇이 모순인지 명시
5. 처음 가정이 거짓 → 원래 결론 참
```

금지:

> 이는 모순이다.

만 쓰고 끝내는 해설.

반드시 모순 대상을 명시한다.

예:

```text
m,n을 서로소라고 두었는데
m,n이 모두 2의 배수라는 결론이 나왔다.
이는 서로소라는 처음 조건과 모순이다.
```

# 13. 제곱의 홀짝·배수 증명

다음과 같은 표현은 학생에게 논리 점프가 될 수 있다.

> q²이 짝수이므로 q도 짝수이다.

필요한 경우 이유를 보강한다.

예:

```text
q가 홀수라고 가정하면 q=2k+1이고
q²=4k²+4k+1도 홀수이다.
따라서 q²이 짝수라면 q는 홀수일 수 없으므로 q는 짝수이다.
```

합동식(mod) 표기는 교육과정과 학생 수준을 고려한다.

공통수학2 학생용 해설에서는 가능하면:

```text
a² ≡ 1 (mod 4)
```

보다는

> 홀수의 제곱을 4로 나누면 나머지가 1이다.

처럼 풀어 쓴다.

# 14. 부등식 증명과 최댓값·최솟값

AM-GM, Cauchy, 완전제곱 등을 적용할 때 다음을 확인한다.

- 적용 조건이 충족되는가
- 왜 그 항을 선택했는가
- 등호 조건은 무엇인가
- 등호가 원래 조건에서도 실제 가능한가
- 하한/상한이 실제로 달성되는가
- 최댓값/최솟값인지 단순 bound인지 구분되는가

단순히 공식만 대입하는 해설은 보강 대상이다.

대상:

- 실수 범위
- 부등식 진리집합
- 매개변수 포함관계
- 열린구간/닫힌구간 경계

수직선에서는 다음이 정확해야 한다.

- 값의 순서
- 포함/불포함
- 열린점/닫힌점
- 좌우 방향
- 무한대 방향

실제 거리 비율은 정확한 척도일 필요가 없다.

## 16.3 `IMPLICATION_FLOW`

대상:

- 조건 연쇄
- 여러 명제 추론
- 필요충분조건 cycle
- 카드 논리

예:

```text
r → t → p → q → r
```

## 16.4 `CONTRAPOSITIVE_MAP`

대상:

- 대우 개념
- 대우 증명
- 역/이/대우 비교

## 16.5 `PROOF_FLOW`

대상:

- 귀류법
- 무리수 증명
- 대우를 이용한 증명
- 여러 단계의 증명

## 16.6 `TRUTH_TABLE / CASE_TABLE`

대상:

- 카드 문제
- 거짓말 문제
- 참/거짓 조합
- 조건게임

# 17. SVG 품질 기준

신규 SVG는 학생용 해설 자료이다.

반드시 다음을 지킨다.

- 문제·해설과 의미 일치
- answer leak 금지
- 선택지 번호 강조 금지
- 내부 provenance visible text 금지
- 답을 미리 알려주는 색칠 금지
- `title`, `desc`, `viewBox` 존재
- 라벨 잘림 금지
- 글자 겹침 금지
- 모바일/인쇄에서 읽을 수 있는 크기
- 개념도는 `SCHEMATIC_ALLOWED`
- 수직선은 경계 semantics 정확

명제 단원에서는 대부분 실제 축척이 필요하지 않다.

```text
DEFAULT_SCALE_POLICY = SCHEMATIC_ALLOWED
```

# 18. 현재 확인된 즉시 수정 후보

이번 전체 작업에 포함한다.

## 18.1 `22_팔마고 2mid q3`

현재:

```text
q:x\gta-7
```

형태의 LaTeX 결함이 발문과 해설에 존재한다.

의도한 표현:

```text
x > a-7
```

source/provenance 확인 후 정상 복구한다.

진리집합 포함 문제이므로 수직선 추가 가치가 높다.

## 18.2 `22_팔마고 2mid q15`

현재 solution에:

```text
a\gtb\gtc
```

등의 깨진 LaTeX가 존재한다.

정상 수식으로 복구한다.

## 18.3 `22_팔마고 2mid q9`

현재:

```text
answer = "③, ⑤"
```

이고 실제 논리상 ③,⑤가 모두 참이다.

발문 형식이 단일 객관식처럼 보이므로 source/provenance에서 원본 선택 형식을 확인한다.

원본이 복수정답형이면 표시 구조를 맞추고, 원본이 단일정답형이면 누락 조건 또는 전사 오류 여부를 조사한다.

임의로 하나의 선택지를 지우지 않는다.

## 18.4 `25_제일고 2final q4`

`x,y`의 수 체계가 명시되지 않은 상태로 실수 명제로 풀이되고 있는지 source 확인 후 자족성을 보강한다.

## 18.5 `25_제일고 2final q22`

학생용 해설에서 합동식 표기:

```text
a²≡1 (mod 4)
```

를 사용하는 부분은 공통수학2 학생 눈높이 기준으로 풀어쓴 설명으로 변경한다.

## 18.6 `24_제일고 2final q6`

`x²≤a`에서 `a<0`일 때 진리집합이 공집합인 경우를 해설에서 누락하지 않도록 한다.

최종 답이 같더라도 조건 전체를 학생이 이해할 수 있게 설명한다.

# 21. 작업 순서

## Phase 0 — Inventory

1. 최신 main SHA lock
2. H15/H22 명제 forward scan
3. reverse scan
4. original/similar 분리
5. student-facing 최종 수량 확정
6. 기존 solutionImage inventory
7. source/provenance 접근 가능 여부 기록

## Phase 1 — Source repair

먼저 다음을 처리한다.

- 깨진 LaTeX
- 원문 누락
- 단일/복수정답 형식
- 수 체계 불명확
- answer/content 구조 충돌

## Phase 2 — Text upgrade

모든 대상 문항을 실제로 읽고 다음을 판단한다.

```text
KEEP_VERIFIED
TEXT_UPGRADE
VISUAL_ADD
TEXT_AND_VISUAL_UPGRADE
SOURCE_REVIEW
```

부족한 해설은 명제 전용 기준에 맞게 보강한다.

## Phase 3 — Visual upgrade

해설을 먼저 완성한 뒤 그 해설에서 필요한 시각자료를 만든다.

```text
solution first
→ visual need decision
→ SVG/table creation
```

그림부터 만들고 해설을 거기에 맞추지 않는다.

## Phase 4 — Static validation

Codex는 수정 후 최소 검증만 수행한다.

- 변경 JS `node --check`
- archive JS evaluation
- `solution` 공란 없음
- solutionImage 경로 존재
- SVG XML 구조
- `title`, `desc`, `viewBox`
- answer leak static scan
- `git diff --check`
- duplicate qKey 없음
- question index regenerate if required

Codex는 최종 PASS를 선언하지 않는다.

## Phase 5 — Git 반영

의미 있는 단위로 commit 가능.

최종적으로:

```text
HEAD == main == origin/main
worktree clean
```

확인.

## Phase 6 — ChatGPT 독립 검수

GitHub에 반영된 최종 SHA 기준으로 ChatGPT가 독립 검수한다.

검수 범위:

- 전체 변경 diff
- source repair 적정성
- 대표 및 고위험 문항 수학 재검
- 필요·충분 방향
- 반례 적절성
- 역·이·대우
- 존재/전칭 부정
- 귀류법 모순 구조
- 증명 교육과정
- 신규 SVG 의미
- answer leak
- solutionImage linkage
- index parity
- 필요 시 실제 렌더 확인

잔여 결함이 발견되면 해당 문항만 핀포인트 수정한다.

# 25. 최종 판정 체계

## `FINAL PASS`

- 모든 HARD 결함 해결
- 학생 이해도 기준 충족
- 신규 visual 의미 정상
- Git 반영 정상
- ChatGPT 독립 재검 통과

- 수학/정답/논리는 정상

- source corruption

- 잘못된 반례
- 잘못된 대우/부정
- 귀류법 논리 오류
- 교육과정 밖 핵심 풀이
- SVG 의미 오류
- answer leak
- 렌더를 방해하는 LaTeX 결함

# 26. 이번 프로젝트의 핵심 성공 기준

이번 작업은 “명제 해설을 길게 만들었다”로 평가하지 않는다.

2. 왜 이 명제는 참 또는 거짓인가?
3. 왜 이 값 하나가 반례가 되는가?
4. 왜 p가 충분조건이고 q가 필요조건인가?
5. 왜 진리집합 포함 방향이 이렇게 되는가?
6. 왜 대우를 사용해도 되는가?
7. 왜 ‘어떤’의 부정이 ‘모든’인가?
8. 귀류법에서 정확히 무엇과 무엇이 모순인가?
9. 왜 이 부등식의 등호 조건이 그 값인가?
10. 같은 유형을 다시 만났을 때 해설 없이 논리를 재현할 수 있는가?

이 질문에 답할 수 없는 문항은 이번 업그레이드에서 미완료로 본다.

## 부록 A.1 현재 production 스냅샷과 범위 잠금

2026-09-04 읽기 전용 스냅샷에서 다음 결과가 재현되었다. 이는 최종 manifest가 아니라 **작업 시작 전 비교 기준**이다.

|---|---:|---:|---:|---:|
| `archive/exams/original/high/h1` | 112 | 144 | 24 | 168 |
| `archive/exams/similar/high/h1` | 25 | 0 | 24 | 24 |
| 합계 | 137 | 144 | 48 | 192 |

위 수량은 각 JS의 `questionBank`를 읽어 다음 순서로 직접 집계한 값이다.

```text
1. archive/exams/original/high/h1 및 archive/exams/similar/high/h1 아래 JS 수집
2. 각 JS의 questionBank 로드
3. standardUnitKey가 H15-SB-02 또는 H22-C2-06인 문항 집계

```

이번 계획에서는 현재 문서의 취지에 따라 `similar` 24문항을 포함한다.


- `standardUnitKey`만 같고 실제 문항 내용이 명제와 무관한 객체
- 동일 문항의 backup/copy 객체 중 manifest에서 중복으로 판정된 객체

반대로 `standardUnitKey`가 비어 있거나 다른 값이어도 실제 명제 문항으로 의심되는 경우에는 누락 후보로 기록한다. 이 후보를 임의로 생산 범위에 넣거나 메타데이터를 즉시 고치지 않고 `METADATA_REVIEW_REQUIRED`로 보류한다.

## 부록 A.2 기준 파일과 source precedence

실행 전 다음 파일의 존재와 읽기 가능 여부를 기록한다.

| 목적 | 기준 경로 |
|---|---|
| 표준단원·세부단원 기준 | `docs/rules/01_CANONICAL/JS아카이브_표준단원키_마스터테이블.md` 및 compiled master |
| 원본 문항 | `archive/exams/original/high/h1/.../*.js` |
| 유사 문항 | `archive/exams/similar/high/h1/.../*.js` 및 `sourceGrounding`/생성 근거 |
| 통합 DB | `archive/db.js` |
| 문항 인덱스 | `archive/question-index.js` |
| 문제·해설·정답 렌더 | `archive/engine.html` |
| 혼합형 렌더가 사용되는 경우 | `archive/mixed_engine.html` |
| 해설용 자산 | `archive/assets/images/...` 또는 실제 JS가 참조하는 경로 |
| 기존 운영 규정 | `docs/rules/02_PIPELINES/해설프로토콜.md`, `docs/rules/02_PIPELINES/수정프로토콜.md`, 관련 review 규정 |

근거의 우선순위는 다음과 같이 고정한다.

```text
원본 시험지·스캔/PDF가 확인 가능한 경우의 원문
→ production JS의 content/choices/answer 구조
→ production JS의 기존 solution 및 solutionImage
→ 기존 answer/index/db 파생값
→ 유사문항의 sourceGrounding 및 생성 계획
```

기존 `solution`과 `answer`는 검토 대상이지 독립적인 수학적 근거가 아니다. 원본과 production JS가 충돌하면 `SOURCE_REVIEW`로 멈추고, 어느 한쪽을 임의로 정답 근거로 선택하지 않는다.

## 부록 A.3 시작 게이트와 사용자 변경 보호

다음 값을 작업 ledger의 첫 레코드에 기록한 뒤에만 문항을 수정한다.

```text
BASELINE_ORIGIN_MAIN_SHA
BASELINE_WORKTREE_STATUS
BASELINE_MANIFEST_SHA
BASELINE_RENDER_RUNTIME_FINGERPRINT
BASELINE_DATE_KST
```

실행 규칙:

1. `git fetch origin --prune`은 원격 참조를 읽기 위한 단계로만 수행한다.
2. `origin/main`을 확인한 뒤 자동 `reset --hard`, `clean`, `checkout`, 대규모 `merge`로 작업트리를 덮어쓰지 않는다.
3. 작업트리가 dirty이면 변경 파일 목록과 현재 SHA만 보고하고, 사용자 변경을 보존한 채 구현을 시작하지 않는다.
4. 구현은 `codex/` 접두사의 작업 브랜치에서 진행한다. `main` 직접 수정은 금지한다.
5. 수정 전 보호 필드의 정규화 해시를 저장하고, 수정 후 허용되지 않은 필드의 해시가 달라지면 즉시 `SCOPE_VIOLATION`으로 처리한다.
6. 최종 `HEAD == main == origin/main`은 사용자가 명시적으로 merge/push를 승인한 릴리스 단계에서만 요구한다. 작업 브랜치의 완결과 main 반영을 같은 단계로 간주하지 않는다.

## 부록 A.6 명제 전용 수학 안전장치

기존 §6~§15 기준에 다음 항목을 추가한다.

### 부록 A.6.1 정의역과 공집합

각 문항마다 변수의 정의역을 해설과 ledger에 명시하거나 source에서 확인한다.

- 실수·정수·자연수·양의 정수·0이 아닌 실수 여부
- 약수·배수·서로소 조건에 적용되는 수 체계
- 전체집합 `U`와 각 진리집합의 관계
- 제곱근·분모·로그 등 추가 정의 조건
- 진리집합이 공집합이거나 전체집합인 경우

정의역이 결과에 영향을 주는데 source에도 명시가 없으면 `DOMAIN_UNCLEAR` 및 `SOURCE_REVIEW`로 둔다. 자연수에 0을 포함하는 관례처럼 결과가 달라질 수 있는 관례를 조용히 선택하지 않는다.

### 부록 A.6.2 조건명제의 참·거짓과 허위 전건

조건명제 `p → q`를 판정할 때 다음 표를 기본으로 사용한다.

| p | q | p → q |
|---|---|---|
| 참 | 참 | 참 |
| 참 | 거짓 | 거짓 |
| 거짓 | 참 | 참 |
| 거짓 | 거짓 | 참 |

전칭 조건명제를 반박하는 반례는 단순히 `q`가 거짓인 값이 아니라, **정의역 안에서 `p`는 참이고 `q`는 거짓인 값**이어야 한다. 반대로 전건이 거짓인 경우를 찾아 명제가 거짓이라고 하지 않는다.

### 부록 A.6.3 논리연산과 부정

양화사와 부등호뿐 아니라 복합조건의 부정도 함께 확인한다.

```text
~(p ∧ q) = (~p) ∨ (~q)
~(p ∨ q) = (~p) ∧ (~q)
~(p → q) = p ∧ (~q)
```

`역`, `이`, `대우`를 구별하고, 원명제와 항상 동치인 것은 대우뿐임을 실제 문장에 적용해 확인한다.

### 부록 A.6.4 필요·충분 방향의 문장 검사

기호 판정 뒤 반드시 자연어로 역번역한다.

```text
“A는 B의 충분조건” → A이면 B
“A는 B의 필요조건” → B이면 A
“A는 B의 필요충분조건” → A이면 B이고 B이면 A
```

`P ⊆ Q`를 사용했다면 “P의 모든 원소가 Q에 들어간다”라는 문장이 실제 문제의 A/B 방향과 일치하는지 확인한다. 포함관계만 맞고 필요·충분 용어를 거꾸로 쓴 경우는 `LOGIC_DIRECTION_ERROR`로 실패시킨다.

### 부록 A.6.5 대수 조작과 증명 조건

다음 조작은 조건을 함께 기록한다.

- 양변 제곱: 양변의 부호 또는 제곱 후 동치/필요조건 여부
- 양변 나누기: 나누는 식이 0인지와 부호
- 부등식 곱셈·나눗셈: 양수/음수에 따른 방향 반전
- 제곱근 제거: 양변의 비음수 조건
- 완전제곱·AM-GM·Cauchy: 적용 조건과 등호 조건
- 귀류법: 부정한 결론, 도출한 모순, 원래 결론으로 돌아오는 연결

특히 “상한/하한을 구했다”와 “최댓값/최솟값을 달성했다”를 구분한다. 등호 조건이 원래 정의역과 제약식에서 실제 가능한지 확인하지 못하면 극값 결론을 내리지 않는다.

## 부록 A.7 문항 형식·정답·자산의 삼각 검수

답 문자열만 맞는 것으로 PASS하지 않는다. 다음을 각각 확인한다.

```text
발문·보기의 요구 형식
↔ questionType / layoutTag
↔ answer cardinality와 표기
↔ solution에서 설명한 선택지·값
↔ solutionImage의 라벨·관계
```

최소 규칙:

- `answer = "③, ⑤"`이면 발문이 복수정답/있는 대로 고르기 형식인지 확인한다.
- 단일 객관식인데 두 선택지가 참이면 하나를 삭제하지 말고 `SOURCE_REVIEW`로 보류한다.
- 단답형·서술형은 정답의 허용 표현과 해설의 최종 값을 구분한다.
- `solutionImage`는 문제용 `image`와 별도 자산이며, 실제 JS가 읽는 상대경로가 존재해야 한다.
- SVG의 숫자·라벨·화살표 방향은 solution의 계산 결과와 직접 대조한다.
- solutionImage가 없다는 이유만으로 FAIL하지 않는다. 해당 문항의 `visualRequirement`와 사유 코드를 먼저 확인한다.

## 부록 A.8 렌더·자산 dependency 게이트

`solutionImage` 지원 여부(capability)와 해당 시험지의 실제 렌더 성공 여부를 분리해 기록한다. capability만 확인하고 실제 화면을 보지 않은 상태는 최종 PASS가 아니다.

### 부록 A.8.1 Render Matrix

`TARGET_RENDER_EXAMS`는 대상 문항을 포함하는 시험지와 shared material/자산 dependency가 연결된 시험지로 계산한다. 각 시험지마다 다음을 기록한다.

| render target | 필수 확인 |
|---|---|
| `exam` | 발문·보기·문제용 이미지·페이지 분할 |
| `solution` | 해설 줄바꿈·수식·solutionImage·캡션·overflow |
| `answer` | 정답 수·정답 표기·복수정답 표시 |
| `mixed_engine` | 실제 혼합형 경로가 사용될 때만 추가 |

최종 `render PASS`는 파일 존재나 HTML capability가 아니라 실제 렌더 결과의 다음 조건을 모두 뜻한다.

- 빈 화면·누락 문항·중복 문항 없음
- 수식 깨짐, raw escape, clipping, overflow, 라벨 겹침 없음
- solutionImage decode 및 상대경로 정상
- exam/solution/answer 사이의 문항 수와 순서가 일치
- 변경된 시험지와 shared dependency 영향 시험지를 모두 확인

### 부록 A.8.2 SVG 게이트

신규 또는 수정 SVG는 다음을 모두 만족한다.

```text
XML parse PASS
title 존재
desc 존재
viewBox 존재
외부 href/image/script/foreignObject 없음
안전여백·라벨·선·화살표 방향 PASS
answer leak 없음
```

명제용 Venn·수직선·논리화살표는 정확한 수치 축척보다 포함·경계·방향의 의미가 우선이다. 열린점/닫힌점, 여집합 방향, `p → q` 화살표를 실제 해설과 대조한다.

## 부록 A.9 독립 검수와 evidence 무효화

Codex의 자기검수는 `BUILDER_SELF_CHECK`일 뿐 최종 PASS가 아니다. ChatGPT는 최종 Git SHA를 기준으로 다음 순서로 독립 재검한다.

```text
1. manifest coverage와 source scope 확인
2. 문제·정답을 먼저 독립적으로 재풀이
3. solution의 논리 방향·정의역·증명 조건 대조
4. solutionImage의 의미·answer leak·경로 대조
5. Render Matrix와 실제 화면 확인
6. protected field와 index parity 확인
```

다음 변화가 생기면 기존 검수 결과를 자동으로 재사용하지 않는다.

| 변경 | 재검 범위 |
|---|---|
| `solution` 변경 | 해당 문항 A/B 및 관련 시험지 C 렌더 |
| `solutionImage` 또는 SVG 변경 | 해당 문항 B 및 관련 시험지 C 렌더 |
| `content/choices/answer` 변경 | 해당 문항 A/B/C 전부 및 answer/index parity |
| shared material·renderSequence 변경 | dependency closure 전체 |
| manifest·source identity·ruleset·engine·MathJax·font·viewport 변경 | 전체 manifest와 전체 Render Matrix |

각 검수 결과에는 `reviewedArtifactSha`와 입력 hash를 함께 기록한다. SHA가 달라졌는데 이전 PASS를 그대로 인용하면 `STALE_EVIDENCE`로 실패시킨다.

## 부록 A.10 최종 완료 게이트

다음 조건을 모두 만족하기 전에는 `FINAL PASS`를 쓰지 않는다.

```text
MANIFEST_FROZEN = YES
FORWARD_REVERSE_SCOPE_MISMATCH = 0
UNRESOLVED_SOURCE_REVIEW = 0
UNAUTHORIZED_FIELD_CHANGE = 0
TRIAGE_COVERAGE = 100%
```

`WARN`은 문장 다듬기처럼 수학·정답·범위·렌더에 영향을 주지 않는 경우에만 허용한다. 정의역, 필요·충분 방향, 반례, 부정, 귀류법, 답 형식, 자산 경로, 렌더 결함은 `WARN`으로 낮추지 않고 `FAIL` 또는 `SOURCE_REVIEW`로 유지한다.

# 28. 운영 원칙 최종 선언

이번 명제 단원 업그레이드의 기본 원칙은 다음 한 문장으로 요약한다.

> **정답을 아는 사람의 해설이 아니라, 명제를 처음 어려워하는 학생이 논리의 방향을 따라갈 수 있는 해설을 만든다.**
