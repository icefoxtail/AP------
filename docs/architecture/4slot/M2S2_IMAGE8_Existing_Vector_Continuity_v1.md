# M2-S2 IMAGE8 existing-vector continuity v1

## Scope and authority

This opt-in successor covers the fixed, already published IMAGE_REPAIR8 profile only: E017 ordinals 4, 5, 9, 18, 20, 23 and E023 ordinals 6, 10. It transports the complete existing E017 23-row and E023 24-row compact vectors. It grants no mathematical, slot, native metadata, difficulty or source-edit approval.

`tools/4slot/m2s2-image8-pins.json` is production code, not a user-supplied configuration. It pins both complete literal prior compacts, their prior source snapshots, the eight original and accepted asset byte identities, the two original static records, the immutable official student-screen evidence and independent visual closeout, and the selected 47 generated metadata/identity projections. Changing those pins is a code change requiring separate review; a carrier cannot select another source, image, prior, observer, viewport or authority.

The literal prior for E017 is the published `ede308fb38af5879aea99c115bafd2ee35df4f57` compact with its issued-metadata successor. The literal prior for E023 is the published `b76eaf3a1ed8a1ade1dae6185e7b7c044455ef66` compact with its imported native amendment and issued-metadata successor. Each source validation must fully replay its corresponding prior. That replay preserves the original native review, ROOT acceptance, full vectors, candidates, dictionary validation, negative observations, repair/amendment decisions, issued requests and issued receipts. Historical replay is evidence, never an ordinary live-validation bypass.

## Compact and carrier

The only compact change is an added `evidence.currentM2Image8Continuity` object with one `carrier` reference containing `commit`, `path`, `sha256`. Every other compact byte value, including the existing `sourceGitBlobSha`, items, headers, reviewer and candidates, must equal the literal prior. The source blob is not silently rebound.

The carrier basename is `m2-image8-existing-vector-continuity.json`. Its closed fields are:

- `schemaVersion`: `m2-s2-image8-existing-vector-continuity-v1`.
- `scope`: `EXACT_IMAGE8_POINTERS_KEEP_FULL_LITERAL_METADATA_SUCCESSOR`.
- `transportAuthor`, `examId`, `sourceArchiveFile`, `expectedQuestionCount`.
- `priorValidatedCompactRef` and `sourceRef`, each FULL4 (`commit`, `path`, `gitBlobSha1`, `sha256`).
- `staticRefs` containing the exact two original Git references and `staticCopyRefs` containing the exact durable-copy references. Each copy must equal its original immutable bytes; the originals retain their original decision, author, date and PENDING UI status.
- `uiPublicationCommit` and the complete `uiEvidenceRefs` set of 25 original technical, capture, independent observation and closeout files.
- `historicalEvidenceRefs`, exactly the complete sorted live-evidence set returned by the private prior replay. It may not be shortened to the selected image rows.
- `rows`, the complete 23- or 24-row UID/ordinal/question-number, prior/current whole-object, student-payload and compact-item hash partition.
- `currentAssets`, the complete sorted asset set of the current full source.
- `fullItemsSha256` and the exact pinned `generatedForwardPolicy`.
- Zero-valued `newSemanticApprovals`, `newDifficultyApprovals`, `newMathQa`, `newSlotValues`, `sourceWrites`, `assetWrites`, `nativeMetadataWrites`.

Current source, assets, carrier, static copies and all live historical/UI evidence require regular files, Git mode 100644, the declared OID/raw SHA, immutable ancestry where specified, current HEAD equality and actual live-byte equality. A valid immutable reference does not excuse a missing or different current file. The original old image files remain exact immutable evidence at the prior and current HEAD even after the new image pointer is used.

## Question and vector preservation

For each selected image row, the only whole-question delta is the `image` string from the pinned old path to the pinned new path. The current asset must equal the accepted asset at its pinned publication commit. No caption, content, choice, answer, solution, metadata, geometry or label is inferred or edited by this contract. The other 39 whole questions are exact. Existing full vectors and fallback candidates remain exact for all 47 rows.

The runtime builder performs the full file validation before cache reuse. Only the exact eight UID/source-ordinal joins receive `FIXED_IMAGE8_EXISTING_VECTOR_CONTINUITY`; other rows keep the ordinary freshness rules. This successor cannot mix another renderer authority into a selected row. The original hold, dictionary, UID uniqueness, source-quality and consumer checks remain active.

## Original screen evidence and generated forward boundary

The original official UI run, all 18 selected PNGs covering eight questions at two viewports, the separate independent screen observation and the 207-entry dependency fence remain immutable. The original technical report still says visual review was pending; the independent closeout supplies the subsequent screen review without rewriting that history. The original static records also retain `actualUi: PENDING`. No new browser execution or mathematical approval is claimed.

The explicit IMAGE_REPAIR8 profile requires student-screen inspection. Its published contract and checker do not add a print/PDF gate. Actual print validation remains NOT_RUN; this does not waive any unrelated printing requirement.

Of the original 207 dependency paths, 205 renderer/source inputs retain exact current HEAD mode/OID. Any materialized live copy must be exact; current source, assets and proofs are mandatory live inputs. The two generated paths `archive/data/question_metadata.json` and `archive/data/question_identity_map.json` have a separate closed forward boundary. Treating their original OIDs as permanent current OIDs would incorrectly reject a later official registration commit.

Both the HEAD and live versions of those two generated files are parsed independently, one record at a time. Their full raw bytes are hashed freshly. The selected 47 UIDs must retain unique exact source/ordinal/question-number tuples and all original metadata meaning fields. Identity changes are limited to the current source fingerprint. Metadata changes are limited to `approvalEvidence`, `contentFingerprint`, `metadataRevision`, and `sourceFingerprint`; all original evidence entries must remain. New fingerprints must be the computed exact current source values. Arbitrary generated semantic changes are not accepted, even if another request claims to approve them.

A changed selected row must equal an exact REGISTERED v2 receipt row, with the full declared receipt denominator and unique metadata/identity rows. The receipt must bind the current source raw/blob and the unchanged source tuple. For a HEAD generated change, the receipt must exist at HEAD. For a live change, a committed receipt must remain byte-exact; if no receipt is committed yet, HEAD must contain the complete exact pending request. Its stable request digest, approval, registry-zero declaration, source, expected denominator, all selected UIDs, before values and after values must match the receipt and HEAD/live records. A live-only receipt without that immutable request cannot establish provenance. These rules verify cursor continuity; they do not replace any official registrar, NativeMeta, AutoMeta or Consumer approval gate.

The pinned `question-meta.js` implementation writes metadata fields and diagnostic metadata references only. It does not replace the student `content`, `image`, `choices`, `answer` or `solution` fields. Its exact renderer-input bytes remain among the 205 fixed dependencies. The 47 metadata meaning projections are independently fixed rather than relying solely on this code observation.

Only the two declared generated paths have a 128 MiB bounded Git read allowance, checked against declared object size, actual raw length and blob identity. Other reads keep the existing bounded allowance. No global timeout or Git-buffer relaxation is introduced. No successful approval result is cached.

## Deletion resistance and historical adapters

The carrier obligation is discovered from actual HEAD and its full history, including merge parents. Discovery is pass-local and checks HEAD again on every call. It does not scan unrelated branches. Once issued, removing the marker, carrier, historical proof, native copy, static copy, negative evidence or current UI proof cannot erase the obligation. Committing deletion and restoring only a live file also fails. Warm calls, a fresh reader and a fresh process use the same obligation.

The two prior metadata modules retain their original ordinary `validateFile` paths. Their additional `validateHistoricalFile` API accepts a literal FULL4 compact snapshot, requires ancestry and regular Git bytes, and privately supplies that immutable snapshot to the same complete validators. It rejects an IMAGE8 successor as a prior. It returns every required live historical proof to the new caller, which rechecks the entire set against current HEAD and disk. It exposes no alternate reader, skip flag or ordinary approval cache.
