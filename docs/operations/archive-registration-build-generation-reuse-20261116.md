# Reuse identical generated registration files within one preparation

The timed-out main writer run `43861600184` regenerated after protected main changes. Its two completed retries spent 764,347/757,331 ms in the reviewed lane, 440,288/507,306 ms in AutoMeta, and 231,677/237,011 ms in the shared lane. The shared lane's start and end input/output digests were identical in both completed retries. These are historical measurements; they do not prove a future cache hit or a new successful main registration.

`archive-registration-build-db.mjs` is an optional generation checkpoint for the single writer. The writer creates a fresh random preparation identifier and an external cache directory for each preparation, including every race retry. Ordinary callers without these variables always run the original `python archive/build_db.py` command. This does not change retry limits, timeouts, the main branch lock, or the push verification policy.

Before reusing generated bytes, the wrapper requires the same preparation, HEAD, complete shared-lane input and output policy, raw current file hashes, tracked dependency inventory, immutable index entries, all immutable files outside the writer output allowlist, Git references/configuration, environment, executable identities, and wrapper code. It uses `nativeLanes` as the existing dependency contract and does not remove an input. New or modified review documents outside the ordinary shared input patterns are included. Raw SHA-256 checks prevent Git filters or CRLF normalization from hiding worktree changes. Missing, malformed, changed, ignored, symlinked, or otherwise uncertain dependencies cause ordinary generation.

Only a zero-exit, unsignalled build with unchanged read set and immutable execution context creates a checkpoint. Some generated files are also inputs: if a successful generation changes those inputs, it cannot certify generation from the resulting state. The next invocation still runs the original producer so the existing fixed-point path can converge. Synthetic two-pass and continuously changing producers exercise this boundary. The wrapper invalidates the previous checkpoint before executing a producer. The cache is private to this preparation and is never accepted as mathematical approval, a Native receipt, or a consumer verdict. It does not reapply old outputs to a newer main commit.

The complete `nativeLanes` input/output/scoped-input/parameter policy is bound as code and structured metadata. Current bytes use its existing shared generator read set and output set, plus all immutable files outside the union of writer outputs. A writer control output outside that generator read set, such as AutoMeta's last-verification record, remains governed by the existing lane and final-consumer checks. It is not promoted to a cached validation. Different lane-specific environment values or newly staged dependency paths may conservatively prevent reuse; a historical unchanged shared lane does not guarantee a hit.

Every reuse runs these existing official read-only checks again, in order:

1. `build-basic-scope-parent-links.mjs --check`
2. `verify-archive-registration.mjs`
3. `build-archive2-catalog.mjs --check`
4. `refresh-runtime-source-readiness.mjs --check`

Their exits must be zero without signals, and a second snapshot must prove the checks left all bound inputs and outputs unchanged. A refused reuse is recorded before falling back to the ordinary generator. Existing compile/materialize commands, request tests, projection checks, consumer checks, Native replay, final lane verification, and post-push checks remain in their callers.

The cache records only hashes, counts, command names, exits, timings, and the exact HEAD. It does not copy student source text or whole metadata records. `GENERATION_REUSED` is a generation event, not a release PASS. Actual savings and final main registration must be measured in the subsequent ordinary writer run.
