# 예약 작업 공통 프롬프트 — 실행할 때 과목 변수만 바인딩

다음 문구는 `course`만 바꿔 4개의 매시간 독립 예약에 사용한다. 소스/해설/그림의 실제 작업을 수행할 수 없으면 불완전한 성공 보고 대신 `NOT_RUN`·`SAVE_BLOCKED`를 기록한다.

```text
icefoxtail/AP------ 저장소의 고등 학생용 기존 해설 업그레이드 라인이다. 담당 과목은 <COURSE_LABEL>, course key는 <COURSE_KEY>이다. 한 번 실행할 때 해당 과목의 현재 우선순위 시험 구분 **전체 시험지 인벤토리**를 수집하고, 시험지 수의 상한 없이 가능한 만큼 **여러 시험지·전 문항 해설을 빠르게 스캔**하여 복수의 개선 대상을 찾은 뒤, **여러 학생용 수정 해설 전체를 배치로 MD에 작성·저장**한다. JS 직접 수정은 하지 않는다. **기출 → 유사 → 유형 → 교과서 → 문제집** 순서를 절대 지키고, 기출과 학기별 유사시험지는 **2학기 기말 전 연도(최신→과거) → 1학기 중간 전 연도(최신→과거) → 1학기 기말 전 연도(최신→과거) → 2학기 중간 전 연도(최신→과거)** 순으로 고른다. 연도별로 네 시험을 묶어 처리하지 않는다. 기출이 남아 있으면 다른 종류를 시작하지 않는다. 중등은 건드리지 않는다.

**빈 시험 구분 자동 폴백은 필수다.** 기출 2학기 기말을 모든 연도·하위 경로·해당 과목 표기(대수/수학Ⅰ, 미적분Ⅰ/수학Ⅱ 등)로 검색한 후 미처리 시험지가 전혀 없으면 **그 실행에서 바로 1학기 중간을 검색**하라. 없으면 1학기 기말→2학기 중간으로 이동하라. 네 시험 구분이 모두 비었거나 완료되었을 때만 유사로, 이후 유형→교과서→문제집으로 이동한다. 파일 하나/연도 하나/폴더 하나의 없음은 전체 없음이 아니고, EMPTY_BUCKET이나 SCREENED_PRELIMINARY는 종료·SAVE_BLOCKED 조건이 아니다. 기존 '1~3개 시험지 스캔' 제한은 폐지되었다. 빈 구분 탐색도 인벤토리 수집도 스캔 완료로 세지 마라. 실제 스캔 대상이 나타날 때까지 다음 버킷을 탐색하고, 검색한 버킷과 다음 대상/진행 커서를 MD에 남겨 다음 실행에서 이어가라.

작업 시작 시 Git main에 하네스가 있으면 main, 병합 전이라면 work/solution-upgrade-reservation-harness-20261121 브랜치의 docs/operations/solution-upgrade-reservations/HARNESS_CURRENT.md와 docs-manifest.json, tools/solution-upgrade-reservation/preflight.mjs의 실제 본문을 먼저 읽고, 하네스에 지정된 필독 문서 원문 전체와 Golden/Negative 샘플을 읽고 영수증을 남겨라. 링크만 확인하거나 예전 대화 요약으로 대체하지 마라. 하네스 파일이 없거나 필수 문서를 읽을 수 없으면 임의의 일반 규칙으로 작업하지 말고 정확한 장애를 보고하라.

docs/operations/solution-upgrade-reservations/BOARD_SOLUTION_SAMPLES_CURRENT.md의 학생용 판서 샘플 5개를 전부 실제 읽어라. 한글 문장을 늘리는 것이 친절함이 아니다. 필요한 발상·조건만 짧게 설명하고, 수학의 결정 단계는 실제 등호와 계산식으로 보여 주어라. 이 샘플은 Golden/Negative 검수의 대체물이 아니며 문항에 그대로 복사하지 마라.

핵심 식 전개는 '정리하면/계산하면/대입하면' 한 마디로 넘기지 마라. 학생이 멈추는 전환에서는 괄호 전개→항 이동→인수분해/약분→나누는 수가 0이 아님·부호/범위 조건→결론을 실제 수식의 여러 줄로 보여 줘라. 예: p(10-p)=q(10-q)에서 p+q=10으로 뛰지 말고 10p-p²=10q-q², 10(p-q)=(p-q)(p+q), p≠q 확인 후 p+q=10을 차례로 적는다. 왜 처음 식을 세웠는지도 쉬운 문장으로 설명하라. 학생이 따라갈 수 있는 필수 단계를 생략한 '짧은 해설'은 업그레이드가 아니며, 불필요한 장문도 피하라. 전후 비교에는 학생이 멈추는 구체적 식과 보강한 전개를 남겨라.

**실제 결과물은 후보 목록이 아닌 복수 MD의 새 학생용 풀이 본문이다.** 우선 전체 해당 과목 시험지의 경로/연도/시험 구분/원본 SHA 인벤토리를 수집하고, 여러 시험지의 모든 문항 해설을 가능한 한 폭넓게 스캔하라. 검증 가능한 결함 문항을 큐에 모아 한 번에 여러 문제를 독립 검산·개선하라. **한 문제를 작성했다고 그 시간의 작업을 종료하지 마라.** 시간이 부족하면 소스별 스캔 상태와 미처리 후보를 SCAN_LEDGER.md에 남겨 다음 예약에서 우선 이어가라. 먼저 담당 브랜치의 docs/operations/solution-upgrade-reservations/staged/과목키/를 읽어 이전 MD를 재개한다. 원본 JS의 문항·답·기존 solution과 정확한 sourceIdentityKey/blob SHA를 대조한다. 증거 있는 결함만 대상으로 수학을 독립 검산하고 등호 중심의 구체적 개선 해설을 학생용으로 완성한다. 기존 해설이 충분하면 예비 선별 사실만 MD에 기록하고 같은 순서의 다음 시험지를 확인한다.

각 개선 문항 MD에 원본 경로/blob/sourceIdentityKey/qid/answer, 기존 해설 결함, **수식과 계산이 모두 포함된 완성된 제안 solution**, 미완료 검증 게이트, REVIEW_REQUIRED를 적어 담당 브랜치에 GitHub 파일 생성/수정으로 **실제로 커밋하고 readback**한다. JS, 운영 main, SVG는 수정하지 않는다. 20~30초 만에 후보만 적고 멈추지 말고 가능한 시간 동안 실제 풀이를 작성하라. 작업을 다 끝내지 못하면 진행 상태를 MD에 남겨 다음 시간에 이어가라. 최종 Golden/Negative·독립검산·원본/그림·JS/렌더 QA는 나중에 MD를 JS로 옮기기 전에 전부 수행한다. MD 단계에서 검증을 못 했으면 NOT_RUN으로 표시하되 MD 저장을 막을 이유로 삼지 마라. 단, 원시 조건이 불확실한 경우 억지 해설을 작성하지 말고 HOLD하라.


**시험지당 1건에서 멈추지 마라.** 시험지 하나를 골랐으면 1번부터 마지막 문항까지 문제/기존 solution/정답을 실제로 판독하고 문항별 KEEP/UPGRADE/HOLD/UNREAD를 장부에 남겨라. 결함을 하나 찾은 시점에 스캔을 끝내거나 다음 시험지로 넘어가지 마라. 같은 시험지의 **개선 대상 전부를 선별**하고, 가능한 한 **같은 배치 MD에 여러 qid의 완성 풀이**를 작성하라. UPGRADE 후보가 남았으면 PAPER_DRAFT_COMPLETE로 표시하지 말고 DRAFT_IN_PROGRESS로 다음 실행에서 그 시험지부터 이어가라. PAPER_SCAN_COMPLETE는 전체 문항의 개별 판정이 있을 때만 허용한다. 한 시험지에 후보 1개뿐이라는 보고는 전 문항별 판정 근거가 있을 때만 가능하다. 개수만 채우려고 좋은 해설을 고치지는 마라. 보고에는 시험지별 총문항/판정문항/UPGRADE/완성 MD/남은 qid를 명시하라.

SVG/그래프가 학생 이해에 필요하면 해설을 독립 검산한 후 하네스의 조건부 SVG 문서와 AUTHOR_GUIDE 및 형태별 guide/Golden을 실제 읽고 엔진용 item/plan/publish 초안을 작성한다. SVG 파일은 직접 생성하지 말고 엔진 라인에 인계한다. 문서와 형식 검증 없이 plan.json이라고 주장하지 않는다. 필수 그림의 실제 렌더·검수가 끝나기 전에는 해당 시각 게이트를 PASS로 닫지 않는다.

MD에 **여러 시험지·여러 문항의 실제 개선 풀이**와 필요 검증을 기록해 자기 과목 작업 브랜치에 커밋하라. SCAN_LEDGER.md에는 전체 시험지 인벤토리, SCANNED/PENDING/CANDIDATES/DRAFTED 상태, 원본 SHA와 재개 커서를 기록하라. 결과 보고에는 인벤토리 시험지 수/실제 전 문항 스캔 시험지 수/검토 문항 수/후보 수/완성 풀이 수/커밋 수/남은 잔량을 구분하여 적어라. 후보가 여러 개인데 1건만 커밋되었다면 완료라고 말하지 말고 제약과 남은 후보를 밝히고 다음 예약을 이어라. 추측으로 최종 PASS 또는 출고를 주장하지 말고, 작업 결과로 실제 저장한 MD·qid·커밋과 진행 상태를 보고하라. 이후 실행이 중복 작업하지 않도록 이어받을 정보를 남겨라.
```

## 실행 확인

1. 위 Git 문서가 실제 원격에 존재하는지 URL readback 한다.
2. 예약별 시간대 `Asia/Seoul`, `FREQ=HOURLY`, 분 단위를 확인한다.
3. 첫 실행은 정본 읽기, 수정 필드 차이, Git 쓰기 및 실제 검증 증거를 중심으로 점검한다.
4. Git 쓰기 경로가 실제로 불가하면 해당 라인을 무의미하게 반복 실행하지 말고 운영자에게 장애를 알린다.
