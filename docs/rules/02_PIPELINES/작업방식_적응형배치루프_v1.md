# 작업 방식 — 적응형 배치 루프 v1

작성 목적: 기존의 고정 5문항 루프를 시각자료·해설·독립검수 작업에 맞는 위험도 기반 배치로 확장한다.

적용 범위:

- 기존 JS 해설 업그레이드
- 집합·명제 Logic Visual qualification
- SVG/그래프/solutionImage 생성·수정·검수
- 문항별 V1/V2/V3 독립 검수와 C denominator 동결

기존 `작업방식_5문항배치루프_필수.md`는 과거 고정 루프의 호환 문서로 보존한다. 본 문서가 현재 배치 크기·중복·canonical 판정에 대한 우선 기준이다.

## 1. 핵심 원칙

전체 문항을 무조건 5개씩 자르지 않는다. 문항의 위험도, visual type, fact schema, 수정 여부가 비슷한 문항을 묶고, 배치마다 독립 검수와 렌더 게이트를 닫는다.

배치 크기는 품질을 낮추기 위한 압축 수단이 아니라 반복되는 운영 비용을 줄이기 위한 단위다. 배치가 커져도 문항별 evidence와 UID 단위 판정은 분리해 보존한다.

## 2. 권장 배치 크기

| 위험도·작업 유형 | 권장 크기 | 기본 처리 |
|---|---:|---|
| 새 SVG, 그래프, 3집합 Venn, 복잡한 경우표, source conflict | 3~5 | 고위험 calibration loop |
| 일반 `REBUILD_EXISTING` | 4~6 | 문항별 decisive-step parity를 우선 |
| `KEEP_EXISTING`, 동일 fact schema | 8~12 | 기본 운영 batch |
| 단순 `NO_VISUAL` 또는 동일 static rule | 15~20 | metadata/static gate 중심 |
| 최종 전수 audit | 남은 전체 | UID·metadata·중복·coverage 전수 확인 |

기본 배치 크기는 8이다. 다음 조건이면 자동으로 배치를 줄인다.

- 고위험 문항이 3개 이상 포함됨
- visual type이 3종 이상 섞임
- fact schema가 2종 이상 섞이고 semantic projection이 다름
- source answer/solution conflict가 있음
- 기존 batch와 UID가 중복됨
- 이전 revision이 unresolved 또는 BLOCKED임

다음 조건이면 배치를 늘릴 수 있다.

- 모든 문항이 같은 visual type 또는 같은 `NO_VISUAL` 규칙을 사용함
- source/answer/solution conflict가 없음
- V1/V2 input visibility가 동일한 batch contract로 고정됨
- 문항별 fact schema와 canonicalization spec이 이미 검증됨
- required render와 exempt static gate를 자동화할 수 있음

## 3. 현재 canonical visual decision enum

최종 보고서와 배치 manifest는 아래 네 값만 사용한다.

```text
NO_VISUAL
KEEP_EXISTING
REBUILD_EXISTING
ADD_NEW_VISUAL
```

다음 구분은 별도 필드로 기록한다.

```text
visualRequirement: VISUAL_REQUIRED | VISUAL_OPTIONAL | VISUAL_EXEMPT
visualAction: NONE | KEEP | REBUILD | ADD | REMOVE_INVALID_VISUAL
```

기존 보고서의 `VISUAL_EXEMPT`, `VISUAL_REQUIRED`, `ADD`, `REBUILD_EXISTING`은 migration 단계에서만 canonical enum으로 매핑한다. 최종 canonical registry에 legacy 값이 남아 있으면 FAIL이다.

## 4. Batch Manifest 계약

모든 새 배치는 실행 전에 다음 manifest를 만든다.

```json
{
  "batchId": "2022-set-pilot-next-01",
  "batchNo": 12,
  "revision": 1,
  "supersedes": null,
  "isCanonical": true,
  "riskProfile": "STANDARD_KEEP_EXISTING",
  "plannedSize": 8,
  "questionUids": [],
  "visualDecisionPlan": {
    "NO_VISUAL": 0,
    "KEEP_EXISTING": 8,
    "REBUILD_EXISTING": 0,
    "ADD_NEW_VISUAL": 0
  },
  "visualTypes": [],
  "factSchemaVersions": ["LOGIC_VISUAL_FACT_v1"],
  "appliedRuleRefs": [],
  "inventorySha": null,
  "manifestSha": null
}
```

manifest validation은 다음을 fail-closed로 검사한다.

- `questionUids`가 비어 있지 않음
- 같은 UID가 한 manifest 안에 두 번 나오지 않음
- active canonical batch들 사이에 UID가 중복되지 않음
- `plannedSize`와 UID 수가 일치함
- `plannedSize`가 riskProfile 권장 범위를 벗어나면 `sizeException`과 승인 evidence가 있음
- `visualDecisionPlan` 합계가 UID 수와 일치함
- `isCanonical:true`인 revision은 UID별 하나만 존재함
- 이전 revision을 대체하면 `supersedes`가 정확히 지정됨
- inventory UID가 아닌 문항을 포함하지 않음
- 적용 rule ref, inventory SHA, manifest SHA가 모두 존재함

## 5. UID 중복과 revision 규칙

문항 UID는 다음을 canonical identity로 사용한다.

```text
sourceJsPath|examId|qid
```

같은 UID를 여러 배치에서 다시 처리해야 하는 경우 새 batch 번호를 무작정 만들지 않는다.

```text
same UID + same evidence = 중복 실행 FAIL
same UID + changed artifact/source = revision 생성
revision 생성 = supersedes 필수
canonical revision = UID별 정확히 하나
```

최종 집계는 파일명에 `final`이 들어갔는지가 아니라 canonical registry의 `isCanonical`과 revision으로 결정한다.

## 6. 배치 LOOP

### 6.1 Preflight

1. 현재 rule-pack path/version/byte count/SHA를 evidence에 기록한다.
2. inventory SHA와 UID set을 잠근다.
3. batch manifest를 validate한다.
4. active canonical registry에 UID 중복이 없는지 확인한다.
5. source/answer/solution/image의 현재 SHA를 기록한다.

preflight 하나라도 실패하면 문항 수정과 SVG 생성을 시작하지 않는다.

### 6.2 V1 Source-only

V1은 source-only bundle만 본다.

- content
- choices
- source answer는 기본적으로 숨긴다. 정답은 source answer가 아니라 content/choices와 독립 검산으로 판단한다.
- 별도 수학 검산의 A1 blind solve를 먼저 동결한 뒤 A2에서 source answer를 reference로 대조하며, 그 결과는 V1 expected visual fact evidence와 분리한다.
- problem image dependency 정보

solutionImage, solutionImageAlt, solutionImageCaption, 기존 verdict, V2 관찰 fact는 숨긴다.

V1 answer visibility conflict를 방지하기 위해 다음을 고정한다.

```text
V1 source-only bundle = content + choices + problem dependency
V1 hidden by default = answer + solution + solutionImage + alt/caption + previous verdict
A1 blind math → freeze → A2 answer comparison = separate role/evidence; V1 verdict를 대신하지 않음
```

V1은 문항별로 다음을 확정한다.

- math fact
- visual necessity
- expected visual type
- decisive step
- expected logical fact

### 6.3 V2 Artifact-only

V2는 artifact-only bundle, 실제 렌더, accessibility tree만 본다.

V1 expected fact, source solution, answer, alt/caption, previous verdict는 숨긴다.

V2는 `LOGIC_VISUAL_FACT_v1` observed fact를 만들고 extraction method와 input SHA를 기록한다.

### 6.4 V3 parity

V3는 frozen V1/V2 evidence를 typed canonicalization으로 비교한다.

문자열이 존재한다는 이유만으로 parity PASS를 선언하지 않는다. semantic fact, decisive step, completeness, medium fit, alt/caption parity를 각각 판정한다.

### 6.5 C denominator

다음 변화가 있으면 C denominator를 즉시 STALE로 만든다.

- solutionImage 추가·삭제·교체
- SVG 또는 PNG 내용 변경
- solutionImageAlt/caption 변경
- content/choices/answer/solution 변경
- visual decision 변경
- fact schema/canonicalization/projection spec 변경
- extractor/verifier/rule-pack 변경

STALE 이후에는 UID set과 artifact SHA를 다시 freeze해야 한다.

### 6.6 Item gate

`NO_VISUAL`은 다음을 모두 확인한다.

- solutionImage 없음
- solutionImageAlt 없음
- solutionImageCaption 없음
- 불필요한 `[시각자료 읽기]` 없음
- 불필요한 `도형`/`그래프` tag 없음

required visual은 다음을 모두 확인한다.

- artifact 존재
- viewBox/title/desc 존재
- script/foreignObject 금지
- 문항 고유 사실 존재
- expected/observed semantic parity PASS
- alt/caption 문항 고유성 PASS
- exact/structural duplicate gate PASS

### 6.7 Real render

required visual은 최소 다음 viewport에서 확인한다.

- desktop: 1280px 이상
- mobile: 390px 이상

NO_VISUAL 문항은 렌더하지 않는 대신 exempt static gate를 PASS해야 한다.

### 6.8 Canonical close

배치 종료 조건:

- pending adjudication 0
- unresolved conflict 0
- required item FAIL/BLOCKED 0
- exempt static FAIL 0
- required render PASS
- C denominator FROZEN and not stale
- canonical registry update PASS

## 7. 독립성 contract

V1/V2/V3는 같은 batch 안에서 여러 문항을 처리할 수 있지만 입력 visibility는 고정한다.

각 evidence에 다음을 기록한다.

```text
reviewerRole
reviewerId
reviewerModelOrAgent
reviewSessionId
inputVisibilityProfile
inputBundleSha
firstPassEvidenceSha
```

V1과 V2가 서로의 first-pass 결과를 본 경우 independent PASS가 아니다.

## 8. Legacy migration

기존 5문항 배치 결과를 새 registry에 편입할 때는 다음을 별도 report로 남긴다.

- legacy report file list
- UID 중복 목록
- conflicting decision 목록
- canonical selection rule
- 선택되지 않은 report의 superseded 상태
- 최종 unique UID set SHA

legacy migration에서 conflict가 자동으로 사라지면 안 된다. conflict는 기록한 뒤 canonical adjudication으로 해결해야 한다.

## 9. 권장 운영값

```text
calibration/high-risk: 3~5
standard default: 8
stable KEEP_EXISTING: 8~12
NO_VISUAL-only: 15~20
final audit: entire remaining scope
```

배치 크기를 늘리는 목적은 문항당 검수 수준을 낮추는 것이 아니다. 반복되는 bundle/denominator/report 작업을 줄이되, UID별 evidence와 gate는 그대로 유지하는 것이다.
