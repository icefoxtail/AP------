# 토큰 효율 규칙 (상세)

> 루트 `AGENTS.md`의 "토큰 효율" 규칙을 자세히 적은 문서다. 2026-10 Archive 2.0 개선 작업에서 실제로 토큰이 많이 든 곳을 근거로 만들었다.
> 정해진 품질 절차(테스트, 런타임 검사, 시험지 CREATE·R1·R2·R3 검수 범위)는 이 문서로 줄이지 않는다.

## 1. 추가 측정은 표본으로

- 기본은 대표 표본 몇 개로 확인한다. 전수 측정은 사용자가 요청했거나, 개수 자체가 결과물(예: 누락 목록)일 때만 한다.
- 이유: 인쇄 잘림 수정 한 단계가 전 학년 출력물을 몇 시간 동안 측정했다. 출력 시점의 잘림 검사가 잘린 문제지를 이미 오류로 막고 있었다.

## 2. 무거운 검사는 한 번

| 검사 | 소요 (4코어 작업 기계 실측) | 쓰는 시점 |
| --- | --- | --- |
| `node tools/run-tests.js` (전체 테스트) | 약 9~10분 | 병합 직전 1회 |
| `node tools/check-archive2-runtime.cjs` | 약 3분 | 단계당 1회 |
| Pages 배포 워크플로 | 작업기 배포 대기 최대 14분 포함 | 결과는 Actions에서 확인 |

- 런타임 검사는 작업 폴더의 `archive/data/svg-accessibility-index.js`와 `archive/data/archive2-catalog.json`을 다시 만든다. 의도한 변경이 아니면 `git checkout -- <경로>`로 되돌린다.
- main과 비교할 때는 실패한 테스트만 main에서 다시 돌린다. 전체 테스트를 main에서 한 번 더 돌리지 않는다.
- 이유: 구현·검토·수정 때마다 전체 테스트와 런타임 검사를 다시 돌렸고, main 비교를 위해 전체 테스트를 한 번 더 돌렸다.

## 3. 검토는 위험에 맞춰

- 코드 검토자는 바뀐 부분을 읽고 관련 테스트만 다시 돌린다. 구현자가 한 측정을 반복하지 않는다.
- 문서 작업과, 이미 검토를 마친 변경의 단순 병합은 별도 검토를 생략한다. CI와 배포 관문이 마지막 확인을 맡는다.

## 4. 한 번에 하나

- 무거운 작업(전체 테스트, 런타임 검사, Chrome 측정)은 한 번에 하나만 돌린다.
- 이유: 두 작업을 같이 돌리자 시간 기준 테스트(조합 성능, 런타임 검사의 하위 프로세스 시간 초과)가 흔들려 재실행이 늘었다.

## 5. main 합치기와 생성 파일

- main은 PR 직전에 한 번만 합친다.
- 생성 파일(목록·DB·색인·SVG 접근성 색인)이 충돌하면 손으로 고치지 않는다. main 쪽을 받은 뒤 생성기를 한 번만 다시 돌린다.
- 이유: main이 자주 바뀌어 생성 파일이 반복해서 충돌했고, 재생성을 여러 번 다시 했다.

## 6. 테스트는 결함 조건으로

- 계속 늘어나는 운영 데이터(시험지·문항·이미지 수)의 정확한 개수를 테스트에 고정하지 않는다. 누락 0, 중복 0, 깨진 참조 0 같은 결함 조건을 검사한다.
- 이유: 시험지가 늘 때마다 테스트의 고정 숫자를 고치는 수정이 반복됐다.

## 7. 긴 명령은 끝까지 기다린다

- 긴 명령은 백그라운드로 돌리고 완료 표식을 기다린다. 예: `node tools/run-tests.js > run.log 2>&1; echo "RC=$?" >> run.log`를 백그라운드로 실행한 뒤 `until grep -q '^RC=' run.log; do sleep 15; done`.
- 도중에 멈추고 PARTIAL로 끝내지 않는다.
- 이유: 긴 명령을 기다리지 않고 멈춘 작업자를 다시 띄우는 비용이 들었다.

## 8. 작업 지시서

- 완료 증거를 최소로 적는다(예: "알려진 잘림 3건 해결 + 화면 확인 1회"). "전체 측정"처럼 끝이 열린 지시는 쓰지 않는다.
- 기계적인 작업(병합, 재생성, 문서)은 추론 수준을 낮게 두고, 복잡한 로직만 높게 둔다.

## 9. 총괄(ROOT)의 진행 확인과 보고

- 진행 확인은 상태 요약과 마지막 몇 줄만 본다. 큰 상태 파일·로그·대화 기록을 통째로 출력하지 않는다.
- 사용자 보고는 짧게 한다. 결정이 필요한 것은 모아서 한 번에 묻는다.

## 10. 문서 구조 원칙 (apps-in-toss-harness 구조 참고)

- 루트 `AGENTS.md`는 짧은 안내판이고, 영역 문서(`docs/agents/`)는 그 작업을 할 때만 읽는다.
- 현재 진행 상황은 문서에 쌓지 않는다. PR·Actions·이슈에서 확인한다.
- 규칙에는 이유를 한 줄 붙이고, 사고에서 얻은 교훈은 원칙 한 단락으로 남긴다.
- 문서 구조는 검사기로 지킨다(`tests/agents-md-budget.test.js`). 원인보다 결과(실제로 무엇이 읽히는지)를 직접 재는 검사가 더 튼튼하다.

## 운영 교훈 (2026-10)

- Pages 등록 커밋이 main 경쟁에서 지면 실패가 아니라 경고다. 다음 main의 배포가 등록을 이어받는다.
- 검증 실패는 학생 사이트 배포만 막는다. 병합은 CI와 따로 진행한다.
- 작업기(APMS Worker)는 학생 사이트보다 먼저 배포된다(배포 순서 관문).
