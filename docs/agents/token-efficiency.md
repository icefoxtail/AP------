# 토큰 효율 규칙 (상세)

> 루트 `AGENTS.md`의 "토큰 효율" 규칙을 자세히 적은 문서다. 2026-10 Archive 2.0 개선 작업에서 실제로 토큰이 많이 든 곳을 근거로 만들었다.
> 정해진 품질 절차(테스트, 런타임 검사, 시험지 CREATE·R1·R2·R3 검수 범위)는 이 문서로 줄이지 않는다.

## 1. 추가 측정은 표본으로

- 기본은 대표 표본 몇 개로 확인한다. 전수 측정은 사용자가 요청했거나, 개수 자체가 결과물(예: 누락 목록)일 때만 한다.
- 이유: 인쇄 잘림 수정 한 단계가 전 학년 출력물을 몇 시간 동안 측정했다. 출력 시점의 잘림 검사가 잘린 문제지를 이미 오류로 막고 있었다.

## 2. 무거운 검사는 한 번

| 검사 | 소요 (4코어 작업 기계 실측) | 쓰는 시점 |
| --- | --- | --- |
| `node tools/run-tests.js` (전체 테스트) | 약 9~10분 | 병합 직전 1회 |
| `node tools/check-archive2-runtime.cjs` | 약 3분 | 단계당 1회 |
| Pages 배포 워크플로 | 작업기 배포 대기 최대 14분 포함 | 결과는 Actions에서 확인 |

- 런타임 검사는 작업 폴더의 `archive/data/svg-accessibility-index.js`와 `archive/data/archive2-catalog.json`을 다시 만든다. 의도한 변경이 아니면 `git checkout -- <경로>`로 되돌린다.
- `tools/run-tests.js`는 시작할 때 카탈로그 산출물(`archive2-catalog.json` 등 Archive2 canonical 4종과 `archive2-source-verification/`)을 다시 만들고, 끝나면 건드리지 않은 것만 원래대로 되돌린다. 재생성본을 커밋해야 하면 `APMATH_KEEP_TEST_OUTPUT=1`로 돌린다. 이유: 병합 직후 sync bot 커밋 전에는 커밋본이 낡아서, 전체 테스트마다 작업 트리가 더러워져 실수 커밋 위험이 있었다. 그 밖의 파일은 되돌리지 않고 `CHANGED_DURING_RUN`으로만 알린다.
- main과 비교할 때는 실패한 테스트만 main에서 다시 돌린다. 전체 테스트를 main에서 한 번 더 돌리지 않는다.
- 이유: 구현·검토·수정 때마다 전체 테스트와 런타임 검사를 다시 돌렸고, main 비교를 위해 전체 테스트를 한 번 더 돌렸다.

## 3. 검토는 위험에 맞춰

- 코드 검토자는 바뀐 부분을 읽고 관련 테스트만 다시 돌린다. 구현자가 한 측정을 반복하지 않는다.
- 문서 작업과, 이미 검토를 마친 변경의 단순 병합은 별도 검토를 생략한다. CI와 배포 관문이 마지막 확인을 맡는다.

## 4. 한 번에 하나

- 무거운 작업(전체 테스트, 런타임 검사, Chrome 측정)은 한 번에 하나만 돌린다.
- 이유: 두 작업을 같이 돌리자 시간 기준 테스트(조합 성능, 런타임 검사의 하위 프로세스 시간 초과)가 흔들려 재실행이 늘었다.

## 5. main 합치기와 생성 파일

- main은 PR 직전에 한 번만 합친다.
- 생성 파일(목록·DB·색인·SVG 접근성 색인)이 충돌하면 손으로 고치지 않는다. main 쪽을 받은 뒤 생성기를 한 번만 다시 돌린다.
- 이유: main이 자주 바뀌어 생성 파일이 반복해서 충돌했고, 재생성을 여러 번 다시 했다.

## 6. 테스트는 결함 조건으로

- 계속 늘어나는 운영 데이터(시험지·문항·이미지 수)의 정확한 개수를 테스트에 고정하지 않는다. 누락 0, 중복 0, 깨진 참조 0 같은 결함 조건을 검사한다.
- 이유: 시험지가 늘 때마다 테스트의 고정 숫자를 고치는 수정이 반복됐다.

## 7. 긴 명령은 끝까지 기다린다

- 긴 명령은 백그라운드로 돌리고 완료 표식을 기다린다. 예: `node tools/run-tests.js > run.log 2>&1; echo "RC=$?" >> run.log`를 백그라운드로 실행한 뒤 `until grep -q '^RC=' run.log; do sleep 15; done`.
- 도중에 멈추고 PARTIAL로 끝내지 않는다.
- 이유: 긴 명령을 기다리지 않고 멈춘 작업자를 다시 띄우는 비용이 들었다.

## 8. 작업 지시서

- 완료 증거를 최소로 적는다(예: "알려진 잘림 3건 해결 + 화면 확인 1회"). "전체 측정"처럼 끝이 열린 지시는 쓰지 않는다.
- 기계적인 작업(병합, 재생성, 문서)은 추론 수준을 낮게 두고, 복잡한 로직만 높게 둔다.

## 9. 총괄(ROOT)의 진행 확인과 보고

- 진행 확인은 상태 요약과 마지막 몇 줄만 본다. 큰 상태 파일·로그·대화 기록을 통째로 출력하지 않는다.
- 사용자 보고는 짧게 한다. 결정이 필요한 것은 모아서 한 번에 묻는다.

## 10. 문서 구조 원칙 (apps-in-toss-harness 구조 참고)

- 루트 `AGENTS.md`는 짧은 안내판이고, 영역 문서(`docs/agents/`)는 그 작업을 할 때만 읽는다.
- 현재 진행 상황은 문서에 쌓지 않는다. PR·Actions·이슈에서 확인한다.
- 규칙에는 이유를 한 줄 붙이고, 사고에서 얻은 교훈은 원칙 한 단락으로 남긴다.
- 문서 구조는 검사기로 지킨다(`tests/agents-md-budget.test.js`). 원인보다 결과(실제로 무엇이 읽히는지)를 직접 재는 검사가 더 튼튼하다.

## 11. 테스트 목록 (돌지 않는 테스트를 보이게)

- 모든 테스트 파일은 `tests/test-inventory.json`의 한 칸에 속해야 한다. 칸은 `run`(전체 test 잡에서 돎), `elsewhere`(다른 워크플로·스크립트가 돎 — 잡 이름을 적음), `notRun`(안 돎 — 이유를 적음)이다. `tests/test-inventory.test.js`가 "목록에도 없고 돌지도 않는 테스트"를 막는다.
- 대상: git이 추적하는 `*.test.{js,mjs,cjs}`, `*.e2e.{js,mjs,cjs}` 전부(어느 폴더든)와 `tests/test_*.py`. `tests/` 최상위에서 이름에 `.test.`가 없는 스크립트(`*-browser.cjs`, 하네스 등)는 테스트 진입점이 아니라 대상이 아니다.
- `run`은 규칙이다. `tests/` 바로 아래 `이름.test.js`는 실행기(`tools/run-tests.js`의 `collectTests()`)가 자동으로 모으므로 목록을 고치지 않아도 된다. `.mjs`/`.cjs` 등은 `requiredCommands`에 명령을 추가해야 `run`이 된다(목록 검사는 실행기에서 직접 읽는다).
- `notRun`의 `reason`은 사실만 적는다: `pending`(조사 대기), `finished-campaign`(끝난 캠페인 — 근거 적기), `fails-now`(지금 돌리면 실패 — `local`에 결과·실패 문구, 환경 요인이면 `envFactor`), `quarantined`(실행기 격리 목록). "안 돌려도 됨" 같은 판단은 적지 않는다.
- 안 돌던 테스트를 켤 때는 `notRun`에서 지우고 `requiredCommands`(또는 `.test.js` 이름)로 옮긴다. 로컬·CI에서 통과를 확인하고, 실패하면 고치는 것이 기본이다. `local` 결과는 어느 PC·어느 날짜의 한 번 실행이라 근거이지 판정이 아니다.
- 이유: 이름이 실행기에 없는 `.mjs`/`.cjs` 테스트가 수백 개 꺼진 채였고(고1 문제지 저장이 3주간 전면 실패해도 잡는 검사가 없었다), "있는데 안 도는 검사"는 지켜 주는 것이 없는 것과 같다.

## 12. 알려진 실패 (KNOWN-FAIL 서명)

- 목적: main의 `test`가 물려받은 실패로 늘 빨강이면 PR이 새로 만든 실패가 묻힌다. 그래서 기준을 "초록"이 아니라 "알려진 실패 목록과 정확히 일치"로 삼는다. 고치기가 기본이고, `tests/known-failures.json`에는 자료·영수증 재발급처럼 **지금 못 푸는 것만** 적는다.
- 서명 = 테스트 파일 + 테스트 이름(`testName` 하나 또는 `testNames` 여러 개, 이름이 출력되는 node:test 파일은 필수) + 오류 문구 패턴(`pattern`, 정규식). 패턴은 **CI 로그에서 읽은 실제 문구**로 쓰고, 바뀌기 쉬운 부분(해시 전체·바이트 수·러너 경로·시간)은 뺀다. 너무 넓은 패턴은 새 결함을 삼키므로 애매하면 좁게 쓴다.
- 판정(전체 실행 `tools/run-tests.js`와 범위 실행 `--ci-scope`가 `tools/lib/known-failures.js` 한 곳을 같이 쓴다): 서명이 일치하는 실패는 KNOWN-FAIL로 세고 종료 코드에 영향이 없다. 같은 파일에서 다른 이름·다른 문구의 실패가 나면 FAIL. 알려진 실패가 통과하거나 서명이 달라져 재현되지 않으면 FAIL("예상된 실패가 재현되지 않음 — 목록에서 삭제"). 시간 초과·출력 버퍼 초과·신호 종료는 서명 문구가 이미 찍혀 있어도 항목 유무와 무관하게 무조건 FAIL이다("시간 초과 — 알려진 실패로 보지 않음"): 멈춘 뒤에 무엇이 가려졌는지 알 수 없어 알려진 상태가 될 수 없다. 이름이 없는 스크립트(`node 파일`)는 새 결함을 이름으로 가려낼 수 없으므로, 결함 개수를 세는 줄을 서명으로 함께 적는다(예: `item-4slot data defects found 2 !== 0`).
- 항목 필드: `file`, `testName`/`testNames`(선택), `pattern`, `repair`(수리 목록 번호), `cause`(원인 한 줄, 모르면 "원인 미확정"), `resolvedWhen`(무엇이 되면 풀리는가), `stopsAtFirstFailure`(첫 실패에서 멈추는 테스트라 뒤는 미확인이면 true).
- 항목 추가는 PR 본문에 근거(CI 실행 번호와 읽은 문구)를 적는다. 삭제는 자유다. 고쳐서 통과하게 되면 같은 PR에서 항목을 지운다(안 지우면 위 판정으로 빨강이 된다).
- 매 실행 요약에 "KNOWN-FAIL 목록: N건"과 항목별 한 줄(파일, 수리 번호, 원인, 해결 조건, `stopsAtFirstFailure` 표시)이 나온다. 목록 자체도 실행 시작 전에 검사한다: 저장소에 없는 파일, 실행기가 돌지 않는 파일, 중복, 서명(pattern)이 없는 항목은 막는다.
- 이것은 격리가 아니다. 해당 테스트는 매번 돌고 결과를 서명과 정확히 대조한다. 기존 `quarantined`(파일 단위로 기본 실행에서 빼는 목록)는 그대로이고, 서명 목록으로 옮기는 일은 별도 PR이다.
- 범위 실행에서는 선택된 명령 중 항목이 있는 것만 같은 대조를 한다(선택되지 않은 파일의 항목은 평가하지 않는다).

## 운영 교훈 (2026-10)

- Pages 등록 커밋이 main 경쟁에서 지면 실패가 아니라 경고다. 다음 main의 배포가 등록을 이어받는다.
- 검증 실패는 학생 사이트 배포만 막는다. 병합은 CI와 따로 진행한다.
- 작업기(APMS Worker)는 학생 사이트보다 먼저 배포된다(배포 순서 관문).
