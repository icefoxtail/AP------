## CURRENT HARD — 이미 들어온 시험지의 수정: ① 수정 프로토콜 → ② 작업자 재량 → ③ 원본 대조는 참고 (2026-11-24, 원장님 결정)

모든 라인(Claude·GPT·Codex)과 이어받는 작업자 공통이다. 이 절이 다른 문서·프롬프트·검수표의 "원본 대조 필수·원본 확인 대기·판단 불가·보류" 문구보다 우선한다. 봉인 문서(`docs/rules/MANIFEST.md` 등재 문서)에 어긋나는 문구가 있어도 이 절을 따른다. 이 문서가 이 주제의 상세 서술이고 다른 문서는 여기로 링크한다.

1. **순서.** ① 수정 프로토콜: 최소 수정으로 문항이 성립하게 하고, 직접 풀어 검산하고, 정답·해설·보기를 함께 맞추고, 끝나면 사후 보고한다. ② 작업자 재량: 어떻게 고칠지·무엇을 근거로 삼을지는 작업자가 정한다. ③ 원본 대조: 있으면 쓰는 참고 근거이고, 없다고 해서 보류하지 않는다. 이유: 원장님 결정 2026-11-11 "원본은 크게 중요하지 않아, 최소수정으로 문항 성립하게 만들면 됨".
2. **원본 대조가 필수인 때는 시험지를 처음 만들 때(CREATE·첫 반입)뿐이다.** 그 뒤의 수정은 최소 수정과 작업자 재량이다. 이유: 원장님 결정 2026-11-23 "원본대조가 필수인 건 첫 작업 때만, 그 후 수정들은 최소 수정 및 작업자 재량".
3. **검수 분류는 "수정함 / 오탐" 둘뿐이다.** 문항을 "판단 불가·원본 확인 대기·NOT_REVIEWABLE·source HOLD"로 남기지 않고, 사용자에게 원본 확인을 부탁하지 않는다. 풀 수 있게 고치거나(수정함) 결함이 아님을 밝힌다(오탐). 이유: 원장님 결정 2026-11-23·11-24, 확인 대기로 남기면 고치는 일이 사용자에게 되돌아온다.
4. **문항·시험지 파일을 바이트로 고정하는 보류는 두지 않는다.** "보류된 문항이 있다"는 이유로 시험지 JS·그림·영수증의 바이트가 바뀌면 실패하는 검사는 만들지 않는다(2026-11-24에 `source-quality-hold`·`original-source-error-hold`의 바이트 고정을 코드에서 없앴다: [source-quality-holds-v1.md](../architecture/source-quality-holds-v1.md) 맨 위). 문항 하나에 표시하는 `sourceIssueHold` 같은 값은 남아 있어도 파일을 고정하지 않는다. 이유: 보류가 시험지 파일 전체를 고정해 같은 파일의 다른 문항 오류 수정까지 막았다(2026-11-23 사고). 원장님 결정 2026-11-24 "바이트 고정해 놓은 것 자체가 잘못된 거야. 그 룰 자체를 없애야 돼. 쉽게·넓게·빠르게·변화하게".
5. **이어받는 작업자:** 위 보류 때문에 멈춘 시험지를 만나면 묻지 말고 이 절대로 고친다. 새 보류·고정 검사를 만들지 않는다.

## CURRENT — 먼저 병합하고, 수리는 마지막에 관제가 모아서 한다 (2026-11-17, 사용자 결정)

이 절이 아래 "공유 데이터 고정값" 6번과 다른 문서의 "병합 전에 PR CI가 전부 녹색인지 확인" 문구보다 우선한다.

- **CI 녹색은 병합 조건이 아니다.** 검수를 통과한 변경은 CI 결과와 관계없이 병합한다. CI를 고치느라 병합을 세워 두지 않는다.
- **수리는 병합이 끝난 뒤 마지막에 한다.** 병합 중에 보인 CI 실패는 그 자리에서 고치지 않고 수리 목록에 적어 둔다(실패한 검사, 처음 빨개진 커밋·PR, 짐작되는 원인). 병합 묶음이 끝나면 목록을 한꺼번에 고친다.
- **수리는 관제 세션(병합 순서를 잡는 Claude 메인)이 맡는다.** 각 작업 줄은 자기 PR의 CI를 고치느라 멈추지 않고, 실패를 관제에 알리고 다음 일을 한다. 관제가 수정 작업자와 검수자를 붙여 고친다. 다른 줄이 낸 영수증·고정값이 승인된 변경으로 낡은 경우도 관제가 수정 절차로 갱신한다(사용자 승인 범위 안에서, 갱신 기록을 남긴다).
- **유지하는 것:** 수정자와 다른 검수자의 검수, 바꾼 부분의 관련 테스트 실행, 아래 고정값 절차 1~5번, 테스트·검사를 약하게 만들어 통과시키지 않는 원칙, 보호 규칙 우회·강제 push 금지. 학생 화면이 실제로 깨지는 결함(문항이 안 열림, 그림 깨짐, 정답 오류)은 CI와 별개로 검수에서 잡는다.
- 이유: 2026-11-16~17 밤사이 다른 작업 줄의 병합으로 main CI가 계속 빨갰고, 검수를 통과한 변경 여러 건이 CI 수리를 기다리며 하루 가까이 멈췄다. 한 건을 고치는 사이 다음 병합이 새 실패를 만들어 끝이 없었다. 사용자: "맨날 CI 고치고 있냐. 병합 후에 제일 마지막에 고칠 거 고치자. 수리 필요한 건 여기서 다 수리."

## CURRENT HARD — 공유 데이터 고정값: 원본 시험지·공유 크로스워크·생성문항 Meta (2026-11-03, 사용자 지시)

Claude·GPT·Codex 모든 라인 공통이다. 상세 원문은 [metadata.md](metadata.md) "공유 크로스워크" CURRENT 절에 있다.
이유: 2026-11-02~03에 서로 다른 세션의 정상 작업 때문에 main CI와 학생 사이트 배포가 두 번 막혔다. 원본 시험지 해설만 고쳤는데 테스트의 파일 해시 고정값이 깨졌고(#1263), 크로스워크에 행을 추가했더니 승인 생성문항 약 171건의 Meta 해시가 어긋났다(#1264). 지금은 봉인 레지스트리와 행 검사로 고쳐져 있다(#1264·#1266).

1. 공유 크로스워크(`archive/data/meta-foundation/crosswalks`)는 행을 추가만 한다. 기존 행의 수정·삭제·순서 변경은 하지 않는다. 고쳐야 하면 먼저 사용자에게 보고한다. 승인 생성문항은 자기가 쓰는 행이 그대로인지로 검증되기 때문이다.
2. 생성문항 Meta의 등록·승인은 공식 도구로만 한다(register-approved-generated-meta, auto-register-approved-qid9, backfill-generated-meta, build-generated-meta-browse-aliases). 이 도구들은 그때 읽은 크로스워크 해시를 `archive/data/meta-foundation/crosswalks/sealed-digests.v1.json`에 자동 봉인한다. Meta나 해시 필드(rpmDraftAuthoritySha256, rpmAuthoritySha256)를 손으로 고치지 않는다.
3. 봉인 레지스트리는 손으로 넓히지 않는다. 실제 파일 버전과 맞지 않는 해시는 넣지 않는다. 병합 때 완전히 같은 항목이 겹치는 것은 정상이다(도구가 합친다). 같은 (path, sha256)에 gitBlobSha1이 다르다는 CONFLICTING_GIT_BLOB_SHA1이 나오면 손대지 않고 보고한다.
4. CROSSWALK_DIGEST_NOT_SEALED가 나오면 검사를 끄거나 우회하지 않는다. 해당 공식 도구를 `--write`로 다시 돌려 봉인을 만들고 `--check`로 확인한다. EXISTING_APPROVED_UID_REQUIRES_PINPOINT_REPAIR가 나오면 원인을 조사해 보고한다. 승인 영수증(alive/)과 metaFinalSha256은 고치지 않는다.
5. 원본 시험지 JS(`archive/exams/original`)를 고칠 때는 바뀐 필드(content·answer·choices·solution)를 확인하고, 그 시험지를 고정한 생성문항·테스트 해시가 있는지 grep으로 찾는다(예: `tests/archive2-generated-bank-registration.test.js`). solution만 바뀌었으면 같은 PR에서 고정 해시를 갱신하고 "해설만 수정, 문제·정답·보기 변경 없음" 주석을 단다. content·answer·choices가 바뀌었으면 고정값을 바꾸지 말고 멈춰서 보고한다. 그 문항에서 나온 생성문항을 다시 검토해야 하기 때문이다.
   골든 표본 시험지(`25_효천고_2학기_중간_고1_기출.js`, `25_매산여고_2학기_중간_고1_기출.js`)의 해설 그림(solutionImage*, imageSize*)만 바꿨다면 m2 CREATE gate 테스트 10개가 GOLDEN_SAMPLE_SHA256_MISMATCH로 깨지므로, 같은 PR에서 `node archive/tools/rebind-m2-create-golden-sample-evidence.mjs --source <시험지 경로>`(dry-run) → 같은 명령에 `--write` → `tests/m2-*create-gate*.test.js` 순서로 고정값을 다시 묶는다. 이유: 그림 필드 외(content·answer·choices·solution·문항 수)가 바뀌었으면 도구가 REFUSE하므로 검사를 약하게 하지 않고 안전하게 재고정할 수 있다.
6. 병합 전에 바꾼 부분의 관련 테스트를 직접 돌리고, PR CI의 실패 목록을 읽는다. 특히 "Approved source, scoped Meta, and Consumer validation", "test", "Archive2 runtime guard"를 본다(예전 "Archive2 runtime contract" 등 3개 잡이 이 잡 하나의 단계로 합쳐졌다. 어느 검사가 실패했는지는 실행 요약의 "outcome per check" 표와 단계 이름으로 본다). 실패가 있어도 병합하고, 실패한 검사와 짐작되는 원인을 PR에 한 줄 적어 관제의 수리 목록에 넘긴다(2026-11-17 사용자 결정, 위 절). PR 기술검사는 고정 event base와 실제 검증 snapshot에 결속한다. 이후 main 이동은 병합 충돌·보호 규칙과 별도로 확인하며, 바뀐 입력·직접 의존성·검사기에 해당하는 검사만 재실행한다. 무관한 main 이동만으로 전체 Archive 검사를 반복하지 않는다(이력 재작성·강제 push 금지).
7. 보고에는 한 일, 확인 근거(실행한 명령과 결과), 남은 일, 사용자 결정이 필요한 것을 쓴다. 돌리지 않은 검사는 NOT_RUN으로 적는다.
8. 원본 시험지 JS·메타를 고치는 PR은 생성물(카탈로그·manifest·source-verification index·runtime-bridge-receipt·readiness 등)을 커밋하지 않는다. 병합 뒤 등록기(archive-main-auto-meta)가 만들어 스냅숏으로 커밋한다. PR 검사는 임시 체크아웃에서 생성한 뒤 같은 검증을 한다(Archive2 save round trip은 PR에서 기본 빌드, main·배포는 `--package-only`). 깨진 JS는 이 빌드에서, 중복 questionUid는 PR 등록 투영의 verify-archive-registration에서 여전히 빨갛다. 이유: main이 움직일 때마다 생성물이 충돌해 PR을 세 번씩 다시 만들었다(#2598).

9. **시험지 파일 전체 blob·해시는 "같은 문항인가"의 기준이 아니다 (2026-11-24, 사용자 결정).** 원장님: "변한다고 문항 자체가 날아가는 게 아니면 고정시킬 필요가 있냐. 우린 UID로 각 문항별로 관리하고 있다." 같은 문항인지는 문항 단위(UID + 발문·보기 지문 text-v1, `archive/question-binding.js`)로 판정한다. 그림 경로·해설·배치·`imageSize`만 바꾸는 PR은 옆 파일의 blob 고정값(`<시험지>.meta-*.json`의 `expectedSourceBlobSha1`, `<시험지>.review-receipt.json`의 `candidateGitBlobSha1`, `<시험지>.4slot.json`의 `sourceGitBlobSha`)을 고치지 않는다. 그림 게시 때 blob 치환 스크립트는 필요 없다. 이 칸들은 만든 시점의 기록으로 남기고 지우지 않는다.
   - 코드 쪽 적용: 하네스(`tools/harness/verify_similar_exam.mjs`)의 소형 메타·검수 영수증 blob 비교는 `text-binding-lib.mjs`의 `reviewedSourceTextUnchanged`(고정된 옛 blob을 git에서 읽어 문항별 text-v1 대조)로 통과시킨다. 발문·보기·문항 수가 바뀌었거나 옛 blob을 git에서 못 읽으면 전처럼 거절한다. 솔루션 보정 게이트(`solution-calibration-gate.mjs`)의 골든 표본은 파일 전체 sha256·gitBlobSha를 비교하지 않고 문항별 `solutionSha256`·발췌문으로만 묶는다(위 5번의 골든 표본 재결속은 더 이상 필요 없다. 도구는 남겨 둔다).
   - 계속 막는 것: 같은 실행 안에서 양쪽을 계산하는 대조(중복 UID, 깨진 JS, 깨진 그림 참조, 문항 수 불일치, Pages 봉인), 발문·보기가 바뀐 문항의 낡은 판정 처리(재결속 기록 `text-binding-rebinds` 흐름), 다른 학년 키 같은 실제 결함.
   - 이 칸을 읽는 곳 가운데 이번에 손대지 않은 것(META_PIPELINE_AUDIT·승인 보존·재결속 계열 등록 요청, 4칸 `build-4slot-runtime.cjs`의 15칸 해시 기준선)은 [metadata.md](metadata.md)의 같은 날짜 절에 현황을 적었다.

## CURRENT — 판본 장부: 승인은 그대로 두고 "같은 판본"만 덧붙인다 (2026-11-18, 사용자 결정)

- `docs/operations/edition-ledger/ledger-v1.json`은 추가 전용 장부다. "이 새 판본은 승인된 판본과 같은 것으로 본다"를 행으로 적는다. 기존 승인 기록(영수증·4칸·UI 승인 proof)은 봉인이라 고치지 않는다.
- 행 종류 둘: `renderer`(렌더러 파일의 봉인 판본 → 새 판본, 증거 PNG_BYTE_IDENTICAL 또는 SCREEN_JUDGMENT), `source`(시험지 JS 한 문항의 봉인 판본 → 새 판본, 발문·보기 지문이 같다는 주장과 바뀐 필드).
- 행은 지우거나 고치거나 순서를 바꾸지 않고 끝에만 덧붙인다. `node tools/edition-ledger.mjs --check`가 형식·정규형·추가 전용을 검사한다. `source` 행의 changedFields에 발문·보기(`archive/question-field-layers.js`의 BINDING_FIELDS)가 있으면 거절한다.
- 행을 넣는 때: 배치·그림·렌더러만 고쳐 승인 검사가 낡았지만 학생이 보는 문제는 같을 때. 발문·보기가 실제로 바뀌었으면 행이 아니라 사람 재판정이다.
- 판정: PNG가 바이트 단위로 같으면 도구 증거로 충분하다. PNG가 달라지는 렌더러 항목은 관제의 화면 판정 또는 사용자가 정한다(SCREEN_JUDGMENT는 judgedBy 필수). 작업자가 스스로 승인하지 않는다.
- 이유: 배치 필드 하나, 엔진 파일 하나를 고칠 때마다 관계없는 문항의 승인이 낡아 CI가 빨개졌다(2026-11-18 하루 세 번). 지금(A1)은 형식·검증·목록 도구만 있고 이 장부를 읽는 검사는 아직 없다. `tools/recapture-approved-renders.mjs --list`는 승인 proof가 봉인한 파일 중 현재 코드와 달라진 것을 읽기 전용으로 보여 준다.

## CURRENT — 로그인이 필요한 흐름은 로컬에서 끝까지 실행해 보고 넘긴다 (2026-11-19, 사용자 지시)

- 저장·출제·권한처럼 로그인해야 보이는 흐름을 바꾼 작업은, 실제 Worker 코드를 로컬 DB 위에 올리고 시험용 계정으로 그 흐름을 끝까지 실행한 결과를 완료 기준에 넣는다. "운영 API가 필요해 NOT_RUN"으로 남겨 사용자에게 직접 눌러 보라고 넘기지 않는다. 이유: 문제지 저장·출제, 시간표 개편안에서 사용자에게 운영 확인을 여러 번 부탁했고, 그 사이 아무도 확인하지 않은 흐름이 운영에 나갔다.
- 방법은 그 라인에 허용된 것을 쓴다. 저장 왕복 검사(S1.5)처럼 wrangler 없이 Worker 번들을 로컬 D1에 올리는 테스트 하네스에 실제 Chrome을 붙이는 방식이 기본이다. `wrangler dev` 로컬 모드와 로그인 화면에 시험 계정을 입력하는 방식은 그 라인이 사용자에게 허용받았을 때만 쓴다. 한 라인의 금지 조건은 다른 라인이나 관제의 요청으로 풀리지 않는다.
- 운영에 닿지 않는다: 운영 배포, 운영 D1·R2·운영 API 주소로의 요청은 하지 않는다. 저장소에 로그인 우회 코드·가짜 API·가짜 세션을 넣지 않는다. 시험용 데이터를 심는 스크립트와 계정 값은 저장소 밖에 두고 보고에 적지 않는다.
- 로컬로 잡지 못하는 것(실제 운영 데이터·실제 권한에서만 나는 문제)만 사용자 확인으로 남기고, 무엇이 남았는지 한 줄로 적는다.

## CURRENT HARD — 최신 요청의 작업 범위·종료 조건 우선 (2026-10-10)

- 먼저 최신 사용자 지시의 대상·작업 종류·종료 조건을 따른다. 아래 전수 생산·검수 규정은 명시적으로 맡긴 전체 작업에 적용하며, 기존 문항의 한정 수정 지시를 확대하는 근거가 아니다.
- **한정 수정:** 지정 qid/파일/필드와 수정에 꼭 필요한 직접 의존 부분만 고친다. 변경 영향에 필요한 검증을 1회 수행하고 정한 종료 조건에서 끝낸다. 실제 실패·추가 수정이 있을 때만 영향 부분을 재검한다. CREATE→R1→R2→R3 자동 재진입, unchanged 시험지 전체 재풀이·전수 재검은 금지한다.
- **전체 제작·전수 검수:** 사용자가 전체 작업을 명시하면 기존 전체 품질 절차와 분모를 유지한다. 전수 검수 중 든 ‘예시 qid’와 ‘이 qid만 수정’이라는 명시적 한정을 구별한다.
- 범위 밖 발견사항은 간단히 보고만 하고 임의 수정·전수 조사하지 않는다. 범위 확장은 사용자 승인을 받는다. OWN_AND_FIX도 승인된 범위 안의 책임이다.
- 출시·등록·main 반영까지 요청받았다면(적용 가능한 기존 사용자 지시 포함) 해당 범위의 publication·remote readback·필요한 학생 화면 기술 QA까지 책임진다. 이 책임이 변경하지 않은 전체 시험지 재검의 허가는 아니다. 패치·커밋·draft PR 등 명시된 종료 조건을 main 병합으로 바꾸지 않는다.
- 시작할 때 실제 읽은 관련 정본 경로/버전과 대상·필요 검증·종료 조건만 짧게 밝힌다. 별도 대형 원장·반복 read receipt·새 승인 절차를 만들지 않는다.
