# CLAUDE TASK — AP Math 사용설명서 코드 동기화 루프 엔지니어링 (2026-07-14)

## 0. 실행 지시

이 문서는 Claude Code가 저장소 루트에서 직접 실행할 작업 지시서다.

목표는 `apmath/`의 실제 구현과 `manual/` 사용설명서를 반복 대조하여, 설명서가 현재 운영 화면과 일치하도록 만드는 것이다. 한 번의 대규모 재작성으로 끝내지 말고 아래 루프를 순서대로 수행한다.

```text
코드 증거 수집
→ 기존 설명서 매핑
→ 누락·불일치 판정
→ 같은 양식으로 최소 수정
→ 정적·계약·화면 검증
→ 실패 원인 수정
→ 다음 기능군으로 반복
```

모든 루프가 끝난 뒤 결과 문서를 작성한다. 검수요청서를 별도로 만들지 않는다.

---

## 1. 목적

1. APMath의 최신 사용자 기능을 코드 기준으로 식별한다.
2. 기존 설명서 54개 섹션과 실제 메뉴·화면·버튼·권한을 매핑한다.
3. 누락된 기능, 오래된 경로, 잘못된 표현, 중복 설명을 찾는다.
4. 기존 검색형 카드 양식을 유지해 설명서를 수정한다.
5. 사용자에게 보이지 않는 내부 구현은 설명서에서 제외한다.
6. 수정 후 검색, 대상별 필터, 카테고리, 직접 링크, 모바일 표시가 유지되는지 검증한다.

완료 기준은 “많이 추가함”이 아니라 **실제 코드와 설명서의 확인 가능한 일치**다.

---

## 2. 절대 금지

1. 코드에 존재하지 않거나 동작을 확인하지 못한 기능을 추측해 설명하지 않는다.
2. 커밋 제목만 보고 사용법을 확정하지 않는다. 반드시 현재 소스와 테스트에서 재확인한다.
3. `apmath/` 제품 코드를 설명서에 맞추기 위해 변경하지 않는다.
4. 기존 `manual/manual-data.js` 전체를 재작성하거나 섹션 순서를 무단으로 갈아엎지 않는다.
5. 기존 사용자 문구·카테고리·ID를 이유 없이 변경하지 않는다.
6. 내부 함수명, API 경로, DB 컬럼, 디버그 용어를 일반 사용자 설명에 노출하지 않는다.
7. 권한 차이를 무시하고 원장용 기능을 선생님용으로 안내하지 않는다.
8. foundation 또는 준비 단계 기능을 운영 완료 기능처럼 안내하지 않는다.
9. 사용자 작업 중인 다른 dirty 파일을 수정·정리·삭제하지 않는다.
10. `git add`, `git commit`, `git push`, 배포를 하지 않는다.
11. 전체 저장소 포맷팅, 의존성 설치, 생성물 일괄 삭제를 하지 않는다.
12. 테스트를 통과시키기 위해 제품 계약이나 기존 테스트를 약화하지 않는다.

## 5. 설명서 섹션 양식 계약

신규 섹션은 기존 데이터와 동일한 필드를 모두 가져야 한다.

```js
{
  id: "고유한-kebab-case-id",
  audience: ["teacher", "admin"],
  category: "기존 카테고리",
  title: "사용자가 찾는 행동형 제목",
  summary: "이 기능으로 무엇을 하는지 한두 문장",
  keywords: ["화면 문구", "검색 동의어"],
  whenToUse: "언제 쓰는지",
  entry: "실제 메뉴 진입 경로",
  steps: ["실제 화면 순서에 맞는 단계"],
  cautions: ["권한·저장 단위·데이터 전제 등"],
  faq: [{ q: "실제 발생 가능한 질문", a: "코드 근거가 있는 답" }],
  related: ["관련 기능"]
}
```

작성 원칙:

- 제목은 “~하기”, “~확인하기”처럼 실제 행동을 드러낸다.
- `entry`는 현재 화면의 메뉴명과 버튼명을 그대로 쓴다.
- 단계는 UI 순서대로 쓰며 내부 함수 호출 순서를 설명하지 않는다.
- 저장 위치와 적용 단위가 다르면 주의사항에 명시한다.
- 빈 데이터, 권한 제한, 연결 전제는 확인된 경우에만 안내한다.
- 검색 키워드에는 실제 화면 문구와 사용자가 검색할 쉬운 말을 함께 넣는다.
- 같은 내용을 가진 섹션을 새로 만들기 전에 기존 섹션의 국소 수정 가능성을 먼저 본다.

## 6. 공통 루프 프로토콜

각 루프에서 반드시 아래 7단계를 수행한다.

### Step A — 코드 증거 수집

- 메뉴 라벨, 탭, 버튼, 제목, 빈 상태 문구를 `rg`로 찾는다.
- 해당 렌더 함수와 이벤트 진입점을 읽는다.
- 관련 테스트에서 노출 계약과 예외 조건을 확인한다.
- 필요할 때만 최근 git log를 보조 근거로 사용한다.

### Step B — 설명서 매핑

- 관련 기존 섹션 ID를 찾는다.
- 상태를 아래 중 하나로 판정한다.

```text
MATCH       현재 코드와 일치
STALE       경로·버튼·동작이 오래됨
PARTIAL     핵심 단계나 주의사항 누락
MISSING     대응 섹션 없음
DUPLICATE   다른 섹션과 실질 중복
INTERNAL    사용자 설명 대상 아님
```

### Step C — 수정안 결정

- `STALE/PARTIAL`은 기존 섹션을 최소 수정한다.
- `MISSING`만 신규 섹션을 만든다.
- `DUPLICATE`는 자동 삭제하지 말고 링크 통합 또는 문구 축소를 우선한다.
- `INTERNAL`은 설명서에 추가하지 않는다.

### Step D — 구현

- 기존 데이터 구조와 표현 밀도를 유지한다.
- 한 루프에서는 해당 기능군만 수정한다.
- 수정 후 즉시 문법 검사를 실행한다.

### Step E — 자동 검증

- JS 문법, 데이터 구조, ID 중복, audience, category, keyword 검색 계약을 검사한다.
- 관련 기존 테스트와 신규 계약 테스트를 실행한다.

### Step F — 화면 검증

- 로컬 정적 서버로 `manual/index.html`을 연다.
- 데스크톱과 모바일 폭에서 확인한다.
- 대상 탭, 카테고리, 검색, 바로가기, 펼침 카드, 직접 해시 링크를 점검한다.
- 오류가 있으면 같은 루프 안에서 수정 후 다시 검증한다.

### Step G — 루프 기록

결과 문서의 표에 다음을 누적한다.

```text
기능군 | 코드 근거 | 기존 섹션 | 판정 | 변경 파일 | 테스트 | 남은 위험
```

## 7. LOOP 0 — 기준선과 작업트리 보호

### 목표

현재 설명서와 저장소 상태를 고정 기록하고 다른 작업을 침범하지 않는다.

### 실행

1. `git status --short`를 기록한다.
2. 설명서 파일의 현재 변경 내용을 `git diff -- manual`로 확인한다.
3. `manual-data.js`와 `manual-data-20260711.js`를 함께 실행했을 때 총 섹션 수, ID, 카테고리, audience를 추출한다.
4. 현재 기준은 49개 기본 섹션 + 5개 보강 섹션 = 54개다. 숫자가 다르면 실패로 단정하지 말고 원인을 확인한다.
5. 기존 설명서 테스트를 먼저 실행해 baseline을 기록한다.

### 통과 조건

- 사용자 dirty 파일 목록을 결과 문서에 기록했다.
- 설명서 데이터가 평가 가능하다.
- 기존 실패와 신규 실패를 구분할 수 있다.

## 17. 테스트 추가 기준

가능하면 `tests/manual-current-sync.test.js`를 추가해 다음 계약을 고정한다.

1. 두 데이터 파일을 순서대로 실행하면 정상 데이터가 만들어진다.
2. 보강 스크립트를 두 번 실행해도 섹션이 중복되지 않는다.
3. 필수 필드가 모두 존재한다.
4. 모든 ID가 고유하다.
5. category가 등록된 카테고리와 일치한다.
6. audience 값이 유효하다.
7. 주요 검색어가 관련 섹션을 찾는다.
8. `updatedAt`이 최신 보강 날짜를 표시한다.
9. `manual/index.html`이 데이터 파일을 올바른 순서로 불러온다.

테스트는 UI 구현 세부사항보다 사용자 계약을 고정해야 한다.
