# AP Math 학원 운영 플랫폼 고도화 마스터 플랜

> 문서 성격: 상위 방향 계획서  
> 기준일: 2026-07-11  
> 보완일: 2026-07-13  
> 상태: 실행 조건 보완본 v1.1  
> 대상: AP Math 운영 시스템  
> 목적: AP Math를 수학 학습관리 도구에서 실제 학원 운영 전반을 연결하는 통합 플랫폼으로 확장한다.

---

## 1. 계획의 배경

AP Math는 학생·반·시간표·출결·숙제·진도·상담·성적·시험·OMR·오답·리포트 등 수학 학사관리 영역에서 강한 기반을 갖추고 있다.

반면 실제 상용 학원 운영프로그램은 다음과 같은 운영 흐름을 핵심 가치로 제공한다.

- 신규 문의에서 상담, 진단, 등록까지 이어지는 입학 CRM
- 월별 청구, 납부, 미납, 할인, 환불, 이월을 포함한 수납 업무
- 출결, 청구, 공지, 리포트를 학부모에게 전달하는 메시지 체계
- 원장, 상담실, 데스크, 강사 등 역할별 업무 화면
- 재원, 매출, 퇴원, 등록 전환율을 포함한 경영 분석

따라서 AP Math의 다음 성장 단계는 새로운 학습 기능을 계속 추가하는 것보다 이미 강한 학사관리 기능을 실제 학원 운영 흐름과 연결하는 데 둔다.

---

## 2. 제품 비전

### 비전 선언

AP Math를 수학 수업과 학생 성장을 중심으로 상담, 출결, 수납, 학부모 소통, 경영관리를 하나의 흐름으로 연결하는 학원 운영 OS로 발전시킨다.

### 지향점

```text
문의 유입
  → 상담·진단
  → 등록·반 배정
  → 수업·출결·과제·평가
  → 상담·리포트·학부모 소통
  → 청구·수납
  → 재등록·반 이동·휴퇴원
  → 경영 분석
```

각 단계의 정보가 별도 도구에 분산되지 않고 학생 한 명을 중심으로 연결되어야 한다.

## 3. 기본 원칙

### 3.1 AP Math의 강점을 유지한다

- 시험지, OMR, 오답, 클리닉, 성적 분석 기능을 약화하지 않는다.
- 기존 수업·출결·상담·시간표 진입점을 보존한다.
- 일반 ERP 기능이 수학 학습관리 흐름을 방해하지 않도록 한다.

### 3.2 기능보다 업무의 완결성을 우선한다

화면이나 테이블의 존재를 완료로 보지 않는다. 시작부터 후속 처리까지 실제 업무가 끝나는지를 완료 기준으로 삼는다.

예:

```text
출결 저장 → 학부모 알림 → 발송 결과 확인
월 청구 생성 → 납부 처리 → 미납 관리 → 환불·이월 → 장부 반영
신규 문의 → 담당자 배정 → 방문·진단 → 등록 또는 미등록 사유 기록
```

### 3.3 학생을 중심 데이터로 삼는다

수업, 출결, 과제, 상담, 성적, 수납, 발송, 수강이력은 학생 상세에서 연결되어야 한다.

### 3.4 역할별로 필요한 일만 보여준다

원장, 상담실장, 데스크, 강사, 조교, 조회 전용 사용자의 첫 화면과 권한을 구분한다.

### 3.5 외부 연동 전에 내부 원장을 완성한다

PG, 알림톡, 앱을 먼저 붙이지 않는다. 청구 원장, 발송 원장, 권한, 상태 흐름을 먼저 완성한 뒤 외부 서비스를 연결한다.

### 3.6 개인정보와 변경 이력을 기본 요건으로 둔다

연락처, 상담, 수납, 성적 정보의 조회·수정·내보내기 이력을 남긴다. 보호자별 정보성·광고성 수신 동의, 동의 철회, 퇴원생 보존기간, 파기 예정일과 파기 이력도 Phase 1의 기준 데이터에 포함한다. 구체적인 보존·파기 기간과 발송 요건은 구현 당시 적용 법령과 사용 공급자의 공식 정책을 확인해 별도 준법 체크리스트로 확정한다.

### 3.7 시간 상한과 범위 축소를 적용한다

각 Phase는 착수 전에 시간 상한과 필수 결과물을 확정한다. 상한을 초과할 가능성이 생기면 기간을 무기한 연장하지 않고 부가 기능, 자동화, 외부 연동 순으로 범위를 축소한다. 핵심 업무 흐름을 완주하지 못한 상태에서 다음 Phase의 화면 개발을 시작하지 않는다.

### 3.8 운영과 개발을 분리 가능한 단위로 진행한다

운영 중인 AP Math를 유지하면서 개발하므로 한 번에 하나의 핵심 업무 흐름만 활성화한다. 신규 기능은 기존 업무와 병행 검증하고, 데이터 복구와 이전 방식이 확인된 뒤 기존 수기 장부나 외부 도구를 종료한다.

## 5. 핵심 고도화 축

## 축 1. 학생 360

학생 한 명에 관한 운영 정보를 한 화면에서 파악하게 한다.

핵심 범위:

- 기본정보와 보호자 정보
- 현재 수강반과 과거 수강·반 이동 이력
- 출결·지각·결석·보강
- 숙제·진도·수업 특이사항
- 학교성적·원내평가·오답·클리닉
- 상담 기록과 예정된 후속조치
- 청구·납부·미납·환불·이월
- 학부모 발송 및 열람 이력
- 휴원·퇴원·재등록 이력
- 학생 위험 신호와 담당자 할 일

학생 360은 별도 기능 하나가 아니라 모든 운영 기능을 연결하는 중심 화면으로 정의한다.

---

## 축 2. 신규 문의 및 입학 CRM

등록 전 학생도 정식 관리 대상으로 포함한다.

표준 흐름:

```text
신규 문의
→ 전화상담
→ 방문 예약
→ 레벨테스트
→ 결과 상담
→ 등록 예정
→ 등록 완료 / 보류 / 미등록
```

핵심 관리 항목:

- 유입경로와 문의 목적
- 담당 상담자
- 다음 연락 예정일
- 희망 시간과 추천 반
- 레벨테스트 및 상담 결과
- 예상 수강료
- 보류·미등록 사유
- 상담자·유입경로별 등록 전환율

---

## 축 3. 수납·청구·회계 운영

현재의 수납 기반 기능을 실제 데스크 업무 수준으로 완성한다.

핵심 흐름:

```text
수강료 규칙
→ 월 청구 초안
→ 할인·교재비·특강비 조정
→ 청구 확정·발송
→ 납부·부분 납부
→ 미납 관리
→ 취소·환불·이월
→ 장부·매출 집계
```

내부 수납 원장을 먼저 완성하고 다음 순서로 외부 연동을 진행한다.

1. 현금·계좌이체·카드단말기 수기 수납
2. 영수증·교육비 납입증명
3. 청구 링크와 온라인 결제
4. 현금영수증·PG·단말기 연동

---

## 축 4. 출결·보강·학부모 알림

출결 기록을 단순 상태값이 아니라 운영 이벤트로 확장한다.

핵심 범위:

- 등원과 하원 이벤트 분리
- 결석·지각·조퇴·공결·보강 표준화
- PIN·태블릿 출결
- 미확인 결석 확인 업무
- 결석과 보강의 연결
- 보강 요청·승인·배정·완료 흐름
- 학부모별 출결 알림 수신 설정
- 발송 성공·실패·재시도 기록

Phase 2에서는 출결 이벤트와 발송할 내용을 메시지 원장에 안전하게 기록하는 단계까지만 구현한다. 실제 SMS·알림톡 전송, 공급자 실패 재시도와 학부모 수신 확인은 Phase 4 범위로 둔다.

---

## 축 5. 학부모 소통과 포털

초기에는 별도 앱보다 모바일 웹과 안전한 공유 링크를 우선한다.

학부모 제공 범위:

- 출결 현황
- 수업 진도와 숙제
- 시험 결과와 상담 리포트
- 청구·납부·영수증
- 공지 확인
- 상담·보강 신청
- 개인정보 및 알림 수신 설정

메시지 채널은 알림톡 우선, 실패 시 SMS 대체 구조를 기본으로 하며 모든 발송 결과를 기록한다.

---

## 축 6. 역할별 업무 운영

메뉴 중심 화면을 오늘 처리할 일 중심 화면으로 전환한다.

| 역할 | 핵심 화면 |
|---|---|
| 원장 | 재원·매출·미납·퇴원 위험·등록 전환·교사 운영 |
| 상담실장 | 신규 문의·방문예약·레벨테스트·미상담·재상담 |
| 데스크 | 출결 이상·보강 배정·청구·납부·공지·서류 |
| 강사 | 오늘 수업·출결·숙제·진도·평가·상담 |
| 조교 | 채점·자료 준비·미제출·클리닉 지원 |
| 조회 전용 | 허용된 범위의 제한 조회 |

역할별 메뉴 노출뿐 아니라 조회·수정·승인·발송·내보내기 권한을 서버에서도 강제한다.

---

## 축 7. 경영 대시보드

학사 현황과 경영 현황을 함께 제공한다.

핵심 KPI:

- 전체·학년·반별 재원생 증감
- 신규 문의·상담·등록 전환율
- 휴원·퇴원·재등록 현황과 사유
- 월 청구액·수납액·미수금
- 반별 매출과 정원 가동률
- 출결·숙제·성적 기반 관리 필요 학생
- 상담 예정 및 미수행 현황
- 공지·리포트 발송 및 열람률
- 교사별 담당 인원과 운영 업무 이행 현황

강사 평가는 단순 점수 순위가 아니라 학생 성장, 기록 충실도, 상담·업무 이행을 분리하여 제공한다.

## 6. 실행 체계와 시간 상한

### 6.1 실행 전제

- 기본 실행 체계는 학원 운영 책임자 1명과 AI 개발 도구의 협업을 전제로 한다.
- 운영 정책 결정, 실제 데이터 확인, 외부 사업자 계약과 최종 승인은 사람이 담당한다.
- AI는 조사, 설계 초안, 구현, 테스트 자동화와 문서화를 지원하지만 운영 승인 주체가 되지 않는다.
- 동시에 진행하는 핵심 개발 흐름은 최대 1개, 독립적인 조사·문서·테스트 보조 작업은 최대 2개로 제한한다.
- 운영 장애와 기존 AP Math 회귀 수정은 신규 기능보다 우선한다.

### 6.2 Phase별 권장 시간 상한

아래 기간은 1인 운영 병행 기준의 초기 타임박스이며, Phase 0에서 코드·데이터 감사 후 한 번만 재산정한다.

| Phase | 권장 상한 | 상한 초과 시 우선 축소 |
|---|---:|---|
| Phase 0 기준·감사 | 2주 | 문서 표현·비핵심 통계 |
| Phase 1 공통 기반 | 4~6주 | 고급 검색·부가 이력 화면 |
| Phase 2 일일 업무 | 6~8주 | 자동 추천·고급 CRM 통계 |
| Phase 3 수납 | 6~8주 | PG·현금영수증 자동 연동을 Phase 4 이후로 이동 |
| Phase 4 학부모 연결 | 6~10주 | 네이티브 앱·실시간 채팅·다중 채널 동시 지원 |
| Phase 5 경영 분석 | 4~6주 | 예측 모델·강사 비교 지표 |
| Phase 6 안정화 | 최소 4주 | 축소하지 않으며 필요하면 운영 전환일을 연기 |

전체 순차 일정은 약 8~12개월 범위로 관리한다. 이는 확정 납기가 아니라 범위 통제를 위한 상한 기준이며, 외부 심사·계약 대기 기간은 개발 기간과 별도로 추적한다.

### 6.3 중단·축소 기준

다음 중 하나가 발생하면 해당 Phase를 일시 중단하고 범위를 재승인한다.

- 계획 상한의 80%를 사용했는데 필수 업무 시나리오의 절반도 완주하지 못한 경우
- 기존 시험·OMR·오답·리포트 핵심 회귀가 반복되는 경우
- 기준 데이터가 둘 이상으로 갈라져 단일 원장을 보장할 수 없는 경우
- 외부 공급자나 법적 요건이 확정되지 않아 데이터 모델이 달라질 가능성이 큰 경우
- 운영자가 기존 방식과 신규 방식을 동시에 감당할 수 없는 경우

### 6.4 이번 계획의 범위와 제외 범위

| 포함 | 초기 제외 |
|---|---|
| 단일 학원 중심 운영 | 범용 다사업자 SaaS |
| 모바일 웹 학부모 포털 | 네이티브 iOS·Android 앱 |
| 필수 역할과 권한 | 복잡한 인사·급여·근태 ERP |
| 내부 수납 원장과 선택적 외부 연동 | 자체 PG·메시지 인프라 구축 |
| AP Math/EIE 공통 학생 기반 | 모든 과목·학원 유형용 범용 설정 엔진 |
| 안전한 공지·리포트 전달 | 대규모 실시간 커뮤니티·채팅 플랫폼 |

제외 범위는 핵심 운영 흐름이 안정된 이후 별도 승인 없이 본 계획에 추가하지 않는다.

## 7. 외부 의존성·준법·인프라 선행 계획

### 7.1 외부 서비스 선행 일정

외부 연동은 내부 원장 완성 후 활성화하되, 신청·심사·계약·요건 확인은 더 일찍 시작한다.

| 항목 | 사전 착수 시점 | 활성화 목표 | 선행 산출물 |
|---|---|---|---|
| 알림톡·SMS 공급자 | Phase 2 초반 | Phase 4 | 채널·사업자 계정·템플릿 심사·실패 대체 정책 |
| 온라인 결제·PG | Phase 3 초반 | Phase 4 | 정산 주체·취소/부분취소·웹훅·대사 정책 |
| 현금영수증 | Phase 3 설계 시 | Phase 3 후반 또는 Phase 4 | 발급 주체·필수 필드·취소·재발행 절차 |
| 교육비 납입증명 | Phase 3 설계 시 | Phase 3 | 적용 양식·대상 금액·발급 및 보관 절차 |
| 개인정보·수신 동의 | Phase 0 | Phase 1 | 동의 문안·보존·파기·열람·철회 기준 |

외부 서비스 정책과 법적 요건은 변경될 수 있으므로 계약 또는 구현 직전에 공식 문서와 전문가 검토가 필요한 항목을 구분한다.

### 7.2 Cloudflare 인프라 적합성 판단

Phase 0에서 Pages + Workers + D1 구조를 그대로 사용할지 기능별로 판정한다.

필수 검토 항목:

- D1 트랜잭션 범위와 청구·수납 중복 기록 방지 방식
- 결제 웹훅의 멱등성 키와 중복 수신 처리
- 월 청구 일괄 생성 시 배치 크기와 실패 재개 방식
- 메시지 발송 재시도·지연 처리에 Queues가 필요한지 여부
- 동일 학생·청구서에 대한 동시 수정 제어와 Durable Objects 필요 여부
- 예약 작업, 월 마감, 보존·파기 작업의 실행 방식
- D1 백업·복구, 감사 로그 보존과 대량 CSV 내보내기 한계
- 장애 시 외부 결제·메시지 기록과 내부 원장의 대사 절차

Phase 0 인프라 판정서는 기능별로 `D1/Worker만 사용`, `Queues 추가`, `Durable Objects 추가`, `외부 서비스 위임` 중 하나를 선택하고 근거와 비용을 기록한다.

### 7.3 데이터 이관과 병행 운영 원칙

데이터 이관은 Phase 6의 마지막 작업이 아니라 각 업무 Phase의 착수 조건으로 다룬다.

- Phase 1 전: 재원생, 보호자, 반, 수강 상태, 휴퇴원 이력 표본 이관
- Phase 2 전: 신규 문의, 상담 예정, 보강 미완료 자료 표본 이관
- Phase 3 전: 학생별 수강료 규칙, 할인, 과거 미납, 선수금·이월 표본 이관
- Phase 4 전: 수신 동의, 연락처, 기존 발송 템플릿과 차단 대상 이관

모든 이관은 `추출 → 정제 → 시험 이관 → 건수·금액 대조 → 운영자 승인 → 본 이관` 순서로 진행한다. 수납 데이터는 총건수뿐 아니라 학생별 잔액과 전체 미수금 합계가 일치해야 한다.

## 8. 단계별 추진 로드맵

## Phase 0. 기준 확정과 현황 검증

- 학생, 수강, 보호자, 상담, 출결, 수납의 기준 데이터 정의
- 중복 테이블과 상태값 정리
- 역할·권한 매트릭스 확정
- 운영 DB와 배포 환경 검증

- 기존 데이터 출처와 이관 가능성 조사
- Phase별 기준 데이터 소유권과 장애 복구 책임 확정

착수 조건: 현재 운영 코드와 DB에 대한 읽기 권한, 실제 업무 담당자의 확인 가능 시간, 데이터 샘플이 확보되어야 한다.

정량 완료 기준:

- 전체 대상 기능을 `운영 가능/부분 구현/기반/계획/폐기 후보` 5단계로 100% 분류한다.
- 핵심 엔터티마다 기준 테이블·소유 모듈·식별키를 1개씩 확정한다.
- 청구 중복, 메시지 재시도, 동시 수정, 백업·복구에 대한 인프라 선택을 문서로 승인한다.
- 학생·반·상담·출결·수납 표본 데이터를 최소 10건씩 읽고 기존 자료와 대조한다.

## Phase 1. 운영 공통 기반

- 학생 360 기본 구조
- 수강·반 이동·휴원·퇴원·재등록 이력
- 복수 보호자와 수신 동의
- 역할별 권한과 감사 로그
- 통합 상태·이력 모델
- 보존·파기 예정일과 동의 철회 모델
- Phase 1 대상 데이터 시험 이관

착수 조건: Phase 0 현황·데이터 감사서, 인프라 적합성 판정서, 역할·권한 매트릭스 초안이 승인되어야 한다.

정량 완료 기준:

- 재원·휴원·퇴원·재등록·반 이동 시나리오를 각 1회 이상 완주하고 이력이 모두 남는다.
- 표본 학생 20명의 현재 상태·반·보호자 정보가 원자료와 100% 일치한다.
- 관리자·강사·데스크·조회 전용 계정으로 금지된 API 접근 테스트가 모두 거부된다.
- 개인정보 동의 철회와 파기 예정 대상 조회 시나리오를 검증한다.

## Phase 2. 매일 사용하는 운영 업무

- 역할별 오늘 할 일
- 신규 문의 CRM
- 상담 후속조치와 일정
- 출결 이벤트와 미확인 결석
- 보강 요청·배정·완료
- 메시지 발송 원장: 발송 예정 내용과 상태 기록까지이며 외부 전송은 포함하지 않음
- Phase 2 대상 데이터 시험 이관

착수 조건: 학생 360 기준 데이터, 역할별 권한, 신규 문의·상담·출결·보강 상태값이 확정되어야 한다.

정량 완료 기준:

- 문의→상담→진단→등록/미등록 흐름을 최소 10건의 표본으로 완주한다.
- 결석→확인→보강 요청→배정→완료 흐름을 최소 5건 완주한다.
- 상담실·데스크·강사 각 역할이 5일간 시험 운영하며 핵심 업무를 별도 메모 없이 재현한다.
- 생성된 출결·상담·보강 이벤트의 메시지 원장 기록 누락이 0건이어야 한다.

## Phase 3. 수납 업무 완성

- 수강료 및 부가비용 규칙
- 월별 청구 생성
- 납부·부분 납부·미납
- 할인·환불·이월
- 영수증·납입증명
- 일·월 장부와 매출 집계
- 기존 수강료 규칙·미납·선수금·이월 데이터 이관
- 결제·현금영수증 외부 연동 요건 확정

착수 조건: 수납 상세 설계, 금액 계산 규칙, 이관 대조표, 중복 방지·취소·감사 정책이 승인되어야 한다.

정량 완료 기준:

- 실제와 동일한 표본 데이터로 한 달치 `청구→납부→미납→할인→부분납부→환불/이월→월마감` 1사이클을 완주한다.
- 학생별 잔액 합계, 전체 청구액, 수납액, 환불액, 미수금이 원장과 대시보드에서 100% 일치한다.
- 같은 요청을 두 번 보내도 청구·납부가 중복 생성되지 않는 테스트를 통과한다.
- 시험 이관 전후 학생별 잔액과 전체 미수금 대조 차이가 0원이어야 한다.

## Phase 4. 학부모 연결

- SMS·알림톡 실제 발송
- 출결·청구·공지·리포트 템플릿
- 모바일 학부모 포털
- 상담·보강 신청
- 온라인 결제 연동
- 공급자 실패·중복 웹훅·재시도·대사 처리

착수 조건: 승인된 메시지 채널·템플릿, 수신 동의 데이터, 내부 수납 원장, 학부모 인증 방식, 외부 서비스 장애 대응 절차가 준비되어야 한다.

정량 완료 기준:

- 동의한 테스트 수신자에게 출결·공지·청구·리포트 메시지를 각 1회 이상 실제 발송하고 결과를 원장과 대조한다.
- 공급자 실패를 강제로 발생시켜 재시도 또는 SMS 대체 흐름을 검증한다.
- 결제 성공·실패·취소·부분취소·중복 웹훅 시나리오를 각각 통과한다.
- 학부모 테스트 사용자 5명이 모바일에서 자녀 정보·출결·청구를 확인하고 타 학생 정보에는 접근하지 못한다.

## Phase 5. 경영 분석

- 등록 전환 분석
- 재원·휴퇴원·재등록 분석
- 매출·미납·정원 가동률
- 학생 이탈 위험
- 역할·교사·반별 운영 KPI

착수 조건: 학생·CRM·수납·발송 원장의 기준 데이터가 안정되고 KPI 정의서가 승인되어야 한다.

정량 완료 기준:

- 재원생 수, 신규 등록, 퇴원, 청구액, 수납액, 미수금을 원자료와 대조했을 때 차이가 0이어야 한다.
- 원장이 월간 운영 점검 1회를 별도 엑셀 재집계 없이 완료한다.
- 모든 KPI에 계산식, 기준일, 포함·제외 조건과 원본 데이터 위치가 표시된다.

## Phase 6. 운영 안정화

- 모바일·브라우저 실사용 검증
- 대량 데이터 및 동시 사용 테스트
- 권한·개인정보·감사 검증
- 메시지·결제 실패 복구
- 백업·복원·CSV 내보내기
- 사용자 교육과 운영 매뉴얼

착수 조건: Phase 1~5의 필수 시나리오와 데이터 대조가 통과되고 롤백·백업·지원 담당이 정해져야 한다.

정량 완료 기준:

- 최소 4주간 기존 방식과 병행 운영한다.
- 기간 중 발생한 청구·수납 금액 불일치가 0원이며 미처리 메시지·보강·상담 건을 매일 추적한다.
- 백업에서 복원하는 모의훈련과 외부 결제·메시지 대사 훈련을 각각 1회 성공한다.
- 치명적 결함 0건, 미해결 고위험 결함 0건 상태에서 운영 전환을 승인한다.

## 10. 성공 기준

### 운영 효율

- 출결, 상담, 수납, 발송을 별도 장부에 중복 기록하지 않는다.
- 미확인 결석, 미납, 상담 예정, 보강 미배정을 당일 화면에서 확인한다.
- 학생 문의부터 퇴원·재등록까지 이력이 끊기지 않는다.

### 학부모 경험

- 출결과 청구 알림이 실제로 전달되고 실패 여부를 학원에서 확인할 수 있다.
- 성적·상담·수업 정보를 모바일에서 안전하게 확인할 수 있다.
- 보강·상담 요청의 처리 상태를 확인할 수 있다.

### 경영 관리

- 등록 전환율, 미납액, 퇴원율, 반 정원과 매출을 별도 엑셀 없이 확인한다.
- 위험 학생과 필요한 후속조치를 데이터로 식별한다.

### 시스템 품질

- 화면만 존재하는 기능과 실제 완료된 기능을 명확히 구분한다.
- 역할별 권한이 UI와 API 양쪽에서 일치한다.
- 중요 변경과 개인정보 접근 기록을 추적할 수 있다.
- 결제·메시지 외부 서비스 실패 시 재처리할 수 있다.

## 11. 범위 관리 원칙

- 각 Phase 시작 전 현재 구현과 중복되는 기능을 다시 확인한다.
- 한 Phase에서 핵심 업무 흐름을 완성하기 전 새로운 부가 기능을 추가하지 않는다.
- 외부 앱과 결제 연동은 내부 원장과 상태 흐름이 안정된 후 진행한다.
- 기존 시험·OMR·오답·리포트 기능의 회귀를 필수로 검사한다.
- AP Math와 EIE 공통 데이터는 통합하되 과목별 학습 로직은 독립적으로 유지한다.
- Phase 시간 상한의 80% 시점에 범위·결함·운영 부담을 재검토한다.
- 외부 심사나 계약 지연은 내부 핵심 흐름의 완료로 간주하지 않으며 별도 의존성 보드에서 관리한다.
- 운영 전환은 기능 시연이 아니라 정량 완료 기준과 데이터 대조를 통과해야 승인한다.

## 13. 최종 방향
