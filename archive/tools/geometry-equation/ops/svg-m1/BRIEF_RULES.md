# 엔진 확장 지시서 쓰는 법 (실패 기록에서 나온 규칙, 2026-10-31)

엔진 빈틈 G1~G11을 Sonnet 작업자에게 하나씩 맡기며 생긴 실패와 그 원인이다. 다음 오케스트레이터와 작업자는 지시서를 쓰기 전에 이 문서를 읽는다. 템플릿은 `briefs/engine-gap-template.md`.

## 1. 실패 사례와 원인

| 묶음 | 결과 | 실제 원인 | 지시서 쪽 문제 |
|---|---|---|---|
| G6 (그래프 위 원) | 원 안쪽·원과 곡선 사이 색칠 미구현 | 엔진에서 곡선 영역(G5)과 원호 영역이 서로 다른 모듈이다 | "범위가 크면 색칠은 미뤄도 된다"고 써서 빠져나갈 길을 열어 줬다 |
| G6b (원 후속) | 원과 곡선 사이 영역 미구현 | 위와 같다 | "경계에 원호 허용"만 쓰고 **곡선 조각+원호를 한 경계로 잇는 것**을 명시하지 않았다 |
| G6b | 원 그림에서 삼차 극점 배치 실패 | 극점은 `requiredPoints` 필수 → 좌표 띠가 넘친다 | 새로 만든 `coordinateBand.hide`를 이 필수 규칙과 **연결하라**고 쓰지 않았다 |
| G6b | 접점(겹근) 교점 미탐지 | 교점 계산이 부호 변화 탐색이라 접하기만 하는 점을 못 찾는다 | **계산 방법**(SymPy로 연립 풀기·겹근)을 적지 않았다 |
| G6 | 작업자가 "해설 그림 없음"이라 보고했는데 실제로 있었다 | 작업자가 `solutionImage` 한 필드만 있는 경우를 놓쳤다 | 기존 그림 확인 방법을 정하지 않았다 |
| G7 | 작업자가 파일을 CRLF로 저장해 diff가 1만 2천 줄 | Windows 기본 줄바꿈 | LF 규칙이 없었다(G9부터 추가) |
| G7·G6b·G6c | 배치에 실패한 눈금(y=-1)·좌표(P(1/3,1/3))·원점 이름 O를 작업자가 **지우고** 완료로 보고 | 이름 있는 점의 좌표 지시선이 그래프 경로에 없었음(G6c에서 추가), 같은 자리 점이 라벨 경쟁자로 잡힘 | "필수 라벨을 지우지 말라"는 문구와 대안(지시선으로 끌어내기, 좌표 띠, 축 보조선)이 없었다 |
| G7·G6 | 샘플이 2019·2022년 | 최신 연도 기준이 지시서에 없었다 | 학원은 최근 3~5년 고등 기출을 주로 쓴다 |

한 번에 기능 4개+샘플 3개를 맡긴 G6b는 28분·도구 호출 145회가 걸렸고 그중 3개가 빠졌다. **Sonnet 능력 문제가 아니라 지시서가 "무엇을"만 쓰고 "어떻게"를 비워 둔 것**이 주원인이다.

## 2. 지시서 규칙

1. **기능마다 설계를 적는다.** 각 기능에 ① plan 필드 모양(예시 JSON 한 줄) ② 계산 방법(어느 모듈, 어떤 알고리즘·SymPy 호출) ③ 관측기가 최종 SVG에서 다시 계산해 확인할 것 ④ 거절할 경우와 오류 코드 이름 후보. "가능하면", "범위가 크면 미뤄도 된다" 같은 탈출 문구를 쓰지 않는다.
2. **기존 규칙과 충돌하는 곳을 미리 찾아 적는다.** 새 기능이 기존 필수 규칙(예: 극점 `requiredPoints` 필수, 같은 배율, 세로 1/2 압축 한도)과 부딪히면 어떻게 연결할지 지시서에 쓴다. 모르면 먼저 짧은 읽기 전용 조사를 한다.
3. **한 묶음 = 기능 1~3개.** 그보다 많으면 나눈다. 샘플 문항은 2개.
4. **샘플은 최신 고등부터.** `archive/exams/original/high/**`의 26_ → 25_ → 24_. 못 찾으면 그때만 내려가고 보고에 이유를 적는다. 실제로 막힌 문항(예: 이전 묶음에서 못 그린 문항)이 있으면 그것을 샘플로 쓴다.
5. **기존 해설 그림 확인 방법을 정해 준다.** 문항 객체에서 `solutionImage`로 시작하는 키가 하나라도 있으면 기존 그림이 있는 것이다. 그 SVG/PNG를 렌더해 새 그림과 나란히 보고, 정답 노출 여부와 함께 더 나은지 판단을 적게 한다.
6. **못 한 것은 "한계"로 끝내지 않는다.** 작업자가 못 한 항목은 이유(엔진 구조/규칙 충돌/알고리즘)를 적게 하고, 오케스트레이터는 그 항목으로 **후속 묶음(예: G6b → G6c)을 설계해 바로 이어서** 맡긴다.
7. **고정 문구**(템플릿에 들어 있음): 워크트리 생성 명령, 정션, LF, 관련 테스트만, 정답지 전후 바이트 동일, golden-out 폴더에 쓰지 않기, 시험지 JS 수정 금지, push·PR 금지, 백그라운드 작업 남기지 않기, 보고 8줄.

8. **필수 라벨을 지워서 배치를 통과시키지 않는다.** 점 이름·좌표·눈금이 자리가 없으면 먼저 기존 수단(좌표를 빈 자리로 끌어내 지시선으로 잇기 — 좌표 그림의 `A(3,9)` 방식, 좌표 띠, 축 보조선, E37 끌어내기)을 쓰고, 그래도 안 되면 엔진 빈틈으로 보고해 엔진을 고친다.

9. **라벨 문제의 기본 해결책은 지시선으로 끌어내기다(사용자 지시 2026-10-31).** 점 이름·좌표·눈금·곡선 이름·각·길이 라벨이 자리가 없거나 어느 것의 라벨인지 헷갈리면 빈 자리로 끌어내 주인(점·곡선 위 점·눈금)에서 가는 선으로 잇는다. 지시서에는 라벨 종류마다 지시선 후보를 넣고, 작업자는 "배치 한계"로 보고하기 전에 이것부터 쓴다. 지시선 검사(`*_LEADER_NOT_ON_OWNER/LABEL`)를 재사용한다.

10. **정답지 회귀는 표본으로 한다(사용자 지시 2026-10-31).** 작업자·검수자 모두 바뀐 코드가 그리는 정답지 표본 10개 안팎과 새 항목만 렌더해 바이트 비교한다. 정답지 전체(120개 이상, 약 75분) 회귀는 사용자 승인이 있을 때만 한다. 재검수는 수정 커밋의 diff·관련 테스트·실패했던 문항만 본다. 이유: 전체 회귀는 시간·토큰이 크고, 표본으로도 공용 코드 회귀를 충분히 잡는다.

## 3. 검수 지시서 규칙
- 검수자에게 **작업자가 바꾼 기존 테스트가 있으면 이유가 정당한지** 꼭 보라고 쓴다.
- 삭제된 오류 코드가 정말 사라졌는지는 오케스트레이터가 `git grep -c <코드> origin/main` / `HEAD`로 직접 확인한다(검수자 보고만 믿지 않는다).
- 검수자가 테스트 통과 수치를 못 잡으면 오케스트레이터가 `node --test --test-reporter=tap <파일>`로 직접 확인한다.

## 4. 게시 규칙(엔진 묶음 끝마다)
- 엔진 PR 머지 → 샘플 그림을 시험지 JS에 게시하는 PR → 머지 → 원격 main 읽어 확인.
- 기존 그림이 있으면 나란히 비교해 **새 그림이 낫거나 기존이 정답을 노출할 때만** 교체(새 파일 이름 `-v2`). 비슷하거나 기존이 나으면 게시하지 않는다.
- 게시 확인: `solutionImage*` 외 변경 없음, `tests/m2-*-create-gate-*.test.js` 통과, `verify-published.mjs`로 해설 페이지 표시 확인.
